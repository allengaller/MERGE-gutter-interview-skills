## 1. 节点 DiskPressure，Pod 开始被驱逐

**一句话**｜先看是**根盘满**还是 **imagefs（容器运行时空间）满**——90% 的情况是后者，且是镜像和日志没人清。

**30 秒答**｜kubelet 有 eviction 硬/软阈值，默认针对 `nodefs.available`、`imagefs.available`、`memory.available`。
`imagefs` 就是 containerd/docker 的根目录（`/var/lib/containerd`），
**镜像 GC 只在磁盘吃紧时才激进回收**，所以平时会堆到几十上百 GB。
`kubectl describe node <n>` 的 Conditions 里 `DiskPressure=True`，Events 有 `FreeDiskSpaceFailed` 更直接。
处置顺序：先 `crictl rmi --prune`（清未使用镜像，最见效）→
清容器日志（`/var/log/pods` 软链到 `/var/log/containers`，看 `json.log.*` 有没有 size limit）→
清空目录和已退出容器（`crictl rm $(crictl ps -a -q --state Exited)`）→
再考虑扩盘。
**判断线**：`df` 满了但 `du` 加起来对不上 → **有进程持有已删除文件的句柄**，`lsof +L1` 找出来重启它。

**弹药**
- `df -h / /var/lib/containerd /var/lib/kubelet` 分别看（**三个可能不同盘**）
- `du -sh /var/lib/containerd/* /var/log/* | sort -h | tail`
- `crictl imagefsinfo` / `crictl rmi --prune`
- kubelet 侧配置：`--image-gc-high-threshold`（默认 85）/ `--image-gc-low-threshold`（默认 80），
  日志 `containerLogMaxSize`（**默认 10MB**）+ `containerLogMaxFiles`
- 驱逐是**软隔离**：不保证业务无损，节点级故障优先靠**提前告警**而不是等驱逐

**红线**｜❌ 直接 `rm -rf /var/lib/containerd/*`。会让 containerd 元数据和实际不一致，节点直接不可用——用 `crictl rmi`。

**下一问**｜"驱逐（eviction）和 OOMKilled 是同一回事吗？"（→ 驱逐是 kubelet 主动按策略丢 Pod，OOM 是内核 cgroup 杀进程）

## 2. PVC 一直 Pending

**一句话**｜静态卷看有没有可用的 PV（含 node affinity / zone 约束），动态卷看 StorageClass 和 provisioner 有没有报错。

**30 秒答**｜`kubectl get pvc` 的 `STORAGECLASS` 和 `VOLUME NAME` 两列先分开看：
VOLUME 为空 → 没绑上；有值但状态还是 Pending → 卷在创建中或**等首次使用**。
三种典型：
（1）`StorageClass` 不存在 / 名字写错（PVC 上没写 sc 且集群没有 default sc → **永远 Pending**，报错信息很含糊）；
（2）provisioner 挂了或权限不对（云盘创建失败）——`kubectl describe pvc` 的 events 里有
`persistentvolume-controller` 还是外部 provisioner 的报错，**两者的责任方完全不同**；
（3）**`WaitForFirstConsumer`**：这是延迟绑定模式，PVC Pending 是**正常状态**，
必须等 Pod 调度到某节点后才创建卷——这时真正要查的是那个 Pod 为什么 Pending。
**判断线**：看到 PVC Pending 先 `kubectl get sc <name> -o yaml` 看 `volumeBindingMode`。

**弹药**
- `kubectl get pvc -n <ns>` + `kubectl describe pvc <p> -n <ns>`（只看 Events）
- `kubectl get sc` / `kubectl get pv`（`Available` vs `Bound` vs `Released`）
- `kubectl get events -n <ns> --field-selector involvedKind=PersistentVolumeClaim`
- 注意 **`Released` 状态不会自动回收**：静态卷被删后 PV 留在 Released，要手动清 claimRef 才能重用

**红线**｜❌ 以为 WaitForFirstConsumer 的 Pending 是故障，去"重建 PVC"——重建会丢绑定关系，正确做法是解决 Pod 调度。

**下一问**｜"Immediate 和 WaitForFirstConsumer 各自的代价是什么？"（→ 前者卷可能跨 zone 导致 Pod 调度不上，后者首启多等一次卷创建）

## 3. Pod / PVC 卡在 Terminating

**一句话**｜Terminating 不是"慢"，是**有人不放行**：要么 kubelet 清理失败（卷卸载不掉），要么 finalizer 没人摘。

**30 秒答**｜先分清是哪一类：
Pod 卡 Terminating 常见是**卷 unmount/detach 失败**或**容器进程不接受 SIGKILL**（D 状态，通常是 NFS/云盘 IO 挂住），
`kubectl describe pod` + 节点上 `ps -eo stat,cmd | grep '^D'`、`dmesg | tail`（NFS `not responding`、`I/O error`）。
PVC/PV 卡 Terminating 是 **finalizer**：`kubernetes.io/pvc-protection`（还有 Pod 在用）
和 `kubernetes.io/pv-protection`（外部 provisioner 没删完）。
判断线：**finalizer 能不能手摘，取决于"底层资源会不会泄漏"**——
PVC 手摘 finalizer 会让云盘变孤儿（还在扣钱），PV 摘了会让 provisioner 永远忘记它。
所以先解决"谁还在用"，实在要强行摘，必须**记录卷 ID 人工确认后端已删**。

**弹药**
- `kubectl get pvc <p> -o jsonpath='{.metadata.finalizers}'`
- `kubectl get pod <p> -o jsonpath='{.metadata.deletionTimestamp} {.status.phase}'`（有 deletionTimestamp 但没进 Succeeded/Failed = 卡住）
- 节点侧：`mount | grep <volume-handle>`、`lsblk`、`journalctl -u kubelet | grep -i unmount`
- CSI 侧：`kubectl logs -n <csi-ns> <csi-attacher/controller pod>`；attach/detach 由 **CSI 的 external-attacher + NodeDriverRegistration** 驱动

**红线**｜❌ 把 `kubectl delete --force --grace-period=0` 当日常手段。它只绕过 apiserver，节点上的卷和挂载还在，之后一定出更恶心的问题。

**下一问**｜"什么时候你允许自己用 --force？"（→ 节点确认已隔离/已下线，且业务能容忍该 Pod 可能还在跑）

## 4. 云盘（RWO）无法跨节点挂载

**一句话**｜块存储只能挂一个节点，所以 Pod 一旦被调度到别的节点，卷永远挂不上——这是拓扑约束，不是 CSI bug。

**30 秒答**｜`ReadWriteOnce` 的真实含义是"**一个节点**能读写"，
云盘（EBS/云盘/Cinder）还多一层限制：**必须和目标实例同可用区**。
所以现象是 `pod was scheduled to node-a but volume is in zone-b` 或 `Multi-Attach error`。
定位看 `kubectl describe pod` 的 `MountVolume.SetUp failed` / `AttachVolume.Attach failed`，
再 `kubectl get pv <pv> -o jsonpath='{.spec.nodeAffinity}'` 看卷的 zone 约束。
根治三选一：
（1）用 `volumeBindingMode: WaitForFirstConsumer`（从源头保证卷和 Pod 同 zone）；
（2）工作负载加 `nodeAffinity`/`podAntiAffinity` 钉住拓扑（有状态服务用 StatefulSet + 拓扑 spread）；
（3）需要多节点读写就换 **NAS/ReadWriteMany** 类文件存储（代价是延迟和一致性）。

**弹药**
- `kubectl get pv -o custom-columns=NAME:.metadata.name,ZONE:.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0],ACCESS:.spec.accessModes`
- `kubectl get volumeattachment` — attach 层的真相（比 Pod events 更早暴露问题）
- 驱逐后重建到新节点 = 触发一次 detach+attach，**这个窗口就是不可用时间**，说得出这点是加分
- `kubectl cordon` 保流量、`kubectl drain` 前先确认 PDB，别在故障高峰期做卷迁移

**红线**｜❌ 用 `ReadWriteMany` 兜底所有场景。NFS 上跑数据库的延迟和锁语义问题，比调度失败更贵。

**下一问**｜"有状态服务你怎么做跨可用区高可用？"（→ 优先应用层多副本+主从，而不是指望块存储漂移）

## 5. 挂载慢：Pod 起来了但迟迟不 Ready

**一句话**｜挂载分 **attach（接到实例）和 mount（文件系统挂到目录）两段**，慢在哪段决定找谁。

**30 秒答**｜attach 慢通常是云 API 限流/实例已达卷数上限（每机型能挂的盘数有限，常见 16/32 块），
`VolumeAttachment` 对象创建成功但 status 不 ready；
mount 慢常见于**大文件系统做 fsck**、NFS 服务端握手/权限（root squash）反复重试、
或者**目录里有几十万小文件**导致 bind mount 后的探测慢。
判断线：看 Pod events 里 `SuccessfulAttachVolume` 和 `Mounted` 两个时间戳的差，
前者慢找云厂商/配额，后者慢找存储服务和 OS。
**大量 Pod 同时挂载慢**基本是同一个原因：**controller 串行度太低或云 API 限流**（`external-provisioner`/`external-attacher` 的 `-worker` 数）。

**弹药**
- `kubectl get volumeattachment -w` / `kubectl describe pv <pv>` 看 events 时间戳
- `dmesg -T | tail -50` 节点侧看内核挂载报错（`XFS (vdb): mounting...`、`Buffer I/O error`）
- `blkid` / `lsblk` 确认设备是否出现（设备没出现 = attach 层，出现了挂不上 = fs 层）
- CSI driver 的 `DaemonSet` 日志在**节点侧那个 container**（node plugin），controller 日志在 controller pod，别找错

**红线**｜❌ "多给点超时时间就好了"。超时掩盖的是配额或限流，下一次批量扩容会再炸。

**下一问**｜"你怎么给存储操作定义 SLO？"（→ 分位数拆成 attach 时延 / mount 时延 / IO 延迟三段，各自有阈值）

## 6. 文件系统变只读

**一句话**｜内核发现 IO 错误会主动把 fs 重挂为 `ro` 保护数据，所以"只读"是**症状**，根因一定在块设备层。

**30 秒答**｜`mount | grep ro,` 或 `dmesg -T | grep -i 'read-only file system'` 确认；
根因三类：底层盘故障/掉盘（云盘快照回滚、实例迁移）、
文件系统本身损坏（非正常关机后 journal 不一致）、
内核/驱动 bug 或 IO 调度超时。
处置：先看同节点是否**只有这一个卷**出问题（个例）还是多卷同时（HBA/驱动/内核级）；
单卷 → 迁移 Pod、节点 cordon、云侧换盘/快照恢复；
fs 损坏 → 卸载后 `xfs_repair` / `fsck`（**注意 ext4 对已挂载盘 fsck 会毁数据**）。
应用侧表现是 `Input/output error` 或 `Read-only file system` 写失败，
**这时先止血（切副本、摘流量），不要在故障节点上做修复实验**。

**弹药**
- `dmesg -T | grep -iE 'i/o error|remounting|EXT4-fs error|XFS'`
- `findmnt -no OPTIONS /var/lib/kubelet` 看 `ro` / `errors=remount-ro`
- `smartctl -a /dev/vdX`（自建）/ 云侧控制台看盘状态与事件
- `cat /sys/block/vdb/queue/rotational`、`iostat -x 1` 看 `%util` 和 `await`

**红线**｜❌ 在还挂着的卷上直接 `fsck`。必须先卸载（umount），否则必然造成二次损坏。

**下一问**｜"如何提前发现盘要坏？"（→ iostat 的 await/util 趋势 + dmesg 错误计数 + 云厂商事件订阅）

## 7. inode / 文件句柄耗尽（磁盘没满但写不进去）

**一句话**｜`No space left on device` 有两个来源：**块用完了**和**inode/句柄用完了**——`df -h` 看不出后者。

**30 秒答**｜三条排查线：
`df -i`（inode 使用率，几十万小文件就能把 inode 吃光）；
`/proc/sys/fs/file-nr` 与容器 cgroup 的 `limits.nofile`（进程级 fd 泄漏，报 `Too many open files`）；
`ulimit -n`（K8s 里默认继承容器运行时，常见 **1024 软限制**，高并发服务必爆）。
定位工具：`lsof | wc -l`、`ls /proc/<pid>/fd | wc -l`、
`for d in /*; do echo "$d $(find $d -xdev | wc -l)"; done | sort -k2 -n | tail` 找 inode 大户目录。
**判断线**：报错是 `Too many open files` → 句柄；`No space left` + `df -h` 有余量 → inode。

**弹药**
- `df -i /` + `df -h /`（**两个都要看**，说这题只说 df -h 就是没做过）
- `cat /proc/sys/fs/file-max` / `file-nr`
- 修 fd：`securityContext` 不能设 ulimit，要靠**改运行时默认**或 `privileged` 下 `prlimit`；更常见是修应用别泄漏
- K8s 侧：`/etc/sysctl.d` 的 `fs.file-max` 在容器里是**namespace 共享**的，调它影响全节点

**红线**｜❌ 建议"把 inode 加大"就完事（重建文件系统）。真正的答案是**找出为什么有百万小文件**——通常是日志切片、缓存、临时文件没清理。

**下一问**｜"高并发服务你在 K8s 里怎么系统性设置 fd/连接数上限？"

## 8. PVC 在线扩容

**一句话**｜要 **StorageClass 开 `allowVolumeExpansion`** + 扩容 + 可能补一次文件系统 resize，三步缺一不可。

**30 秒答**｜直接改 PVC 的 `spec.resources.requests.storage`（**只能改大，不能改小**），
控制器把请求传给 CSI；PV 容量先到，文件系统扩展由 **CSI node plugin 在下一次挂载周期或 kubelet resize 时做**，
所以会出现"PV 已经 200Gi 但 `df` 还是 100Gi"的中间态——**这不是失败，是时序**。
不自动 resize 的老驱动/某些场景需要手动 `pvs/vgresize + resize2fs/xfs_growfs`，或重启 Pod 触发挂载时扩展。
判断线：`kubectl get pvc` 看 status 里 `Allocated resources` / condition `Resizing`，
再看 `kubectl get pv` 容量与节点上 `lsblk` 设备大小、`df` 文件系统大小**三者是否一致**。

**弹药**
- `kubectl patch pvc <p> -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'`
- `kubectl get pvc <p> -o jsonpath='{.status.conditions}'`
- `xfs_growfs /mountpoint`（xfs 支持在线扩）/ `resize2fs /dev/vdb`（ext4）
- 前提检查：`kubectl get sc <sc> -o jsonpath='{.allowVolumeExpansion}'` 必须 true

**红线**｜❌ 以为改完 PVC 就生效、立刻去 `df` 确认然后宣布失败。要按 attach→fs 两段看，并注意有些驱动要求 Pod 重建。

**下一问**｜"扩容后如何防止 Pod 又因为突发写爆盘？"（→ 配额 + 容量水位告警 + 应用侧限流，扩容不是终态方案）

## 9. 备份与恢复：VolumeSnapshot / etcd / 应用层

**一句话**｜快照恢复的难点从来不是"怎么恢复"，是**"RPO 多少、恢复到哪一刻的应用状态算一致"**。

**30 秒答**｜三层要分开设计：
（1）**卷级**：`VolumeSnapshotClass` + `VolumeSnapshot` → 恢复是新 PVC，
注意**云盘快照是崩溃一致性（crash-consistent）**，数据库需要应用层 freeze（`FLUSH TABLES WITH READ LOCK` / `pg_backup_start`）才是**应用一致性**；
（2）**控制面**：etcd snapshot（见 `卡/控制面.md` #1）+ **GitOps 仓库才是集群期望态的真相**，
两者结合才能重建集群；只备份 etcd 而不备份 PV，等于备份了一个"引用不存在数据"的清单；
（3）**应用/数据层**：数据库主从 + PITR binlog / WAL 归档，跨可用区。
判断线：**恢复演练频率**——说不出"我们多久演练一次"，这题就是不及格。
（合理答案：etcd 每周演练、业务卷每季度至少一次真实恢复演练）

**弹药**
- `kubectl get volumesnapshotclass` / `volumesnapshotcontent`
- `etcdctl snapshot save/restore` + **snapshot 的 revision 就是 RPO 的时间戳**（能讲到这点很加分）
- Velero：备份 K8s 对象 + 卷数据，支持 label 选择器和 hook（`pre` 里做 DB dump）
- 校验：恢复后 `kubectl auth can-i --list`（RBAC 完整性）、`kubectl get pvc -A | grep -v Bound`（卷绑定）

**红线**｜❌ "我们每天快照"但从未验证过能恢复。备份的可信度只等于最近一次成功演练。

**下一问**｜"给你 4 小时前的快照和 4 小时的 binlog，你怎么把数据库恢复到故障前 1 分钟？"

## 10. 本地盘 vs 云盘 vs 文件/对象存储

**一句话**｜按"能不能容忍 Pod 和存储绑死"来选：性能优先选本地盘，可漂移选云盘，共享选 NAS，非结构化选对象。

**30 秒答**｜**本地 NVMe**：延迟最低、成本最低，但**数据和节点同生命周期**——节点挂就丢，
所以要应用层多副本（如 Kafka/ES/ClickHouse 这类自带复制的系统）；
**云盘**：可 attach 漂移、有快照，但受 zone 约束和挂载数限制，扩展性差；
**NAS/文件（RWX）**：多节点共享、扩容方便，代价是延迟高、锁语义弱、易被单点打满；
**对象存储**：无限容量、天然跨 AZ，但**不是文件系统**（无 rename 原子性、无追加语义），
只适合放快照/日志/模型权重/大文件。
选型话术：先问"**这个数据的 owner 是应用还是平台**"——应用能管复制就用本地盘换性能，不能就用云盘让平台兜。

**弹药**
- 量级感（说出来就是经验）：本地 NVMe 亚毫秒、云盘 1–3ms、NAS 数毫秒起且抖动大
- 云盘 IOPS 常按容量线性给（**1TiB 才可能拿到高性能档**），要高性能得单独买性能型
- 大文件只读场景优先 **对象存储 + 本地缓存**（如 JuiceFS / Alluxio 类），说得出这个组合是加分
- K8s 里的落点：`storageClassName` + `accessModes` + `volumeMode: Block`（少数应用要裸块）

**红线**｜❌ 无脑上 RWX "方便"。文件系统层的共享会掩盖应用层本该解决的复制/一致性问题。

**下一问**｜"数据库你放本地盘还是云盘？为什么？"（→ 有状态数据库通常选**云盘 + 应用层高可用**；极致性能选本地盘 + 副本，必须接受丢盘风险）

## 11. 有状态工作负载（StatefulSet）的存储编排

**一句话**｜StatefulSet 给你的是"**稳定标识**"：名字有序、PVC 一对一、网络域名可预测——不是给你"数据一致性"。

**30 秒答**｜`volumeClaimTemplates` 会为每个序号生成**独立 PVC**（`data-<sts>-0`），
Pod 删除重建后仍绑回同一个卷，这是它和 Deployment 挂载同 PVC 的本质差别。
有序性：创建按 0→N，删除/缩容按 N→0（配合 `podManagementPolicy: Parallel` 可放弃顺序换速度）；
无头 Service（`serviceName`）提供 `pod-0.svc.ns.svc.cluster.local` 的稳定 DNS。
**必须清楚它的边界**：K8s 不理解"主从"语义，
把主选出来的是应用（或 Operator）；StatefulSet 只保证标识稳定。
**判断线**：这题的加分点是**主动说"什么时候不该用 StatefulSet"**——能用 Operator/云服务就别自己编排；数据一致性靠应用复制协议，不靠 K8s。

**弹药**
- `kubectl get sts <n> -o jsonpath='{.spec.volumeClaimTemplates[*].metadata.name}'`
- `persistentVolumeClaimRetentionPolicy: {whenDeleted: Delete, whenScaled: Delete}`（1.27+ 可选，**默认是保留**，别忘了）
- `podManagementPolicy: OrderedReady | Parallel`、`updateStrategy: RollingUpdate + partition`（金丝雀式分批发版）
- 删 Pod 换节点会触发 detach+attach，**这个窗口就是 RTO**（回到卡 #4 的判断线）

**红线**｜❌ 把 StatefulSet 当"K8s 能跑数据库"的证据。能跑 ≠ 该跑，Operator 和托管服务通常更对。
