# 卡 · 可观测性与 SLO

> 监控 / 告警 / SLO / 值班体系的速答口径。**这类题考"你信什么数据"，不是背工具名**。
> 每题都是 `一句话 → 30 秒答 → 弹药 → 红线 → 下一问` 五段，直接照念。

## 1. Prometheus 重启后丢了 6 小时数据

**一句话**｜Prometheus 的本地 TSDB 是**可重建的临时缓存**，不是存储系统——把它当长期存储用才是根因。

**30 秒答**｜机制：数据先写 **WAL**（`wal` 目录，按 2h 一段切 block，中间产生 `checkpoint`），
重启时 replay WAL 恢复最近未 compaction 的数据。
丢 6 小时说明：**要么 WAL 目录和 storage 目录不同盘/被清（挂载丢了、用了 emptyDir 而不是 PVC）**，
要么 block 损坏、要么 WAL 超出 replay 上限、要么进程被 OOM 杀时正在写没落盘。
先确认事实：`kubectl get pod -o jsonpath='{.spec.volumes}'` 看 `--storage.tsdb.path` 挂的是不是持久卷——
**"重启后数据没了"的第一嫌疑就是没挂 PVC**。
缓解：从**多副本**的另一个 Prometheus 查（这就是为什么要双写多副本）、
用 recording rule 重算可推导指标、从 remote write 下游（Mimir/Thanos/VictoriaMetrics）回捞。
长期：**remote write → 长期存储 + 多副本 + 对象存储归档**，本地只留 2–15 天热数据。

**弹药**
- `promtool tsdb analyze /data/prometheus` — 直接看 block 和 WAL 结构
- `--storage.tsdb.retention.time`（默认 **15d**）；WAL 段 `--storage.tsdb.wal-segment-size-bytes`
- 指标：`prometheus_wal_written_bytes_total`、`prometheus_tsdb_reloads_failures_total`、`prometheus_remote_storage_samples_failed_total`
- remote write 兜底：`queue_config` 的容量 + **`wal_only`/磁盘 WAL 重放**，下游挂了不会立刻丢，但有上限
- 高可用标准做法：**规则相同的双副本（prometheus-operator 的 replicas=2）**，不是靠"存得久"

**红线**｜❌ 说"我们 Prometheus 存一年所以没问题"。存得久 ≠ 不丢——单副本 + 本地盘 = 必然丢。
❌ remote write 不做失败监控，等要用的时候才发现链路早断了。

**下一问**｜"remote write 持续失败，你怎么在丢数据之前知道？"

## 2. SLI / SLO / SLA 和错误预算

**一句话**｜SLI 是**测出来的数**，SLO 是**内部目标**，SLA 是**对外承诺（带赔偿）**；错误预算 = 1 − SLO，是把可靠性变成发布刹车的那个数。

**30 秒答**｜先给定义再给例子：
`SLI = 成功请求数 / 总请求数`（或"P99 延迟 < 500ms 的请求占比"）；
`SLO = 过去 30 天 SLI ≥ 99.9%`；
`SLA = 达不到就赔钱/服务积分`——**内部不要随便用 SLA 这个词**。
错误预算换算要能张口就来：30 天 = 43200 分钟，
**99.9% → 43.2 分钟**、99.95% → 21.6 分钟、**99.99% → 4.32 分钟**（每 30 天）。
用法是**机制而非态度**：预算没花完 → 正常发版、做实验；
预算花完 → 冻结变更、只做稳定性工作（这条要让管理层认账，否则 SLO 只是墙上的数字）。
定 SLO 的判断线：**不是越高越好**——核心服务 99.95%–99.99%、周边 99.5%–99.9% 合理；
SLO 要定在**用户体验拐点**上（用户能感知 500ms 变 800ms，感知不到 300ms 变 350ms）。

**弹药**
- 口径必须明确：**分子分母、统计窗口、请求范围（入口还是内部调用）**——面试官深挖的一定是这里
- SLO 别只做可用性：**延迟 SLO（P99）+ 饱和度/队列时延**才能提前发现容量问题
- 依赖链：下游 99.9% × 下游 99.9% → 上游理论上限 99.8%，**多依赖天然拉低你的 SLO**，
  所以要么降级要么冗余（能算这个乘法就是 Senior）
- Google SRE 速查：99.9% ≈ 每月 43min，99.99% ≈ 每月 4.3min，99.999% ≈ 每年 5min

**红线**｜❌ "我们 SLO 是 99.99%"但说不出 SLI 怎么算、告警阈值和 SLO 有没有关系。
❌ SLO 违约就 paging——SLO 违约说明**预算已耗尽**，正确动作是变更冻结。

**下一问**｜"你的 SLI 是从入口网关统计还是从应用统计？两者的差异说明什么？"

## 3. 告警太多怎么降噪？

**一句话**｜按 **burn rate 多窗口**分级 + 抑制/静默/路由三件套，把告警数量压到"每条都必须在 5 分钟内有人动"。

**30 秒答**｜核心是把"阈值告警"换成"**错误预算燃烧速率告警**"：
SLO 99.9%（30 天窗口）下，如果 1 小时内烧掉 2% 预算（burn rate = 14.4），
说明按这个速率 2 天就耗尽窗口 → **page**；
烧得慢（1 小时 0.9%）→ ticket。
多窗口（fast: 1h/5m、medium: 6h/30m、slow: 3d/6h）避免"短窗口误报 + 长窗口迟钝"两头的坑。
工程侧三件套：**聚合**（同服务同类 `group_by` 合成一条）、
**抑制**（根因告警触发时抑制下游派生告警，"apiserver 挂了"要压掉几百条 "pod unreachable"）、
**静默**（变更窗口/发布期提前 silence，**事后审计 silence 是否被滥用**）。
硬性纪律：**没有 runbook 的告警一律删掉**——不可执行的告警等于噪声，还会训练大家忽略真信号。

**弹药**
- 分级：Critical（**< 5 分钟响应**、page）/ Warning（当班处理，< 4 小时）/ Info（次日、容量预警类）
- Alertmanager：`group_by` / `inhibit_rules`（`source_match` 抑制 `target_match`）/ `route` 按团队分流 / `time_intervals` 做静默窗口
- 多窗口 burn rate 的"1h 烧 2% 预算"是 **2% rule（Google SRE Workbook）**，说得出这个数是加分
- 反向指标：每周统计 **告警准确率 / 无效告警比 / 单人 page 次数**，page 次数超阈值就是排班不可持续，必须治

**红线**｜❌ 加告警前先"把阈值调低一点更保险"。阈值过敏感 → 疲劳 → 真故障被淹没，这是最常见的自毁。
❌ 靠"人肉判断"过滤告警——要沉淀成抑制规则和 runbook。

**下一问**｜"一条 page 进来，你的前 60 秒做什么？"（→ 见卡 #12 值班动作）

## 4. 指标爆炸 / 高基数

**一句话**｜时间序列数量 = 各 label 取值的**笛卡尔积**，一个 `user_id`/`pod_ip`/`request_id` 标签就能打爆整个 Prometheus。

**30 秒答**｜先量化：单指标 100 万活跃序列就已经是"要开始紧张"的量级，
常见爆点是把 **label 用成了维度表**（`container='app-7d9f8b-x2kq'` 每次重启都是新序列、
`path='/user/12345'` 未归一化、加 `trace_id`）。
定位：`count({__name__=~".+"})` 看总序列数、`topk(10, count by (__name__)({__name__=~".+"}))` 找大户，
`promtool tsdb analyze` 看哪个 label 值数量异常。
治理：路径归一化（`/user/:id`）、去掉随机后缀 label、
在采集侧用 metric relabel **丢弃或白名单**、
高频业务指标（订单量按用户）走日志/OLAP（ClickHouse/SLS）而不是 Prometheus。
**判断线**：这是"选型问题"——Prometheus 适合**低基数聚合**，高基数明细是 OLAP 的活。

**弹药**
- 指标：`prometheus_tsdb_head_series`（当前活跃序列数）、`prometheus_tsdb_retention_limit_bytes`
- 存储量级感：<100 万序列单机 Prometheus 够用；**100 万–1000 万上 Thanos/Mimir；>1000 万考虑 VictoriaMetrics Cluster**
- 抓取自开销：`scrape_samples_scraped`（能算出"每分钟采集多少点"就是老手）
- 采样精度取舍：5s 抓取 vs 30s 抓取——**毛刺类故障（内存尖峰、瞬时 5xx）30s 采样会整段漏掉**

**红线**｜❌ 出问题才清理，事前没有 label 规范。要在指标接入评审里就禁高基数 label。

**下一问**｜"怎么在不存明细的前提下，事后仍能定位到是哪个租户出的问题？"（→ 日志下钻 + trace 关联，指标只做聚合）

## 5. 三支柱怎么配合（metrics / logs / traces）

**一句话**｜**metrics 定位到"哪个服务、什么时候"，traces 定位到"哪一跳"，logs 定位到"为什么"**——三者靠 trace_id / label 串起来。

**30 秒答**｜排查动线要能画出来：
告警（metrics）→ 看该服务 RED 指标（rate/errors/duration）确认是流量、错误还是延迟 →
下钻到 trace 找到慢/错的那一跳和下游依赖 → 用该请求的 trace_id + 时间戳去查日志上下文。
所以**串联比工具更重要**：exemplar（metrics 里带 trace_id）、日志注入 trace_id、统一标签（cluster/namespace/service/pod）。
选型上（口径要稳）：
metrics — Prometheus + 长期存储（Mimir/Thanos/VM）；
logs — 中小规模 ELK 功能全但重，云原生场景 **Loki 成本低**（只索引 label，不索引全文，代价是不能全文快查），
大规模自建成本高、通常上 SLS/ClickHouse；
traces — Jaeger 通用、Tempo 与 Grafana 统一存储，**OpenTelemetry 是标准（采集层优先 OTel）**。
**判断线**：能说"我们生产 trace 只采 0.1%，慢请求靠尾部采样"→ 说明真在大规模环境跑过。

**弹药**
- **RED**（面向服务：Rate/Errors/Duration）用于业务链路；**USE**（面向资源：Utilization/Saturation/Errors）用于节点和中间件——
  能区分这两套方法论是加分项
- 头部采样（入口决定）漏掉低概率慢请求；**尾部采样（按结果决定：错误/超阈值必采）**才留得住有价值的样本
- 生产采样常态：**0.1% 全量 + 异常/慢请求 100%**；金丝雀期临时放大
- OTel Collector 作为统一接入 + 路由 + 采样 + 脱敏的位置（**顺便做 PII 脱敏**）

**红线**｜❌ "装了 Prometheus 就有可观测性"——只有 metrics 的系统，故障时必须靠人猜。
❌ 为了"全"把 trace 100% 常开，成本失控后被迫下掉，反而丢失历史。

**下一问**｜"给你 3 分钟，从一条 P99 告警定位到具体代码路径，你怎么走？"

## 6. 指标"没有值"和"值是 0"怎么区分？

**一句话**｜这是排障里最容易被忽略的区分：**采集断了自己不知道，就会把"没数据"当成"没问题"**。

**30 秒答**｜`up == 0`（抓取失败）、序列**根本不存在**（应用没启动/label 变了）、
`absent()` 判空、以及**staleness**（序列存在但最后一次采样太旧，查询返回空而不是上一个值）
——这四种现象在 Grafana 上都显示为"平的"，但含义完全不同。
典型事故：Exporter 挂了 → 错误率指标消失 → 面板空白 → 值班以为"一切正常"。
所以要在告警规则里显式覆盖**"数据缺失"本身**：
`absent(up{job="x"})` 或 `count(up{job="x"} == 1) < N`。
**判断线**：任何基于比率的告警，分母为 0 时的行为必须显式定义（否则除零 → 无告警 → 漏报）。

**弹药**
- `up`（每次抓取的存活指标）+ `scrape_duration_seconds`（抓取变慢常是目标侧卡住的第一信号）
- PromQL 的 staleness 规则：某序列在 5 分钟窗口内无新样本 → 查询视为不存在
- Grafana 设置 **No value / Null display**，别让它默认"连成平线"
- 采集链路自检：Alertmanager 自身、推送链路、下游存储都要被监控（**谁来监控监控系统**）

**红线**｜❌ 面板空白当"没问题"。值班手册里必须写"看不到数据 = 有数据问题"。

**下一问**｜"你的告警链路本身挂了，谁会知道？"

## 7. 监控体系从 0 到 1 怎么建？

**一句话**｜顺序是**先定 SLO 再定告警，先保核心链路再铺全面**——反过来一定变成"指标很多、故障照旧"。

**30 秒答**｜四步，每步都有可交付物：
（1）**画服务地图**：入口有哪些、每条链路的核心依赖、谁是关键用户旅程（没有这张图，后面全是散点）；
（2）**分层指标**：业务层（下单成功率、支付转化）→ 应用层（RED）→ 运行时（JVM/Go runtime）→ 资源层（USE）→ 控制面/平台层（集群组件）；
（3）**SLO + 告警收口**：只对**用户可感知**的 SLI 定 SLO，page 只挂"影响用户"和"即将影响用户"两类，
其余降级为 ticket/看板；
（4）**Runbook + 演练**：每条 page 对应一个能执行的处置文档，季度演练（含监控失效演练）。
判断线：**"覆盖率"不是成果，"MTTD 下降"才是**。这题一定要落到数字上。

**弹药**
- 分层速答（说出来结构感很强）：`业务指标 → 服务指标 → 资源指标 → 平台/控制面指标 → 变更事件流`
- **变更事件必须进可观测体系**（发布/配置/扩缩事件打点）——大部分故障定位就是"这个时间谁改了什么"
- 常见误区清单：只监控平均值（掩盖长尾）、只看 CPU 不看饱和度（队列才是排队问题的信号）、
  日志全 INFO 常开（成本）
- 数据留存的取舍：热 2–15 天全精度、冷数据降采样到 1min/5min 精度保留年尺度趋势

**红线**｜❌ 先买工具再想问题。❌ 上来就"全量采集最安全"——成本会在三个月后逼你砍掉，反而失去连续性。

**下一问**｜"老板问'我们的监控够不够'，你用什么指标回答？"（→ MTTD、告警准确率、故障由监控先发现的比例）

## 8. SLO 与容量 / 成本的平衡

**一句话**｜可靠性是**预算换来的**：每一档 9 都有边际成本，超过业务需要的可用性就是浪费。

**30 秒答**｜先把"多一个 9 花多少钱"说清楚：
99.9% 单可用区多副本就够；99.99% 要**跨可用区 + 自动故障转移 + 变更管控**（驱逐窗口、发布窗口都要设计）；
99.999% 要**同城双活甚至读写分离**，成本不是线性翻倍。
所以做法是**分级**：核心链路高 SLO，周边服务 99.5% 就够，
用**依赖图**识别哪些是真关键路径（避免"全集群都 99.99%"这种自杀式目标）。
成本侧常见抓手（有数字支撑）：指标降采样与 TTL 分级、日志按级别采样 + 冷存归档、
trace 尾部采样、**闲时资源回收（超卖/混部/spot 实例 + 优先级抢占）**。
**判断线**：面试里被问"成本降 30% 怎么来的"，要能拆到**具体来源占比**（超卖 / 装箱率 / spot / 存储分层），
而不是"我们做了 FinOps"。

**弹药**
- 错误预算是**沟通工具**：预算耗尽还要求发版，就让业务方签字消耗预算——把技术决策显性化
- 容量类故障的典型误判："CPU 只有 40% 所以没问题"→ 要看**饱和度**（队列长度、连接 backlog、线程池等待）
- 可用性算法：**冗余份数 × 单点失败率**；多副本 + 反亲和只解决"节点级"，不解决"可用区级"，跨 AZ 才算
- K8s 里的成本指标：`requests` vs 实际用量的**差值**就是浪费（能报出装箱率数字最有力）

**红线**｜❌ 为省钱把 PDB/反亲和/探针删掉。**降本不能降可靠性**——被追问"可用性有没有受影响"时必须有答案。

**下一问**｜"你怎么证明降了 30% 成本而可用性没退？"（→ 同窗口对比可用性/错误预算消耗 + 无新增容量类故障）

## 9. 变更可观测：发布期间到底看什么？

**一句话**｜看**新旧版本的差分指标**，不是看绝对值——大盘不报错不代表发布没问题。

**30 秒答**｜发布观察最小集（按时间尺度）：
错误率差分（新版本 vs 老版本，同窗口对比）、
延迟差分（P50/P99 分开，P99 更能暴露问题）、
饱和度（Pod 重启次数、OOM、CPU throttle、GC 时间）、
下游影响（依赖方的错误率、DB 慢查询、限流计数）、
业务指标（转化/下单成功率——**它是最终裁判**）。
关键实现是**版本 label**：`version="abc123"` 打到指标上，PromQL 用
`sum by (version)(rate(http_requests_total{code=~"5.."}[5m]))` 直接对比；
Argo Rollouts/Flagger 就是把这些分析写成 `AnalysisTemplate` 自动晋级/回滚。
**判断线**：留观多久由**流量周期**决定——日级批处理任务要看到下一个批次窗口结束。

**弹药**
- 事件标注（annotation）在 Grafana 上画发布竖线：**复盘时间线的第一工具**
- `kube_pod_container_status_restarts_total`、`container_cpu_cfs_throttled_periods_total`（**throttle 是"limit 太低"的直接证据**）
- 发布期临时放宽告警阈值要**登记并在结束后撤销**（忘记撤销 = 后续故障漏报）
- 回滚判据提前定死（如"错误率相对基线 +0.5% 且持续 3 分钟"），避免现场辩论

**红线**｜❌ "发布完成，指标都正常"（看的是全局大盘）。❌ 无版本 label，事后无法归因到某个版本。

**下一问**｜"只有 P99 涨了、错误率没涨，你回滚吗？"

## 10. On-call 与事故响应：MTTR 怎么压下来？

**一句话**｜MTTR 不是一件事，是**四段之和**：发现（MTTD）→ 定位 → 决策 → 恢复。压哪一段，取决于哪一段最长。

**30 秒答**｜先把时间拆开量：
`发现`——靠 SLO 告警而不是用户报障（这条最能体现体系成熟度；"多少故障由监控先发现"要能报百分比）；
`定位`——靠可观测下钻动线（卡 #5）+ **变更事件关联**（多数故障源于变更）；
`决策`——靠预案和授权（oncall 有没有权力直接切流/回滚，不用等审批 20 分钟）；
`恢复`——靠自动化（回滚、切流、扩容做成一键或自动）。
**压 MTTR 最有效的三件事，按性价比排序**：
（1）**回滚路径演练**（没演练过的预案实际执行会慢 3–5 倍）；
（2）**告警即入口**（每条 page 带 dashboard 链接 + runbook 链接，省掉找链接的 5 分钟）；
（3）**自动化止血**（把"无人值守恢复"从 0 做到 80% 这类数字，比加人有效）。
**判断线**：讲 MTTR 必须带**基线和口径**——"45 分钟到 12 分钟"要说清分母是"哪一类故障、统计多久"。

**弹药**
- 角色分工：**IC（处置）/ Scribe（记录时间线）/ Comms（对外同步）**，超过 2 条线并行就必须分工
- 沟通节奏：**每 15 分钟同步一次进展**（哪怕"没有进展"），这是防止管理层反复打断处置的机制
- 严重度分级（P0–P3）要预先定义**影响面判据**（受影响用户比例/时长/资金损失），不能现场拍
- 复盘量化：MTTD / MTTM（判断为事故的时间）/ MTTR 分开统计，才能知道该投哪儿

**红线**｜❌ 一个人既处置又对外沟通（必然两头失守）。
❌ 报 MTTR 下降但拿不出故障时间线原始记录。
