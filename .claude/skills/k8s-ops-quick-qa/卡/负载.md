# 卡 · 工作负载排障

> Pod / Deployment / 容器层的速答口径。**面试出现频率最高的一类**，占比约 60%。
> 每题都是 `一句话 → 30 秒答 → 弹药 → 红线 → 下一问` 五段，直接照念。

---

## 1. Pod 一直 Pending 起不来，怎么查？

**一句话**｜Pending 只有三种可能：调度不上去、镜像拉不动、挂载挂不上。

**30 秒答**｜先 `kubectl describe pod` 看 events，events 直接把三类分开了。
调度类是 `FailedScheduling`，看 Insufficient cpu/memory 还是 node 选择器/污点不匹配；
镜像类是 `ErrImagePull`/`ImagePullBackOff`，查镜像名、tag、仓库凭证；
存储类是 `MountVolume.SetUp failed`，查 PV 是否 Available、zone 是否和调度节点匹配。
**判断线**：Pending 且 events 里一条调度失败都没有 → 去看 PVC 是否 Binding 卡住（`kubectl get pvc`），
PVC 未绑定会让 Pod 永远 Pending，90% 的人会漏掉这条。

**弹药**
- `kubectl describe pod <p> -n <ns>` → 只看 `Events` 段
- `kubectl get events -A --sort-by=.lastTimestamp | tail -20`
- `kubectl get pvc`（`Pending` = 没 PV 可绑）
- 调度失败原因看 annotation：`kubectl get pod <p> -o jsonpath='{.metadata.annotations.kubernetes\.io/failed-schedulable-nodes}'`

**红线**｜❌ 上来就说"删了重建"。Pending 是**调度器给出的明确拒绝**，删了还是 Pending，等于没排查。

**下一问**｜"集群还有 40% 空闲 CPU，为什么还报 Insufficient memory？"（→ 节点级碎片 + requests 不等于实际用量）

## 2. CrashLoopBackOff 怎么定位？

**一句话**｜容器**起来了又退出**，所以问题在应用或探针，不在调度——先看上一次退出的日志。

**30 秒答**｜第一步 `kubectl logs <p> --previous`，`--previous` 是关键，当前容器是空的。
日志里有异常栈 → 应用问题（配置、依赖、启动脚本报错）；
日志什么都没有 → 看 `lastState.terminated.exitCode` 和 `reason`：`137` 是 OOMKilled 或被 SIGKILL，
`1`/`2` 是应用自己抛错；`reason: Completed` 说明进程正常退出，那就是**容器没有前台进程**（Dockerfile CMD 起成了守护进程）。
同时确认探针：liveness 探测失败会被**重启**，表现为无限 CrashLoop，但根因是探针配置过激。

**弹药**
- `kubectl logs <p> --previous --tail=100`
- `kubectl get pod <p> -o jsonpath='{.status.containerStatuses[0].lastState}'`
- exitCode `137` = `128+9`(SIGKILL)，配合 `reason: OOMKilled` 才是内存问题；没有 OOMKilled 就是节点层杀的
- 区分 liveness 重启 vs 应用自杀：`kubectl describe pod` 里 `Liveness probe failed` 事件

**红线**｜❌ 不看 `--previous` 只看当前日志，答"日志里没有信息所以无法判断"。
❌ 把 CrashLoopBackOff 全归因为内存不足。

**下一问**｜"liveness 和 readiness 都能让 Pod 表现为反复重启吗？"（→ readiness 不会重启，只会摘流量；能答出这个差别才算懂）

## 3. OOMKilled，但内存 limit 没打满？

**一句话**｜先分清是 **cgroup OOM**（容器超了自己的 limit）还是 **节点 OOM**（节点没内存了，内核挑一个杀）。

**30 秒答**｜`kubectl describe pod` 看 `lastState.terminated.reason`，是 `OOMKilled` 才是 cgroup 层。
如果 limit 1Gi、RSS 才 600Mi 就被杀 → 三种典型原因：
①**page cache 算进了 cgroup 用量**，RSS 低但 cache 把 limit 顶满了；
②**瞬时尖峰**，监控是 30s 采样，秒级毛刺采不到；
③**节点级压力驱逐**，节点内存不足时 kubelet 按 requests 优先级挑受害者，Pod 会先被 Evicted 而不是 OOMKilled。
**判断线**：节点 OOM 去查 `dmesg -T | grep -i oom` 和 `/proc/meminfo` 的 `MemAvailable`；
Pod 侧只有 `Evicted` 没有 `OOMKilled` → 一定是节点层，别看容器了。

**弹药**
- `dmesg -T | grep -i "killed process"` — 节点 OOM 的铁证
- `kubectl get events -n <ns> --field-selector reason=Evicted`
- cgroup 用量含 cache：`kubectl exec <p> -- cat /sys/fs/cgroup/memory.current` vs `memory.stat` 里的 `file`
- Java 场景：`-Xmx` 必须 < limit，堆外（direct buffer / metaspace）不在 -Xmx 内，最容易超

**红线**｜❌ "把 limit 调大就行了" —— 掩盖问题，下次是节点被搞挂。
❌ 分不清 cgroup OOM 和 node OOM，这是这题 90% 候选人栽的地方。

**下一问**｜"怎么自动识别'节点 OOM 但 cgroup 没到'这种场景？"（→ 关联节点 MemAvailable 与 Pod 事件）

## 4. ImagePullBackOff / ErrImagePull？

**一句话**｜四个原因按概率排：tag 不存在、私有仓库凭证没配、网络不通、架构不匹配。

**30 秒答**｜`kubectl describe pod` 的 events 里那行 `pull image ... : <报错>` 已经把答案写全了，一定要念出来。
`manifest unknown` / `not found` → tag 写错或镜像没推上去；
`unauthorized` / `authentication required` → 缺 `imagePullSecrets`，确认 secret 在**同 namespace**；
`no such host` / `timeout` → 节点到仓库的网络/DNS/代理问题，`crictl pull` 到节点上直测；
`image platform ... does not match host platform` → **架构不匹配**（arm64 镜像调度到 amd64 节点，或反过来）。
最后一类最容易被忽略：多架构镜像要 `docker buildx` 出 manifest list。

**弹药**
- 节点侧绕开 K8s 直接验：`crictl pull <image>`（更快、报错更干净）
- `kubectl get secret -n <ns> | grep docker`；`kubectl describe sa default -n <ns>` 看 `imagePullSecrets`
- 查架构：`docker manifest inspect <image>` / `crictl inspecti <image> | grep -i arch`
- `latest` tag + `imagePullPolicy: IfNotPresent` = 节点上留着旧镜像不更新，经典事故源

**红线**｜❌ 一上来就说"节点拉不到外网"，不看 events 里报的是 401 还是 404。

**下一问**｜"生产环境为什么禁止用 latest tag？"（→ 无法回滚、滚动更新不生效、镜像内容与 tag 解耦）

## 5. 节点突然 NotReady，Pod 全挂？

**一句话**｜NotReady 是 **kubelet 停止上报心跳**，不代表 Pod 真死了——先确认是节点本身还是它到 apiserver 的路。

**30 秒答**｜`kubectl describe node` 看 conditions 的 `Reason`：`KubeletStoppedPingingAPI` / `NodeStatusUnknown` 就是心跳问题。
然后**分单节点还是集群级**——这一个判断决定后面所有动作。
单节点 → 上节点查 `journalctl -u kubelet`，常见是磁盘压力（`hard eviction` 触发 taint）、容器运行时挂了、证书过期、PLEG relist 过长。
大面积同时 NotReady → 一定不是节点自身问题，查共同依赖：underlay 网络、CNI（`calico-node`/`cilium` Pod 状态）、apiserver 被打爆、或一次批量变更。
**关键**：控制面失联时 Pod 常常还在跑（"幻象 Pod"），**别急着删节点上的 Pod**，网络分区恢复后会出现双活。

**弹药**
- `kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints`（磁盘压力会打 `node.kubernetes.io/disk-pressure`）
- `journalctl -u kubelet --since "-10m" | grep -iE "pleg|relist|certificate|ephemeral"`
- PLEG 不健康阈值：relist 超 3min → kubelet 自判 NotReady
- 证书过期：`kubeadm certs check-expiration` / `openssl x509 -in kubelet.crt -noout -dates`

**红线**｜❌ 网络分区未确认就 force delete Pod 或重启节点 —— 分区恢复后脑裂、重复写。
❌ 200 台同时 NotReady 还逐台上机排查（应先确认故障域：同 AZ？同交换机？同批次变更？）

**下一问**｜"1000 节点集群 5 分钟内 200 台同时 NotReady，你 2 分钟内看哪 3 个指标？"

## 6. 滚动更新卡住，新 Pod 不替代旧 Pod？

**一句话**｜看 `maxUnavailable`/`maxSurge` 算出来的预算，和新 Pod 到底有没有 Ready —— 大多数卡住是**新 Pod readiness 永远不过**。

**30 秒答**｜`kubectl rollout status deploy/<d>` 会直接告你当前 unavailable 数和期望。
新 Pod 起不来 → 回到第 1/2/4 题的排障链路。
新 Pod Running 但 rollout 不动 → **readiness 探针没通过**，Service 不接流量，控制器认为不可用；
去 `kubectl describe pod` 找 `Readiness probe failed`。
另一种隐蔽情况：`maxUnavailable: 0` + `maxSurge: 0` = 没有推进空间；或 PDB 太严，节点排水时旧 Pod 不允许被删，形成僵局。
**判断线**：replicas 字段 `READY < desired` 且 `UP-TO-DATE == desired` → 镜像已换但新 Pod 不 Ready，是应用/探针问题不是发布问题。

**弹药**
- `kubectl rollout status deploy/<d> --timeout=60s`
- `kubectl get deploy <d> -o jsonpath='{.spec.strategy}{"\n"}{.spec.minReadySeconds}'`
- `kubectl get pdb -A`（`ALLOWED DISRUPTIONS 0` = 僵局来源）
- 回滚：`kubectl rollout undo deploy/<d> --to-revision=<r>`；查历史 `kubectl rollout history`

**红线**｜❌ 没有回滚预案就发。SA 面试里"你怎么保证 6 个月上线"和这里同源：**先说止损，再说推进**。

**下一问**｜"怎么设计一个'自动判断能否继续放量'的发布流程？"（→ 灰度 + 指标门禁 + 自动回滚）

## 7. Deployment 改了镜像，按顺序讲每一步谁做了什么？

**一句话**｜kubectl → apiserver → etcd → Deployment 控制器 → ReplicaSet 控制器 → 调度器 → kubelet → CRI/CNI，七跳。

**30 秒答**｜① kubectl 把变更 POST 给 **apiserver**；② apiserver 校验后写 **etcd**；
③ **Deployment 控制器** watch 到 spec 变化，派生出一个新的 **ReplicaSet**（新 podTemplateHash）；
④ **ReplicaSet 控制器** 按新旧 RS 差额创建新 Pod，此时新 Pod **只写了 spec、没有 nodeName**，状态 Pending；
⑤ **scheduler** watch 到 `spec.nodeName` 为空的 Pod，Predicate 过滤 + Priority 打分，写回 nodeName（一次绑定请求）；
⑥ 目标节点的 **kubelet** watch 到"分给我的新 Pod"，走 PLEG 感知 → CRI 拉镜像起容器 → CNI 配网络 → CSI 挂卷；
⑦ kubelet 把 status 回写 apiserver→etcd，readiness 通过后 **Endpoint 控制器** 把 Pod IP 加进 Service Endpoints，流量才进来。
**核心讲三点就是 Senior**：控制器之间**不通信**，全部通过 apiserver + watch 异步协作；reconcile 是 **level-triggered**（比对 spec 与 status，不靠事件驱动）；写 etcd 用 **resourceVersion 乐观锁**防并发冲突。

**弹药**
- `kubectl get rs -o wide`（IMAGE 列直接看出新旧 RS）
- 调度发生在 apiserver 的 `binding` 子资源写，不是 scheduler 直接联系 kubelet
- kubelet 与 apiserver 是 **HTTP long watch**，不是长连接，会被网络抖动断，靠 re-list + watch 补偿
- 常见误区："scheduler 会重启 Pod" —— 它只决定落点，起容器是 kubelet 的事

**红线**｜❌ 说成"kubectl 通知 scheduler 去调度"。整条链路是**各自 watch 各自关心的资源**，没有谁通知谁。
❌ 说不清 level-triggered 和 edge-triggered 的区别。

**下一问**｜"watch 断线后会漏事件吗？怎么补偿？"

## 8. 三个探针配错出过什么事故？

**一句话**｜startup 管"给多久冷启动"，readiness 管"能不能进流量"，liveness 管"要不要杀掉重启"——**语义完全不同，不能混用**。

**30 秒答**｜最常见的生产事故是 **liveness 探得过激**：依赖冷启动或下游抖动时，liveness 连续失败触发重启，
重启后其他 Pod 同时在重连，把下游彻底压垮 —— **liveness 探活把局部抖动放大成集群级雪崩**。
liveness 应该只探**进程自身不可恢复的死状态**（死锁、事件循环卡死），**绝不要在 liveness 里探下游依赖**（DB/Redis 连不上就重启自己 = 无意义循环）。
readiness 才该探依赖，因为它只是摘流量不杀进程。
冷启动慢的服务（JVM、模型加载）必须配 **startupProbe** 兜住，否则它一慢就被 liveness 打死，永远起不来。

**弹药**
- 典型组合：`startupProbe failureThreshold: 30, periodSeconds: 5`（给 150s 冷启动）+ `liveness periodSeconds: 10, failureThreshold: 3` + `readiness periodSeconds: 5, failureThreshold: 2`
- 摘流量 ≠ 重启：readiness 失败 → 从 Endpoints 移除；liveness 失败 → 容器重启
- 探针打到 `localhost` 才准（kubelet 在节点上发请求，走 Service 会绕一圈）
- 优雅下线要配 `preStop sleep` + readiness 先转失败，否则上下线瞬间有 5xx

**红线**｜❌ "liveness 用来保证服务健康" —— 它保证的是"进程活着"，服务健康是 readiness 的事。
❌ 在 liveness 里连数据库。

**下一问**｜"为什么滚动发布时还是会出现少量请求失败？"（→ 摘 Endpoints 与 kube-proxy 规则同步有延迟 + 连接 drain）

## 9. HPA 为什么不生效 / 疯狂抖动？

**一句话**｜八成是**没配 requests 导致算不出利用率**，或者**扩缩窗口和指标抖动打架**。

**30 秒答**｜HPA 用 `当前用量 / requests` 算利用率，**没设 requests 就没有分母，CPU HPA 直接不算**——这是第一检查项。
然后看 `kubectl describe hpa`，`MetricsAvailable` / `ScalingActive` 条件里写着原因。
抖动两个来源：
①指标源本身抖（用 15s 采样的 raw 指标做扩缩，配 `behaviors.scaleDown.stabilizationWindowSeconds: 300` 拉平）；
②**扩缩回环**：扩容后单 Pod 负载降下来又触发缩容，缩回去又涨 —— 要么放宽 target（用 60-70% 而不是 40%），要么只扩不缩。
自定义指标（QPS、队列长度）要确认 adapter 注册成功，且指标是 **rate 类型**不是 gauge。

**弹药**
- `kubectl describe hpa <h>` → `Metrics: (current/target)`，current 缺失就是指标源问题
- `kubectl get --raw "/apis/metrics.k8s.io/v1beta1/namespaces/<ns>/pods"` 验 metrics-server
- `behaviors` 字段（autoscaling/v2）分别控 `scaleUp`/`scaleDown` 的 `policies` 与 `stabilizationWindowSeconds`
- 与 VPA 别同时管 CPU（互相打架），要上就分工：VPA 定 requests、HPA 定副本

**红线**｜❌ 只答"把阈值调一下"，说不出没配 requests 这个前置条件。

**下一问**｜"突发流量比 HPA 反应快（HPA 要 15s+ 采样），怎么办？"（→ CronHPA 预扩 + startupProbe 冷启动时间共同决定）

## 10. Pod 被驱逐（Evicted）是怎么回事？

**一句话**｜节点资源不够，kubelet 主动杀掉 Pod 保护节点——**驱逐是节点行为，不是调度失败**。

**30 秒答**｜`kubectl describe pod` 里 `Reason: Evicted`，`Message` 会写触发的信号：
`memory.available` / `nodefs.available`（磁盘）/ `imagefs.available`（镜像层占用）三类最常见。
镜像把 `imagefs` 撑满是隐形杀手（日志、镜像层、容器可写层堆积）。
关键区分：**requests 和 limits 差距大**（超卖严重）的节点最容易触发驱逐，
且 **Guaranteed（requests==limits）在驱逐排序里最后被牺牲**，BestEffort（没设 requests）最先被杀。
处置：先清节点磁盘/镜像 → 再看是不是 requests 设得太乐观 → 长期做节点资源画像 + 按 QoS 分层调度。

**弹药**
- 驱逐是 **软阈值**（`--eviction-hard`）先触发 taint + 杀 Pod，硬阈值直接杀且不给优雅退出时间
- `kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.conditions[?(@.type=="MemoryPressure")]}{"\n"}{end}'`
- 节点磁盘：`df -h /var/lib/kubelet`；容器可写层爆 → 应用往 /tmp 疯狂写日志
- 排除误判：Evicted 的 Pod **不会自愈**（RS 会补新的，但 Job/裸 Pod 留尸），需要 `kubectl delete pod` 清理记录

**红线**｜❌ "重启节点就好了"——驱逐是容量不足，重启后照样驱逐，还搭上一个节点的 Pod。

**下一问**｜" ephemeral-storage 的 limit 和 requests 分别控制什么？日志算谁的？"

## 11. 一个 Pod 里 sidecar 和业务容器，谁先起？

**一句话**｜1.28 之前的原生 sidecar **没有顺序保证**；1.28+ 用 `initContainers` + `restartPolicy: Always` 才是真正的 sidecar。

**30 秒答**｜传统 initContainer 顺序执行完才起主容器，但**它跑完就退出**，不能当常驻 sidecar。
新形态 sidecar（native sidecar）：在 `initContainers` 里声明并设 `restartPolicy: Always`，
kubelet 保证它**先于依赖它的主容器启动**、**后于主容器退出**，用 `startupPolicy: Order` / `waitFor` 控制顺序。
这在实际运维里最痛的是 **istio-proxy 必须先于业务容器 ready**（否则业务第一批出网请求被 iptables 拦死），
以及 mesh sidecar 优雅退出要晚于业务，否则最后一段流量黑洞。

**弹药**
- sidecar 判定字段：`initContainers[].restartPolicy: Always`
- 顺序控制：`startupPolicy: Order` + `waitFor: {name: <container>}`（1.32+ 稳定）
- istio 的经典兜底：业务容器加 `postStart sleep` 或靠 readiness 探测 mesh 端口
- 容器共享：`shareProcessNamespace: true` 才能在一个容器里 kill 另一个

**红线**｜❌ 说"initContainer 就是 sidecar"。旧世界它是"跑完退出"，新世界 sidecar 语义是"常驻且先起后停"。

**下一问**｜"主容器 OOM 被杀，sidecar 会被重启吗？"

## 12. 同一份 YAML，测试环境跑得好好的，生产 Pending？

**一句话**｜环境差异九成在**调度约束**，不在应用：资源余量、污点、拓扑分布、PDB、配额。

**30 秒答**｜生产特有而测试没有的东西：taint（GPU/系统节点池不接受普通 Pod）、
`PodTopologySpread` 强制跨 zone（生产有 3 个 zone 的硬约束，测试单 zone 永远不触发）、
NamespaceResourceQuota / LimitRange（生产按团队配额），
以及**节点池标签体系不同**导致 nodeSelector 匹配不到任何节点。
所以答这题的正确顺序不是"看报错"，而是**"对比两个环境的调度约束差异"** —— 体现的是配置漂移意识。
最后补一句长期方案：GitOps + 环境一致性校验，能提前在 CI 拦住这类问题。

**弹药**
