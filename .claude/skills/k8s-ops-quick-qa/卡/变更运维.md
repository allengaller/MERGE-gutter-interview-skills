# 卡 · 变更与发布

> 升级 / 灰度 / 回滚 / GitOps / 引入新组件的速答口径。**这类题看的是判断力，不是命令**。
> 每题都是 `一句话 → 30 秒答 → 弹药 → 红线 → 下一问` 五段，直接照念。

---

## 1. 一次上线前你的 checklist 是什么？

**一句话**｜四问：**怎么灰度、怎么观测、怎么回滚、谁是责任人**——缺任何一个就不该发。

**30 秒答**｜按时间轴说：
变更前——变更单里写清影响面和**回滚步骤（要能 5 分钟内执行完）**；
配置/DB/集群三类变更确认顺序（**先做向后兼容的**）；
容量预检（新版本资源画像是否变化，HPA 上下限够不够）；
观察窗口和 SLO 指标提前定义好（不是发完再想看看什么）。
变更中——分批（1% → 10% → 50% → 100%），每批有**明确晋级指标**（错误率、P99、饱和度）和**停留时间**；
变更中不并行做别的变更。
变更后——留观到下一个流量高峰；关闭变更前不清空告警抑制。
**判断线**：真正区分资深与否的是"你有没有说出**变更窗口选择**和**不做什么**"（周五晚上不发、大促冻结期不发）。

**弹药**
- `kubectl rollout history` / `kubectl rollout undo`（回滚要**演练过**才算有回滚方案）
- `kubectl diff -f` 对 GitOps 仓库做发布前 diff（能看出**漂移**：集群里有手工改的东西）
- PDB 检查：`kubectl get pdb -A` — 发布期是否会把副本全 drain 掉
- readiness 参与流量摘除：新 Pod Ready ≠ 已接到流量，要等 **endpoints 传播 + 客户端连接池刷新**

**红线**｜❌ "有问题再说"。❌ 变更单写"回滚：重新发布旧版本"但没测过旧版本还能不能起来（依赖的新配置它读不了）。

**下一问**｜"这次变更你预判最可能出问题的点是什么？"（面试必备：任何变更都要能指一个具体风险）

## 2. 灰度发布怎么做？

**一句话**｜灰度不是"发一台看看"，是**可控地把一小部分真实流量导到新版本，并且有量化晋级线**。

**30 秒答**｜四种切法，按可控性递增：
（1）**副本比例**（滚动更新 maxSurge/maxUnavailable）——最简单，但流量按连接随机分配，
长连接场景下"10% 副本"实际承接的可能远多于 10%；
（2）**Service/label 双版本并存 + Ingress/Gateway 按 header、cookie、权重分流**——真正的流量比例控制；
（3）**按用户/租户维度**（白名单客户先上）——业务可控，适合 To B；
（4）**影子流量（镜像回放）**——新集群接复制流量但不回响应，最安全、成本最高。
晋级指标必须是**差分**（新旧版本对比），不是绝对值：新版本 P99 比老版本高 5ms 才停，而不是"P99 超过 200ms 才停"。
**判断线**：先问"这个服务是不是幂等、有没有状态"，有状态服务的灰度难点在数据兼容不在流量切分。

**弹药**
- Istio/Envoy Gateway `VirtualService.weight` + `match.headers`（金丝雀）
- Argo Rollouts `Canary` + `analysis.templates`（**自动晋级/自动回滚**，指标不达标直接 abort）
- 长连接灰度：要主动**驱逐客户端重连**（分批断连 / 靠 LB 的 drain），否则灰度比例失真
- 数据库变更配套：**expand-contract**（先加新列双写 → 切读 → 再删旧列），保证任意时刻可回滚

**红线**｜❌ 用"发布到 1 个 Pod"冒充灰度——没有流量比例控制、没有自动晋级判定。

**下一问**｜"灰度 10% 时报错率涨了 0.3%，你停还是继续？"（→ 看基线方差 + 是否新版独有 + 绝对量，先停再查是标准答案）

## 3. 线上出故障，你回滚还是继续排查？

**一句话**｜**先止血再定位**——回滚是第一止血手段，除非回滚本身有风险。

**30 秒答**｜判断顺序：
（1）故障是否发生在变更后（或变更后 30 分钟内）？是 → **默认回滚**，不要辩护"这个变更不可能引起"；
（2）回滚有没有副作用？**有状态变更（DB schema、数据迁移、外部方已消费的消息）不能简单回滚** →
改用开关（feature flag 关闭）、扩容、降级、限流止血；
（3）不可回滚又没有开关 → 前滚修复，但要**立刻拉更多人、把时间预算说清楚**。
关键原则：**恢复优先于根因**。MTTR 是结果指标，先把业务恢复，根因留给复盘。
**判断线**：能说出"我不确定是不是这个变更引起的，但回滚成本比排查成本低，所以先回滚"——这就是资深 SRE 的判断。

**弹药**
- `kubectl rollout undo deployment/<x> --to-revision=<n>`（先 `rollout history` 确认目标版本可用）
- GitOps 回滚：**回滚 Git 提交 + 同步**，别 `kubectl edit` 手改（会和仓库漂移，下次同步又被覆盖）
- 回滚后**保留现场**：故障 Pod 先 `cordon` 节点、别删（`kubectl describe`/`logs --previous`/heapdump）
- 止血工具箱：降级（关非核心功能）、限流（入口保护）、扩容（应对容量类故障）、切流（跨 AZ/集群容灾）

**红线**｜❌ 故障中 `kubectl edit` 改线上——没有记录、没有回滚点、和 GitOps 冲突。
❌ 在没搞清依赖时回滚数据库（应用新版本已经写了不兼容的数据，回滚 DB = 数据损坏）。

**下一问**｜"回滚之后告警还在，你怎么判断是第二个故障还是余波？"

## 4. K8s 小版本升级后一批 Pod CrashLoopBackOff

**一句话**｜小版本最咬人的是**默认值变化和 API 弃用**，不是新功能——先看 release notes 的 breaking changes。

**30 秒答**｜定位三刀：
（1）`kubectl logs --previous` 看有没有明确异常（没有异常、只有 `Completed` → 可能是**安全策略拒绝**或探针杀）；
（2）`kubectl describe pod` 看 events 里有没有 **admission webhook / PSA** 的拒绝信息；
（3）**diff 正常 Pod 和异常 Pod 的 spec**，差异点直指某个默认值变了。
1.28→1.29 这类升级的典型坑：**PodSecurity 准入（PSA）默认等级收紧**
（`privileged`/`baseline`/`restricted`，走 namespace label）
导致带 `hostPath`/`hostNetwork`/提权的 Pod 起不来；
另外 **`status` 字段变更、CSI/CNI 版本偏移、kubelet 配置字段废弃（如老的 `--cadvisor-port`、`PodSecurityPolicy` 早在 1.25 移除）** 都常见。
**止血**：给 namespace 打豁免 label（`pod-security.kubernetes.io/enforce=baseline`）或临时放宽，
**先恢复业务再改 workload**（加 `securityContext`、去掉 hostPath）。
**判断线**：升级故障的正确姿势是**分批灰度**——先升一个节点组、留观 24h，再推全量。

**弹药**
- `kubectl get ns --show-labels | grep pod-security`
- `kubeadm upgrade plan` / 托管集群的兼容性预检（云厂商都有）
- 弃用扫描：`pluto detect-helm -o wide` / API 迁移审计（`apiserver_requested_deprecated_apis` 指标）
- 集群里 `kubectl get events -A --field-selector reason=FailedCreate | grep -i 'violates'` — 直接看 PSA 拒绝

**红线**｜❌ 一次跨多个 minor；❌ 只升控制面不升节点（版本偏移区间外，行为不保证）；❌ 没备份 etcd 快照就开始升。

**下一问**｜"怎么设计一个'升级后 5 分钟内能判定要不要回滚'的观察方案？"

## 5. GitOps（ArgoCD）同步失败 / 配置漂移

**一句话**｜先分清是 **ArgoCD 自己连不上集群**（认证/证书/网络）还是**同步被拒绝**（资源冲突/DRIFT/Hook 失败）。

**30 秒答**｜ArgoCD 整体挂（所有 app 同步失败）→ 查**它自己的凭证生命周期**：
repo-server 的仓库 token、ArgoCD server 的证书/TLS、Application 里 serviceAccount 的 RBAC、以及 OIDC 证书过期。
单 app 失败 → 看 UI 里 `ComparisonError` 还是 `Sync failed`，
前者是读集群状态失败（apiserver/权限），后者是 apply 被拒（quota、admission、字段不可变如 `spec.selector`）。
**漂移（OutOfSync）**最常见原因是有人 `kubectl edit` 手改线上，
或 operator 写了 status/默认字段——处置是**声明侧对齐**（把真相写回仓库）而不是 `kubectl patch` 抹平。
**判断线**：ArgoCD 这类"发布停摆"是**变更类事故**，不是业务故障——第一动作是通知业务方"发不上去"，
同时评估**是否需要临时人工发布**（要走审批，且事后必须补回仓库）。

**弹药**
- `kubectl -n argocd get deploy/application-controller repo-server argocd-server`
- `kubectl -n argocd logs deploy/argocd-repo-server | tail -50`（仓库拉取失败在这里）
- `argocd app get <app>` 的 `SYNC STATUS` / `HEALTH STATUS` 两列要分开讲
- 强制同步 + 自愈（`syncPolicy.automated.selfHeal`）——**开自愈前要确认仓库一定是对的**，否则会把故障"自愈"进仓库
- 证书/凭据到期监控 → 见 `卡/控制面.md` #4

**红线**｜❌ 关掉 ArgoCD 的同步、改成手工 kubectl 发布来"先恢复"——制造漂移，之后更难回滚且失去审计链。

**下一问**｜"你允许生产环境有 selfHeal 吗？什么场景不允许？"

## 6. 引入 Istio / 服务网格后延迟飙升

**一句话**｜先回答"**我们为什么上 mesh**"——如果没有明确收益，这题的正解是"应该撤掉"。

**30 秒答**｜技术层面：sidecar 把每次调用变成**4 跳**（app → 本地 sidecar → 对端 sidecar → app），
额外开销来自 mTLS 握手/加解密、Envoy 的配置规模（listener/cluster 数量随服务数增长）、连接池复用失效。
CPU/内存没涨但 P99 涨 → 大概率**不是算力，是路径和队列**：
看 sidecar 的 `istio_request_duration_milliseconds`、`envoy_cluster_upstream_cx_*`、
以及 `iptables` 重定向 vs **eBPF 方式（Ambient / 1.20+ 的 Istio CNI 优化）** 的差别。
排查手法：先**关掉 mTLS（PERMISSIVE）**测一次、再**把该服务的 sidecar 注入去掉**测一次——
两步就能把"是 mesh 还是应用"分开。
**判断线**：这题真正考的是工程判断——**能说出"没想清楚收益就不该上，上了就要为它的复杂度负责"**比背命令值钱得多。

**弹药**
- `istioctl proxy-config clusters <pod>` / `endpoint` / `route`（配置规模膨胀是真实开销源）
- `istioctl analyze`（配置合法性）
- `ztunnel`/Ambient 模式 vs sidecar 模式：延迟和数据平面路径完全不同
- 缓解：调 sidecar `resources`（CPU limit 打满会让代理排队）、
  收敛 `Sidecar` 对象限制推送范围（**大集群里默认全量推送是延迟杀手**）、连接池/`maxRequestsPerConnection`

**红线**｜❌ 一上来就"加资源"。CPU 没涨你加什么 CPU。
❌ 不评估就全量注入——mesh 应该从**非核心链路**开始灰度。

**下一问**｜"什么情况下你会明确建议客户**不要**上 mesh？"（→ 服务数量少、无跨语言 mTLS/合规诉求、团队没有可观测运维能力）

## 7. 数据库主从切换后应用报主键冲突

**一句话**｜切换瞬间**仍有写落到旧主**，且旧主的增量没同步到新主——这是半同步延迟 + 应用重试共同造成的双写。

**30 秒答**｜状态机讲清楚：
旧主故障 → HA 判定失联（有检测窗口）→ 提升新主 → 应用连接池里**旧连接还指向旧主 IP**，
或 DNS/VIP 切换有 TTL 缓存 → 部分写成功落在旧主 → 旧主被降级后这些写**不会自动追平**（甚至被覆盖）。
自增 ID 各自推进 → 双写就是主键冲突 / 唯一键冲突。
止血：**停写 → 校验差异 → 追平或人工合并 → 再放开写**（顺序不能反）。
长期：半同步（`rpl_semi_sync_master_wait_for_slave_count` + `AFTER_SYNC`，即"lossless"）
+ GTID（保证切换后不再从旧主复制）+ **应用层幂等**（唯一业务键 + upsert，而不是依赖自增 ID）
+ 旧主降级后**永久隔离**（fence，不 fence 就会 split-brain）。
**判断线**：能主动区分"数据丢了"和"数据双写了"，并说清 RPO 怎么算（未同步的 binlog 事务数）。

**弹药**
- `SHOW SLAVE STATUS` 的 `Seconds_Behind_Master` / GTID `Executed_Gtid_Set` 差集（**差集就是 RPO**）
- VIP/DNS 切换：应用侧连接池要有 **`maxLifetime` 小于 VIP 漂移窗口**，并监听后端拓扑变更
- 应用重试要**只重试幂等写**；非幂等写重试 = 制造第二条脏数据
- K8s 里同理：StatefulSet + 外部 DB 时，Pod 驱逐重建会让连接风暴重复发生

**红线**｜❌ "配个 HA 自动切换就安全了"。切换的正确性取决于**是否 fence 旧主**和**是否应用幂等**，HA 工具只解决"选谁当主"。

**下一问**｜"半同步延迟突然从 0 涨到 800ms，你怎么监控和处置？"

## 8. 集群扩容：节点池 / Cluster Autoscaler / Karpenter

**一句话**｜扩节点不是终点，**"多快扩出来 + 扩的是不是对的机型"**才是 SLO。

**30 秒答**｜Cluster Autoscaler 按 **node group 预设机型**扩，粒度粗、
常见痛点是"GPU 机型售罄 / 配额不足 / 扩出来 40 分钟才 Ready"。
Karpenter 按 Pod 的**实际需求即时选机型**（含 spot/按需混合），装箱率和速度更好，代价是行为更动态、更难预测。
扩容失败的四类原因：**配额/库存**（云侧限制，要提前报备）、
**taint 没配好**（扩出来的节点没有对应污点，Pod 调度不上去，autoscaler 又以为没扩 → 继续扩，形成循环）、
**PVC 拓扑约束**（卷在 A 区，扩了 B 区节点也没用）、
**镜像预热缺失**（新节点首批 Pod 全在拉大镜像，DiskPressure 连锁）。
**判断线**：先问"**为什么需要扩，是容量还是突发**"——突发靠 HPA/定时预热，容量靠画像。

**弹药**
- Pod 上 `requests`/`limits` + `nodeSelector`/`tolerations` 与 node group 必须**成对设计**
- `kubectl describe node | grep -A5 Taints` — 新节点没被使用先查污点
- 优先级抢占：`PriorityClass` 保证关键负载在扩容时先落位、在资源紧张时能挤掉低优
- **over-provision 哨兵 Pod**（低优先级占位，需要时被抢占）换扩容时间——这是能讲出来的实战技巧
- 缩容同理：`cluster-autoscaler/scale-down-utilization-threshold` + PDB 会互相卡

**红线**｜❌ 靠"手动加节点"应急后不做容量画像复盘。❌ GPU 节点池不做**机型冗余**（单机型售罄 = 弹性归零）。

**下一问**｜"你怎么证明 30% 的成本下降不是靠牺牲可用性换来的？"

## 9. 节点维护：cordon / drain 的正确顺序

**一句话**｜drain 前必须先看 PDB，否则要么把业务打到 0 副本，要么 drain 卡住僵在那。

**30 秒答**｜标准四步：
（1）**告知 + 观察窗口**（选低峰、确认没有正在进行的发布）；
（2）`kubectl cordon <node>` 只挡新调度，**不影响已有 Pod**——先 cordon 观察几分钟再动，是最便宜的保险；
（3）`kubectl drain <node> --ignore-daemonsets --delete-emptydir-data`，
`--grace-period` 要和业务最长请求时间对齐；
（4）维护完 `uncordon`，**并确认节点恢复到 Ready、DaemonSet 全部回归**。
两个高频炸点：**PDB 会阻止驱逐到低于 minAvailable**（drain 会一直重试卡住，不是失败）；
`emptyDir` 数据会随 Pod 删除丢失（要显式确认没人在用 emptyDir 做本地状态）。
**判断线**：**本地盘节点（StatefulSet）drain = 数据不可用窗口**，必须先做副本切换，绝不能直接 drain。

**弹药**
- `kubectl get pdb -A` — 驱逐前必看
- drain 默认拒绝删"裸 Pod"（无控制器的），要 `--force`（**先确认那个裸 Pod 是不是历史遗留**）
- `kubectl describe node | grep -A3 Taints` — 维护中打 `node.kubernetes.io/unschedulable`，完成后确认已清除
- 大批量节点轮换（升级/换 OS）：**分组滚动 + 每组留观**，组间不要并行

**红线**｜❌ 不 cordon 直接 drain（驱逐过程中新 Pod 还可能被调度回来）。
❌ 用 `kubectl delete pod` 代替 drain——绕过了 PDB 语义。

**下一问**｜"drain 卡住不动，你怎么区分是 PDB 阻塞还是卷卸载失败？"

## 10. 事故之后：你怎么防它再来一次？

**一句话**｜**blameless 复盘 + 分层防御**：检测提前、止血变快、根因消除、同类问题系统防住。

**30 秒答**｜复盘产出必须是**可验证的行动项**，不是"加强意识"：
（1）**检测**——这次是用户先发现还是告警先发现？能不能把发现时间从 X 分钟压到 Y？（新增/修正指标和告警阈值）
（2）**止血**——回滚/切流/降级的路径是否 5 分钟内可执行？**没演练过的预案等于没有**；
（3）**根因**——5 Why 挖到"系统性原因"（配置流程缺失、缺少默认保护、依赖单点）而不是"某人改错了"；
（4）**同类扩散**——这个根因在别的集群/服务上是否也存在？做一次**同型排查**。
量化指标要一起报：**MTTD / MTTM / MTTR、错误预算消耗、客户影响面（请求数/时长/比例）**。
**判断线**：这题真正考的是你能不能把"我修好了"讲成"我把这类问题的发生概率降下来了"。

**弹药**
- 时间线要精确到分钟，并标出**每个环节耗时**：发现→定位→决策→执行→恢复（MTTR 拆解，能讲这个说明真做过）
- 防复发的优先级：**默认安全（safe by default）> 工具/流程 > 文档 > 培训**（培训权重最低）
- 用 **SLO + 错误预算**做变更刹车：预算烧完就冻结发布（把可靠性变成机制，不靠自觉）
- 可验证行动项示例："证书到期监控覆盖到 30/14/7 天并接入 oncall"比"注意检查证书"强 10 倍

**红线**｜❌ 追责式复盘（"某某操作失误"）——只会让下一次信息上报更晚、现场被破坏。
❌ 行动项写"加告警"但没有阈值和验证方式。
