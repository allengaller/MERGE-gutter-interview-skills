# 卡 · 控制面（apiserver / etcd / 调度器 / 控制器）

> 控制面题的判断基准：**控制面挂了，数据面不一定挂**。每题都要先答"影响不影响业务流量"。
> 每题都是 `一句话 → 30 秒答 → 弹药 → 红线 → 下一问` 五段，直接照念。

---

## 1. etcd 失去 quorum（3 节点挂 2）

**一句话**｜Raft 要多数派，3 台挂 2 台已经没有多数派，etcd 会**拒绝写入、最终连读都超时**——这时**绝对不能强制拉起来**。

**30 秒答**｜先确认状态：`etcdctl endpoint status --cluster -w table` 看 IS LEADER / RAFT TERM / DB SIZE，
`etcdctl member list -w table` 看成员是否 `started`。
失去 quorum 的集群里，幸存节点日志会持续 `lost quorum`、`failed to apply request`，apiserver 报
`etcdserver: request timed out`。
这时**强制单节点启动**（`--force-new-cluster`）会让旧数据变成唯一真相，
等另外两台回来时它们的更高 revision 会被覆盖 → **数据不可逆丢失**。
正确路径：**先 snapshot/备份现有数据目录**，再决定
（a）只有一台数据完好且能接受 RPO → 用它的 snapshot `etcdctl snapshot restore` 到新集群；
（b）有周期性 snapshot → restore 到最近备份，再核对关键对象（丢失窗口内的变更全靠 GitOps 重放）。
恢复后**必须逐集群校验**：`kubectl get all -A` 对不上 GitOps 仓库就当量重建。
**判断线**：这是"数据完整性 vs 可用性"的选择题，先问业务能不能接受丢数据，再动手。

**弹药**
- `ETCDCTL_API=3 etcdctl --endpoints=... --cacert=... --cert=... snapshot save /tmp/esnap.db`
- `etcdctl snapshot status /tmp/esnap.db -w table`（看 REV / TOTAL KEY，**先验快照不是空的**）
- `etcdctl snapshot restore` 出来的是新 data dir、新集群 ID，不能原地塞回旧目录
- 备份频率：关键集群 **每 5–15 分钟一次 + 变更前手动一次**（说得出数字）

**红线**｜❌ 用 `--force-new-cluster` 赌运气；❌ 事前没有 snapshot 备份还承认没监控（"我们有每小时备份"是这题的及格前提）。

**下一问**｜"丢了 12 分钟的 etcd 数据，你怎么算 RPO、怎么向业务交代？"

## 2. 1000 节点集群，5 分钟内 200 节点 NotReady

**一句话**｜先判断这是**集群级公共依赖故障**而不是 200 次节点故障——2 分钟内必须定出"控制面 / 网络 / kubelet"哪一层。

**30 秒答**｜第一手信息只要三样：
（1）`kubectl get nodes | grep NotReady | awk '{print $1}'` 拿到故障节点集合，**看它们的拓扑分布**（可用区/机架/交换机/版本批次）；
（2）apiserver 与 etcd 健康：`kubectl get --raw /readyz`、`etcdctl endpoint health --cluster`——控制面挂会让所有 kubelet 心跳同时失联，**表现和节点挂一模一样**；
（3）任取一个故障节点看 kubelet：`journalctl -u kubelet --since "-10m"`，
有没有 `PLEG is not healthy`、证书错误、`node status update failed`（后者指向控制面，前者指向本机）。
分布跟机房对齐 → underlay/CNI；跟版本批次对齐 → 变更；完全随机且控制面正常 → 很少见，深挖节点本地。
**判断线**：**"200 台同时挂"的概率分布本身就是排查工具**，一定要先找共同点再看单点。

**弹药**
- `kubectl describe node <n> | grep -A10 Conditions`（Ready=False 的 reason：`KubeletNotReady` / `NodeStatusUnknown`）
- `kubectl get events -A --field-selector reason=NodeNotReady --sort-by=.lastTimestamp | tail -30`
- 心跳机制：kubelet 默认 **10s 上报一次**，controller-manager `node-monitor-grace-period` 默认 **40s**（自建集群常改到 30–60s），
  所以"Unknown"通常意味着**至少 40s 没收到心跳**，不代表 kubelet 死了 → 这就是"幻象 Pod"（Pod 还在跑但控制面认为节点没了）
- 一旦节点 NotReady，`pod-eviction-timeout`（旧）/ taint manager（新，`node.kubernetes.io/unreachable:NoExecute` **默认 300s**）开始计时驱逐

**红线**｜❌ 上来批量 `kubectl delete node` 或重启 kubelet——这会让驱逐+重建同时打爆调度器和镜像仓库，制造第二场故障。

**下一问**｜"200 节点恢复后，大量 Pod 同时重建，你担心什么？"（→ 调度器排队 + 镜像集中拉取打爆仓库/磁盘 + 应用连接风暴）

## 3. apiserver 过载 / 大量 429

**一句话**｜apiserver 是无状态的但**不是无限的**；429 是 APF（Priority and Fairness）在保护 etcd，不是 bug。

**30 秒答**｜先分清是**谁在打**：
`kubectl get --raw '/metrics' | grep apiserver_request_total` 按 verb/resource/user 聚合，
最常见来源是**写得太多的 controller/informer**（尤其 reconcile 里无条件 `Update`，造成 status 空转写）和
`kubectl get -A` 这种全量 list。
再看瓶颈在哪：apiserver 自身 CPU/goroutine、etcd 写延迟（`apiserver_storage_duration_seconds`）、
还是节点上 kubelet 的 list-watch 风暴。
止血：调 APF 优先级给关键 workload（`FlowSchema`/`PriorityLevelConfiguration`）留带宽，
限流噪声客户端（降 `--kube-api-qps/burst`、修 informer 全量 relist）；
扩 apiserver 副本解决不了 etcd 慢——**扩 apiserver 只解决 CPU 和连接数**。

**弹药**
- `apiserver_flowcontrol_rejected_requests_total` — 429 的直接计数来源
- `apiserver_request_duration_seconds{verb="LIST"}` — 大 list 是头号杀手
- `etcd_server_slow_apply_total`、`etcd_disk_wal_fsync_duration_seconds`（**P99 > 10ms 就该紧张**）
- 客户端侧：`WatchList` / paginated list / `field-selector` + namespace 收窄，避免 `-A` 全量

**红线**｜❌ "重启 apiserver"。控制面重启期间所有写全失败，过载只会更糟。

**下一问**｜"为什么扩 apiserver 副本不能解决 etcd 慢？"（→ 写路径串行点在 etcd 多数派，apiserver 只是前端）

## 4. 证书过期（组件 / 集群 CA）

**一句话**｜这是**最容易预防、最常发生**的故障——因为它一定会发生，你不管它它就到。

**30 秒答**｜报错有固定形状：`x509: certificate has expired or is not yet valid`，
表现是"某组件突然全部认证失败"——ArgoCD 同步全挂、kubelet 无法注册、metrics 采不到。
定位：`kubeadm certs check-expiration`（kubeadm 集群）、
或逐个 `openssl x509 -enddate -noout -in <cert.pem>`；
**ServiceAccount 签发密钥、etcd 证书、front-proxy 证书是三套独立生命周期，别只 renew 一套**。
应急：换证书 + 重启依赖组件（apiserver / controller-manager / scheduler / etcd 各自读的证书不同，改对哪个重启哪个）。
长期：**cert-manager + 到期告警（30/14/7 天三档）**，把证书写进变更 checklist——它不是"事件"，是"计划内工作"。

**弹药**
- `kubeadm certs check-expiration` / `kubeadm certs renew all`
- `openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -dates -subject`
- `kubectl get secrets -A -o json | jq` 里找 `kubernetes.io/tls` 类型逐个到期（业务侧入口证书同理）
- 监控：`apiserver_client_certificate_expiration_seconds_count`（**能说出这个指标名就是加分**）

**红线**｜❌ 用"跳过校验"（`insecure-skip-tls-verify`）当长期方案——把可预防故障换成安全事故。

**下一问**｜"证书自动轮转怎么做到不打断业务连接？"（→ kubelet client cert 轮转、连接需重连窗口、旧证书保留一段信任期）

## 5. watch 断线会不会漏事件？

**一句话**｜不会漏——机制是 **resourceVersion + relist**，但代价是"漏了会静默重来一遍全量"。

**30 秒答**｜informer 与 apiserver 之间是 HTTP long-poll 的 watch，不是持久 TCP 长连接，
断线（网络抖动、apiserver 重启、etcd compaction）后 client 带着上次的 `resourceVersion` 重连：
- 服务端还保留该 revision → 从断点续传，事件无缝；
- 已被 compaction 删除 → 返回 **410 Gone**，informer **触发全量 relist** 重建本地缓存。
所以"漏事件"的表现不是丢数据，而是**一次意外的全量 LIST**——在 10 万对象规模的集群里，
一次 410 风暴能把 apiserver 和 etcd 一起打穿。这就是大集群要**分片 watch（shard informer）、避免 `-A` 全量 list** 的原因。
etcd 侧的 revision 全局递增，是 watch 不丢事件的底座；etcd compaction 保留窗口有限，所以 relist 一定会发生，只是概率问题。

**弹药**
- 日志关键字：`too old resource version` / `watch closed` / `Connection reset by peer`
- `--etcd-compaction-interval`（apiserver 侧）与 etcd `--auto-compaction-retention` 要一起看
- informer 侧指标：`workqueue_*`、client-go `reflector_list_duration_seconds`
- 控制器必须**幂等 + level-triggered**：不能假设"事件只来一次"，也不能假设"不会重复来"

**红线**｜❌ 说"kubelet 和 apiserver 是长连接所以不会断"。是 HTTP watch，会被网络抖动打断——这是 90% 候选人栽的误区。

**下一问**｜"为什么 K8s 控制器要设计成 level-triggered 而不是 edge-triggered？"（→ 事件可丢可重，唯一可靠的是对比 spec/status）

## 6. controller-manager / scheduler 挂了会怎样

**一句话**｜**已运行的 Pod 不受影响**，受影响的是"变更能力"：不能调度、不能收敛、不能驱逐。

**30 秒答**｜数据面（已建立的 Pod、Service 转发规则、kubelet 本地管理）不依赖控制面持续在线——
这是 K8s 的关键设计，答这题必须先说这句。
kube-scheduler 挂：新建/重建的 Pod 停在 Pending；
controller-manager 挂：Deployment/ReplicaSet/Endpoint/ServiceAccount/Job/PV 绑定等**所有 reconcile 停摆**，
滚动更新卡住、Job 不创建、Endpoints 不更新（新 Pod Ready 了也不进 Service！）；
apiserver 挂：以上全部 + kubectl 不可用，但 kubelet 用**本地缓存的 pod spec** 继续跑现有容器。
HA 方式：多副本 + **leader election**（kube-controller-manager / kube-scheduler 靠 apiserver 的 Lease 抢锁，同一时刻只有一个活）。

**弹药**
- `kubectl get lease -n kube-system`（`kube-controller-manager` / `kube-scheduler` 两条，看 holder 和 renewTime）
- `kubectl get componentstatuses`（coredns/etcd/scheduler，多数发行版已废弃，**说出来要带"已废弃"这个限定**）
- 验证数据面独立性：停掉 apiserver，`curl <nodeIP>:<nodePort>` 仍通 → 说明 Service 转发规则已在本地
- 驱逐相关：节点 NotReady 后的 Pod 处理由 **controller-manager 的 node lifecycle 控制器**负责，所以它挂了连驱逐都不做

**红线**｜❌ 说"控制面挂了就全停"。数据面自治是这题的及格线。

**下一问**｜"apiserver 挂 30 分钟，业务侧你观察到什么？"（→ 扩缩/发布/自愈全停，但存量流量正常）

## 7. etcd 磁盘 I/O 抖动 → 整个集群变慢

**一句话**｜etcd 对**fsync 延迟**极度敏感，一块慢盘能拖慢整个集群的所有写。

**30 秒答**｜Raft 每条日志都要写 WAL 并 fsync，多数派确认后才返回；
所以 `etcd_disk_wal_fsync_duration_seconds` P99 从 1ms 涨到 50ms，apiserver 写延迟就跟着涨，
表现是"kubectl 卡顿、controller 队列堆积、调度变慢"，而**没有任何一个组件明确报错**——这类故障最难定位。
判据：fsync **P99 > 10ms 报警、> 25ms 已经不正常**（说得出这两条线就是加分）；
同时看 `etcd_server_leader_changes_seen_total`（频繁换 leader = 心跳超时 = 磁盘或网络）。
处置：把 etcd 迁到 **独立 NVMe/本地 SSD**，不与容器数据盘、日志盘共享；
关掉同盘的其它 IO 大户；`--quota-backend-bytes` 控住 DB 大小（**8GB 常用上限，> 8G 就要警惕**），
大 value（>1.5MB）必须拆分——etcd 不适合存大对象，要用 CRD 时把 payload 放对象存储、etcd 只放引用。

**弹药**
- `etcd_disk_wal_fsync_duration_seconds{quantile="0.99"}` / `etcd_disk_backend_commit_duration_seconds`
- `etutl check datapath --io-sync=512 --out-file=/tmp/check.json`（官方压测工具）
- `fio` 基准：etcd 官方要求 99% fsync 512B < 10ms
- compaction/defrag 区别：**compact 只标记逻辑删除，defrag 才回收物理空间**——`--auto-compaction-retention` + 低峰期 defrag

**红线**｜❌ 把 etcd 和容器镜像放在同一块盘上——这是最贵的一课。

**下一问**｜"etcd DB 涨到 10GB 了怎么办？"（→ 先查大对象/未清理事件；compact + defrag；扩 quota 只是止血）

## 8. ConfigMap 改了但不生效

**一句话**｜分两种：**挂载的会热更新但有延迟，env 引用的永远不生效必须重启**。

**30 秒答**｜`envFrom`/`valueFrom` 注入的值在容器启动瞬间就固化了，改 ConfigMap 对已运行 Pod **完全无影响**。
以 volume 挂载的会更新，但链路是 `kubelet 同步周期（默认 period 同步，常见 10s–1min）+ kubelet 缓存`，
所以有几秒到 1 分钟的延迟，**不是立即**；而且**subPath 方式挂载的不更新**——这是最高频的坑。
应用还要真的重读文件：只有支持热加载的组件（nginx `reload`、部分 agent）才受益，
Java 里 `@ConfigurationProperties` 不会因为你换了文件就重新绑定。
需要"改了自动滚动"就用 **checksum annotation**（Helm 常见写法：把 configmap hash 写进 Pod template）或 Reloader/Stash 类工具。

**弹药**
- `kubectl exec <p> -- cat /etc/app/config.yaml` 对比 `kubectl get cm <c> -o yaml` — 一步确定"没同步"还是"没重读"
- 检查是否用了 `subPath`：`kubectl get pod <p> -o jsonpath='{.spec.containers[].volumeMounts[].subPath}'`
- Secret 同理（且 Secret 更新涉及 RBAC 泄露面，挂载方式比 env 更安全）
- 生产纪律：**配置变更走发布流程**，不要依赖热更新——可回滚、可追溯

**红线**｜❌ "改了 ConfigMap 等一会儿就好了"——不写清是 volume 还是 env、有没有热加载就下这个结论。

**下一问**｜"如何让 ConfigMap 变更自动触发滚动重启，同时避免所有 Pod 同时重启？"

## 9. 集群升级后部分功能异常（版本偏移）

**一句话**｜K8s 各组件有**版本偏移（skew）允许区间**，超出区间的行为是"不保证"，不是"应该能用"。

**30 秒答**｜先确认三件事：
（1）**API 弃用/移除**——升级前用 `kubectl get deploy -A -o yaml | grep apiVersion` 或 deprecation 检查工具（pluto）扫一遍，
最典型的是 `PodSecurityPolicy` 在 1.25 被移除 → 换 PSA/PSP 替代控制器；
（2）**默认值变化**——小版本最容易咬人（如 PSA 默认等级、探针默认、topology aware hints 默认开关）；
（3）**组件偏移**：kubelet 版本可以比 apiserver **旧若干个 minor**，但不能更新；CNI/CSI 驱动要跟着验证。
排查手法是**二分**：把异常 Pod 的 spec 与"正常的那个"逐字段 diff（`kubectl get -o yaml` + diff），差异往往指向一个默认值变了。
**判断线**：升级故障的正确回答是"先缓解（回滚/加豁免 label）再定位"，不是"我先研究明白"。

**弹药**
- `kubectl get --raw='/readyz?verbose'`、`kubectl version -o json`（对比各节点 kubelet/kube-proxy 版本）
- `kubeadm upgrade plan` / 托管集群看控制面与节点组版本差
- 发布前：`pluto detect-all-in-cluster` 或厂商的兼容性预检
- 缓解手段示例：给 namespace 打 `pod-security.kubernetes.io/enforce=baseline` 豁免，先恢复业务再改 workload

**红线**｜❌ 一次跨多个 minor 升；❌ 没有分批灰度（先升一个节点组、跑 24h 再推全量）。

**下一问**｜"1.28 → 1.29 后 30% Pod CrashLoopBackOff，你的第一反应是什么？"（→ 题库 场景题 #3：先看 release notes breaking change + PSA 默认值）

## 10. 谁能拖垮控制面？（高频反向题）

**一句话**｜三种写法最致命：全量 list、无条件 Update、无限重试风暴。

**30 秒答**｜（1）`metadata.namespace` 为空 + label selector 缺失 → **cluster-wide LIST**，
apiserver 要从 etcd 读全量再序列化，几十万对象时单次可达 GB 级响应；
（2）reconcile 里没有语义化比较就 `Update`，产生**空转写风暴**（每次写都触发 watch → 再 reconcile → 死循环）；
（3）失败后不带退避地重试 / 不加限流，控制器一崩全集群 QPS 打满。
还有第 4 类：**给大资源开 status 频繁更新**（应该拆 `status` 子资源）和 **finalizer 卡在删除路径**导致 etcd 键堆积。
答这题要顺带给治理手段：client-go `--kube-api-qps/burst`、APF FlowSchema 隔离、
informer 用 `FieldSelector: spec.nodeName`（kubelet 场景标配）+ namespace 收窄、写操作前 `reflect.DeepEqual` 比对。

**弹药**
- 定位手段：`apiserver_request_total` 按 `<userAgent, verb, resource>` 聚合，**top N 就是元凶**
- `apiserver_request_duration_seconds` 找 P99 最高的 resource/verb 组合
- `kubectl get events -A | wc -l` — events 无 TTL 时会把 etcd 撑爆（`--event-ttl` 默认 1h）
- 事件写放大：老集群常见 event 对象占 etcd 一半容量，这是能讲出来的实战细节

**红线**｜❌ 承认自己的控制器"list 全量集群比较省事"。这题的正确态度是先承认这是设计缺陷。

**下一问**｜"给你一个 5 万 Pod 的集群，你的 operator 怎么写才不会成为下一个故障源？"
