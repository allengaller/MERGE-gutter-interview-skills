## 1. K8s 时间常量（背这几个就够上场）

| 场景 | 默认值 | 一句话解释 |
|---|---|---|
| kubelet 上报节点心跳 | **10s** | 节点状态的写入频率 |
| node-monitor-grace-period | **40s** | 超过它没心跳 → 节点 `Unknown`/NotReady |
| 不可达节点驱逐（NoExecute taint） | **300s** | `node.kubernetes.io/unreachable` 起算，之后 Pod 才真被驱逐 |
| terminationGracePeriodSeconds | **30s** | SIGTERM → SIGKILL 的宽限窗口 |
| 容器日志轮转 | **10MB / 5 个** | `containerLogMaxSize`，不设就无限涨 |
| image GC 高/低水位 | **85% / 80%** | 只在 imagefs 吃紧时才激进回收 |
| resolv.conf `ndots` | **5** | 小于 5 个点先按 search 域串查（DNS 慢的头号原因） |
| DNS UDP 超时 → TCP 重试 | **~5s** | "卡 5 秒再成功"的经典形状 |
| 内核 TCP keepalive 探测起始 | **7200s** | 比多数 LB 空闲超时（常见 900s）长得多，**默认值救不了长连接** |
| etcd 事件保留（event-ttl） | **1h** | 但 apiserver 内对象写入无 TTL，要靠归档清理 |
| Prometheus 本地保留 | **15d** | 本地 TSDB 是临时缓存，不是存储 |
| kubelet 同步周期（syncPeriod） | **~10s 起（可配）** | ConfigMap volume 更新有延迟的根因 |
| 抓取间隔（常见实践） | **15s / 30s** | 30s 会整段漏掉毛刺型故障 |

**万能句式**：说数字必须带"默认值/我们改成多少/为什么改"。例：
> grace period 默认 30s，我们核心链路调到 60s，因为最长请求是 45s 的报表导出，且配了 preStop sleep 10s 等 Endpoints 传播。

## 2. 状态码 / 退出码速查

| 现象 | 含义 | 下一步 |
|---|---|---|
| exitCode **137** | 128+9 = **SIGKILL**，多为 OOMKilled 或驱逐/探针杀 | 看 `lastState.terminated.reason` 是不是 `OOMKilled` |
| exitCode **143** | 128+15 = SIGTERM，**正常终止**（或被探针杀） | 查是不是 liveness 过激 |
| reason `Completed` + CrashLoop | 进程**正常退出** = 容器没有前台进程 | 查 Dockerfile CMD 是否守护进程化 |
| `ImagePullBackOff` vs `ErrImagePull` | 前者是退避重试的**状态**，后者是**单次失败原因** | 看 `kubectl describe` 的原话（tag 不存在/凭证/网络/架构） |
| HTTP **503**（Ingress） | **后端没有可用 endpoint** | `kubectl get endpoints <svc>` |
| HTTP **502**（Ingress） | 连上了但上游响应非法/超时 | 查 backend-protocol、超时、header 大小 |
| K8s API **429** | APF 限流：**你在打爆 apiserver** | 看 `apiserver_flowcontrol_rejected_requests_total`，降 QPS/改 list-watch |
| watch **410 Gone** | `too old resource version` → **触发全量 relist** | 大集群要分片 watch，别 `-A` 全量 list |
| `Pending` + `FailedScheduling` | 调度器明确拒绝 | 看 failed-schedulable-nodes 注解（多少节点因何不匹配） |
| `Pending` + 无调度事件 | 大概率 **PVC 未绑定**或等待 first consumer | `kubectl get pvc` |
| `Evicted` | kubelet 主动驱逐（磁盘/内存压力） | 看节点 Condition + QoS 顺序 |
| 节点 `DiskPressure=True` | 通常是 **imagefs 满**，不是根盘 | `crictl rmi --prune` |

## 3. 调度：必备 6 个谓词（能背 6 个及格，8 个加分）

1. `PodFitsHost` — 指定 nodeName
2. `PodFitsHostPorts` — hostPort 冲突
3. `PodMatchNodeSelector` — nodeSelector
4. `PodMatchNodeAffinity` — required / preferred（**要能区分这两者语义**）
5. `PodFitsResources` — CPU/内存/巨页（最常被打满）
6. `NoVolumeZoneConflict` — PV 的 zone 约束

加分 3 个：`MatchToleration`（污点容忍）、`PodTopologySpread`（拓扑分布）、`MatchInterPodAffinity`（Pod 间亲和/反亲和）

**调度框架扩展点（1.17+）**：`PreFilter → Filter → PostFilter → Score（PreScore/Score/NormalizeScore）→ Reserve → Permit → PreBind → Bind`

**默认打分**：**LeastAllocated**（优先调度到空闲率高的节点），**不是 binpack**——这是高频误区，被问到要立刻纠正自己。

## 4. 三探针语义（一张表说完）

| 探针 | 失败后果 | 参与流量摘除 | 典型误用 |
|---|---|---|---|
| **startupProbe** | 通过前其他探针**不生效** | ❌ | 用它兜冷启动（JVM/模型加载 2–5 分钟）才是正解 |
| **readinessProbe** | **摘出 Endpoints，不重启** | ✅ | 探测下游依赖 → 依赖抖动时全场摘流量（雪崩放大器） |
| **livenessProbe** | **重启容器** | ❌ | 探测下游/加载重资源 → 局部抖动放大成集群级重启风暴 |

**判断线（这题的标准答案）**：readiness 管"现在能不能接流量"，liveness 管"重启能不能救回来"——
**只有能被重启解决的问题才配 liveness**，其余全归 readiness。

## 5. QoS 与驱逐顺序

| 等级 | 条件 | 驱逐顺序 | 被 OOM 杀优先级 |
|---|---|---|---|
| **Guaranteed** | 所有容器 requests == limits（CPU+内存） | **最后** | 最低 |
| **Burstable** | 有 requests 但 requests ≠ limits | 中间 | 按超出 requests 的比例 |
| **BestEffort** | 什么都不写 | **最先** | 最高 |

- **驱逐 ≠ OOMKilled**：驱逐是 kubelet 按策略主动丢 Pod（节点级 DiskPressure/MemoryPressure），OOM 是内核在 cgroup 内杀进程。
- **page cache 计入 cgroup 内存**：所以"RSS 没到 limit 却被 OOMKilled"要查的是**容器总内存含 cache**，或**节点级 OOM**（`dmesg` 有记录）。
- **kubelet 默认 30s 采样会漏瞬时毛刺**——这是"看起来没到 limit"的第二个解释。

## 6. SLO / 错误预算换算（30 天 = 43200 分钟）

| SLO | 每月不可用 | 每年不可用 |
|---|---|---|
| 99.9% | **43.2 min** | 8.8 h |
| 99.95% | **21.6 min** | 4.4 h |
| 99.99% | **4.32 min** | 52.6 min |
| 99.999% | 25.9 s | **5.26 min** |

- 业界档位：核心服务 **99.95%–99.99%**，周边服务 **99.5%–99.9%**。
- **burn rate 2% 规则**：短窗 1h 烧掉 2% 预算 → page；长窗 6h/3d 慢慢烧 → ticket。
- 依赖乘法：串 3 个 99.9% 依赖 → 上限约 **99.7%**。**多依赖天然拉低 SLO**，所以要么冗余要么降级。

## 7. etcd / 存储阈值

| 指标 | 健康线 | 说明 |
|---|---|---|
| `etcd_disk_wal_fsync_duration_seconds` P99 | **< 10ms** | > 10ms 报警，> 25ms 已经不正常（**能报这两条线就是资深**） |
| `etcd_disk_backend_commit_duration_seconds` | 同量级 | 慢 = 写路径全线变慢 |
| `--quota-backend-bytes` | **8GiB** 常用上限 | 超了要查大对象/未清理事件，并做 compact + defrag |
| 单对象大小 | **> 1.5MiB 就要改设计** | 大 payload 放对象存储，etcd 只放引用 |
| compact vs defrag | — | **compact 只标记逻辑删除，defrag 才回收物理空间** |
| etcd 备份频率 | **5–15 分钟一次 + 变更前手动一次** | 快照的 **REV 就是 RPO 的时间戳** |

Raft 常识：3 节点容忍 1 台故障，5 节点容忍 2 台；**失去 quorum 绝不能 `--force-new-cluster`**（数据不可逆丢失）。
跨机房：**同 region 内 RTT < 5ms 可跑 Raft，跨 region（> 50ms）不要**，跨区用异步备份。
