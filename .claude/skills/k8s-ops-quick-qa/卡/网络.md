# 卡 · 网络与服务发现

> Service / DNS / Ingress / CNI / NetworkPolicy 层的速答口径。**面试里最容易被问"分层怎么切"的一类**。
> 每题都是 `一句话 → 30 秒答 → 弹药 → 红线 → 下一问` 五段，直接照念。

---

## 1. Service 不通，怎么查？

**一句话**｜按 `Service → Endpoints → Pod → kube-proxy → NetworkPolicy → DNS` 六层往下切，每层都有独立证据。

**30 秒答**｜先分清**是访问不通还是解析不通**：能解析出 ClusterIP 说明 DNS 这一层过了。
第一步 `kubectl get svc` 看 type/端口/targetPort，第二步 `kubectl get endpoints <svc>`——**Endpoints 是空的，问题就一定在 Service 侧，不用再看网络**；
Endpoints 有内容，就 `kubectl exec` 到**同集群另一个 Pod** 里直接 `curl <podIP>:<containerPort>` 绕开 Service 验证；
Pod IP 通、Service IP 不通 → 查 kube-proxy/Service 网络编程；
再不通 → 查 NetworkPolicy；最后才怀疑 CNI。
**判断线**：始终**用 Pod IP 做对照实验**，有对照就能把"应用挂了"和"网络挂了"分开。

**弹药**
- `kubectl get endpoints <svc> -n <ns>` — 最快的一刀
- `kubectl exec -it <dbg> -- curl -sv <podIP>:<port>` — 绕开 Service
- `kubectl get svc <svc> -o wide` — 对 `selector` 和 Pod label
- 节点上 `ipvsadm -Ln | grep <ClusterIP>`（iptables 模式看 `iptables -t nat -L KUBE-SERVICES -n`）

**红线**｜❌ "重启 CoreDNS 试试"。Endpoints 为空跟 DNS 一点关系都没有，先拿证据再动手。

**下一问**｜"Endpoints 是空的，为什么？"（→ selector 不匹配 / readiness 没过）

## 2. Endpoints 为空（或有 Service 没后端）

**一句话**｜只有两个原因：selector 没匹配上，或者匹配上了但 Pod **没通过 readiness**。

**30 秒答**｜Endpoints 控制器只看两件事：label 是否被 selector 选中、Pod 是否 Ready。
`kubectl get pod --show-labels` 对一遍 `kubectl get svc -o jsonpath='{.spec.selector}'`，
两边不一致最常见于 chart 里 label 加了 `app.kubernetes.io/version` 这种**带版本的 label**，一升级 selector 就断。
selector 没问题就看 `kubectl describe pod` 的 readiness 失败原因——**未 Ready 的 Pod 不进 Endpoints**，
这是"Pod Running 但 Service 拿不到它"的标准答案。
**判断线**：Pod Running ≠ Ready，`kubectl get pod` 的 `2/2` 那列才是 Ready。

**弹药**
- `kubectl get endpointslice -l kubernetes.io/service-name=<svc>` — 1.21+ 看真正的后端和 Ready 状态
- `kubectl get pod -l <selector> -o wide` — 手动验 selector
- `kubectl describe pod <p> | grep -A5 Readiness` — 探针失败原因
- `readinessGates`（自定义就绪条件，如 `target-health.elbv2.amazonaws.com`）也会卡住不进 Endpoints

**红线**｜❌ 靠"加个 liveness 探针"来修复——liveness 只管重启，不管流量。

**下一问**｜"liveness 和 readiness 到底谁影响 Endpoints？"（→ 只有 readiness；liveness 挂的是重启）

## 3. DNS 解析慢 / 偶发超时

**一句话**｜九成是 `ndots:5` 导致的**搜索域串查**和 CoreDNS 单副本容量，不是解析器坏了。

**30 秒答**｜`/etc/resolv.conf` 里 K8s 默认 `options ndots:5`：
名字里有 ≥5 个点才直接查绝对域名，否则**先按 search 后缀拼一遍**。
所以 `curl foo.bar.com`（2 个点 < 5）会先查 `foo.bar.com.svc.cluster.local`、`.cluster.local` 等 4 次，
每次 UDP 超时都放大延迟。
排查顺序：先 `time nslookup <完全限定名>`（带末尾点的 `foo.bar.com.`）对比短名，如果 FQDN 快、短名慢，就是 ndots；
再看 CoreDNS 副本数、`errors` 插件日志、`coredns_dns_response_latency`。
**止血**：客户端写 FQDN（末尾加点）、或改 Pod `dnsConfig.options` 把 ndots 降到 2、或上 node-local-dns。

**弹药**
- `kubectl exec -it <p> -- cat /etc/resolv.conf`
- `nslookup <svc>.<ns>.svc.cluster.local.` — 末尾点强制绝对
- `kubectl -n kube-system logs -l k8s-app=kube-dns --tail=100 | grep -i error`
- CoreFS/conntrack：UDP 超时会**重试到超时才走 TCP**，所以表现是"卡 5 秒再成功"

**红线**｜❌ 把 ndots 改成 0 交上去。搜索域失效，所有短名服务全断。

**下一问**｜"为什么 Pod 里访问外部域名比访问集群内服务更容易超时？"（→ UDP 丢包 + resolv.conf 重试策略 + search 域放大）

## 4. Ingress 返回 503 / 502

**一句话**｜503 基本是"**后端没有可用 endpoint**"，502 是"**连上了但上游没答**"——两者排查方向完全不同。

**30 秒答**｜先对着 Ingress Controller 的日志找它拒绝的原因，不要先看业务应用。
503：`kubectl get endpoints <backend-svc>` 是不是空的；再看 host/path 是否匹配（`pathType: Prefix` vs `ImplementationSpecific`），
path 写错会命中 default backend，很多 Ingress Controller 对 default backend 就是返 503/404。
502：Controller 能连到 Pod，但**响应不合法或超时**——查 `proxy-read-timeout`、应用返回非 HTTP 头、大 header（cookie 超 `large-client-header-buffers`）、
后端 HTTPS 证书与 annotation 的 `backend-protocol` 不匹配。
**判断线**：从 Controller 所在节点直接 `curl <podIP>:<port>`，通 → 配置层问题；不通 → 后端/service 层问题。

**弹药**
- `kubectl describe ingress <ing>` — 看 events 里的 "does not have any endpoints"
- `kubectl -n ingress-nginx logs deploy/ingress-nginx-controller | grep -E ' 50[23] '`
- `kubectl get ingressclass` — 有没有第二个 controller 抢了同 host
- 绕过 Ingress 直接 `kubectl port-forward svc/<app> 8080:80` 验证应用本身

**红线**｜❌ 不区分 502/503 就一起说"网络问题"。这是面试官最容易抓住的口误。

**下一问**｜"Ingress 后面是 Service 还是 Pod？流量路径上 NAT 发生在哪一跳？"（→ Ingress Controller → Service ClusterIP DNAT → Pod）

## 5. NetworkPolicy 生效导致不通

**一句话**｜NetworkPolicy 是**白名单模型**：一个 Pod 只要被任意一条 policy 的 podSelector 选中，它就只允许 policy 明确放行的流量。

**30 秒答**｜所以"加了个策略，别的 namespace 全打不进来"是**预期行为**，不是 bug。
排查先确认 CNI 是否真的实现了 policy（calico/cilium 支持；**flannel 不支持，写了也不生效**），
`kubectl get networkpolicy -A` 找命中该 Pod 的所有策略——**多条 policy 是并集（allow 累加），deny 无法显式写**。
放行方向要分开看：`ingress.from` / `egress.to`，`policyTypes` 里只写 Ingress 的话 Egress 完全不受限。
**止血**：临时删策略验证是不是它，再补上 `podSelector`/`namespaceSelector`/`ipBlock`；别改应用。

**弹药**
- `kubectl get netpol -A -o yaml | grep -B10 <pod-label>`
- 判定"被选中"：`kubectl get netpol <n> -o jsonpath='{.spec.podSelector}'`
- calico：`calicoctl get workloadendpoint`；cilium：`cilium policy trace -s <src-pod> -d <dst-pod>`
- 记住 **kube-proxy/CNI 都不为 DNS 开口子**：开了 egress 白名单必须显式放行 UDP 53 到 kube-dns，否则解析全挂

**红线**｜❌ 忘了放行 DNS。这是上 NetworkPolicy 后最高频的连环故障。

**下一问**｜"我开了 egress 限制，为什么 Pod 还能访问外网 IP？"（→ 只放行网段没放行 ipBlock / policyTypes 没写 Egress）

## 6. 间歇性连不通 / 偶发丢包（无明显配置错误）

**一句话**｜先怀疑 conntrack 表满和 LB 空闲超时，这两个都是"看起来随机"的经典来源。

**30 秒答**｜kube-proxy 的 iptables/IPVS 模式都依赖 conntrack，表满时内核直接**丢新建连接**，
日志里是 `nf_conntrack: nf_conntrack: table full, dropping packet`，
现象就是"每隔几分钟有几十毫秒的失败"，重试就好——最容易被误判成应用 bug。
另一类是**长连接被中间设备静默回收**：云 SLB/NAT 默认空闲超时常见 900s 或更短，
客户端没有 keepalive，服务端还以为连接活着。
**判断线**：失败是否集中在固定时间间隔（表满抖动）或固定空闲时长之后（超时被掐）。

**弹药**
- `sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max`
- `dmesg -T | grep -i conntrack`
- TCP keepalive 三层：应用层 keepalive > socket `SO_KEEPALIVE` > 内核 `net.ipv4.tcp_keepalive_time`（默认 **7200s**，比多数 LB 空闲超时都长，所以默认值救不了你）
- `ss -tno state established '( dport = :443 )'` 看 timer 字段

**红线**｜❌ 把 conntrack_max 无脑调大就完事。要同时看内存和为什么这么多连接——通常是**没有连接复用**。

**下一问**｜"调大 conntrack_max 有什么代价？"（→ 每条约 300B 内存 + hash 表退化；治本是长连接池/减少新建）

## 7. 跨节点 Pod 不通 / 大规模 NotReady 的网络分支

**一句话**｜先看 CNI 自己的健康面（BGP peer / 路由表 / agent），再看 underlay——跨节点问题绝大多数不在 K8s 层。

**30 秒答**｜同节点 Pod 互访走 veth+bridge，不经过 CNI 的跨节点路径；
**跨节点不通就是 overlay/路由问题**。calico 看 `calicoctl node status`（BGP Established？），
cilium 看 `cilium status` / `cilium-dbg bgp peers`，flannel 看 `subnet.env` 和 VNI 是否被 underlay 放行。
节点上 `ip route | grep <对端节点IP>` 有没有对应路由条目，是最直接的证据。
如果是**大面积**同时不通，方向立刻转到"公共依赖"：underlay 交换机、MTU 变更、一次集群级配置下发、或者控制面挂了导致 CNI 无法同步。
**判断线**：故障节点分布是否跟可用区/机架/交换机对齐——对齐就是 underlay，随机就是软件层。

**弹药**
- `calicoctl node status` / `cilium-dbg bgp peers` / `ip route show`
- `ip link` 看 MTU：云环境常见 MTU 1400/1450，按 underlay 限制设，**别默认 1500**
- `kubectl get pod -n kube-system -l <cni-selector> -o wide | awk '{print $7}' | sort | uniq -c` — 找 CNI Pod 异常的节点
- 抓包要抓**两跳**：源 Pod netns 内 + 目标节点物理网卡，对比才知道丢在哪一段

**红线**｜❌ 在跨节点不通时先重启 kubelet。CNI agent 挂了才是首选怀疑对象。

**下一问**｜"MTU 配错会表现成什么？"（→ 小包通、大包黑洞，TLS 握手/pod 日志上传偶发卡死）

## 8. Pod 更新时有连接被切断（滚动更新丢包）

**一句话**｜K8s 从"摘 Endpoints"到"真正不接流量"之间有传播延迟，不做 preStop 就会丢。

**30 秒答**｜Pod 被删时，**两件事并行发生**：Endpoint/EndpointSlice 摘除（要经 apiserver → 各节点 kube-proxy 编程）和
容器收到 SIGTERM。摘除是异步的，各节点收敛时间不一致（通常几百毫秒到几秒），
这段时间里老连接还在被新请求打进来，而进程已经开始退出 → reset。
正确姿势：容器捕获 SIGTERM 后**先停止接收新请求、把在途请求做完**，再退出；
配合 `preStop: exec sleep 5~15` 给摘除留出传播窗口，`terminationGracePeriodSeconds` 要大于业务最长请求时间。
**判断线**：丢包集中在发布窗口、且是 reset/502 而不是 refused → 就是这个。

**弹药**
- `lifecycle.preStop.exec.command: ["sh","-c","sleep 10"]` — 摘除传播窗口
- `terminationGracePeriodSeconds`（默认 **30s**）
- `kubectl get endpointslice -w` 观察摘除时间戳
- 客户端必须有重试（幂等）；一次 502 不该变成用户可见故障

**红线**｜❌ 只加 `sleep` 不改应用优雅退出。sleep 只是买时间，进程收到 SIGTERM 立刻硬退照样丢包。

**下一问**｜"readiness 探针和摘流量有什么关系？"（→ readiness 失败也会摘 Endpoint，所以发布期探针抖动=自伤）

## 9. 集群内访问外部服务不通

**一句话**｜先分清是 SNAT 出不了集群、DNS 解析不到、还是被 NetworkPolicy/防火墙拦了。

**30 秒答**｜Pod 出集群的包要经过 **SNAT（masquerade）**，源地址变成节点 IP。
不通先看三点：节点是否有默认路由和出网能力、云安全组是否放行、
**Pod CIDR 是否被 underlay 知道**（自建网络时 Pod 网段没配 NAT 或没发路由，出去有回不来）。
DNS 能解析到外网 IP 但连不上 → 是 egress 路径问题；解析不到 → 查 CoreDNS 的 forward 上游和 `resolv.conf`。
**判断线**：在**节点上** curl 同一个外部地址。节点通、Pod 不通 → SNAT/Pod CIDR；节点也不通 → 出网本身。

**弹药**
- `kubectl get nodes -o wide` 拿节点 IP，节点上直接 `curl -sv <ext>`
- `iptables -t nat -L POSTROUTING -n | grep MASQUERADE`
- `ip route get <extIP>` — 看是否走默认路由、是否命中 Pod CIDR 静态路由
- CoreDNS Corefile：`forward . /etc/resolv.conf`（上游挂了会全量超时）

**红线**｜❌ 直接给 Pod 挂 hostNetwork 绕过。绕过之后你永远查不到根因，而且丢掉了 NetworkPolicy 保护。

**下一问**｜"什么情况下你会真的用 hostNetwork？"（→ CNI 自身、kube-proxy 替代方案、需要节点 IP 的 controller；且必须配 DNS policy 处理）

## 10. 抓包定位：在哪一层抓？

**一句话**｜从两端往中间夹：源 Pod netns 和目的 Pod netns 各抓一次，对比缺哪一段。

**30 秒答**｜`kubectl exec` 到 Pod 里抓（要容器里有 tcpdump，或用 ephemeral debug 容器注入）看**有没有发出**；
在目的节点物理网卡抓看**有没有到达**；两个证据就能定界"中间丢"还是"根本没发"。
Service 的 ClusterIP 是**虚拟地址，抓不到**——它在本地就被 DNAT 改写，抓包要按 Pod IP 过滤，
或者用 `kube-proxy --proxy-mode=ipvs` 的 `ipvsadm` 看转发计数。
**判断线**：三态——没发出（应用/路由）、发出现不回（SNAT/underlay）、回了但被拒（policy/防火墙）。

**弹药**
- `kubectl debug -it <p> --image=nicolaka/netshoot --target=<app-container> -- tcpdump -ni any port <p>`（共享 netns 的临时容器）
- `nstat -az | grep -iE 'TcpRetrans|ListenDrops|ListenOverflows'` — 不抓包也能看出 backlog 溢出
- `ss -ltn sport = :<port>` 看 `Send-Q/Recv-Q`（accept 队列积压 → 应用瓶颈而非网络）
- 反向结论常用：`ListenOverflows` 涨 = **应用没 accept**，不是网络丢包

**红线**｜❌ 对 ClusterIP 抓包然后宣布"网络没问题"。抓不到不等于没转发。

**下一问**｜"如何区分'网络慢'和'应用慢'？"（→ 看 TCP 层重传/RTT vs 队列积压与 accept 速率）
