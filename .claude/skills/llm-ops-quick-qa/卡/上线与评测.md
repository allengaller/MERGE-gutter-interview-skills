# 卡 · 上线、灰度与评测

> 这组题考的是**"你敢不敢把这套东西放到生产上"**。面试官的口头禅是"灰度了没有？""评测跑了没有？"
> 答题共同的判断线：**静默降质比直接崩溃更危险**——崩了你至少知道要回滚。
> 每题都是 `一句话 → 30 秒答 → 弹药 → 红线 → 下一问` 五段，直接照念。

---

## 1. 新模型（比如标称 1M 上下文的 MoE）要上线，你的灰度路径是什么？

**一句话**｜**能力声明 ≠ 已验证能力**——按上下文长度分档灰度，标称 1M 就从 32K 起步，1M 单独压。

**30 秒答**｜
先跑通五阶段（下/引/存/载/服，见 `卡/引擎部署.md` #1），拿到"能推理"的基线；
然后**按长度分档**放量：32K 稳定 → 128K 验证 → **1M 单独压测，不进主流量池**；
每一档看三件事：质量（golden set）、性能（TTFT/TPOT/吞吐）、稳定性（OOM/hang/抢占）。
**判断线**：长上下文是**显存和延迟的非线性放大**，不是"配置里改个大数字"。
`--max-model-len` 从 32K 提到 1M，KV 上限涨 30 倍，并发额度可能直接被压到个位数——
不测就说"支持 1M"，等于把客户的 SLA 押在一个未验证的声明上。

**弹药**
- 长度分池：长上下文请求走独立实例池，**保护短上下文实例的并发和尾延迟**
- 预热必做：上线前用 1K/4K/16K 三档请求预热，把 JIT/图编译的首请求抖动挡在流量之外
- 影子流量 → 小比例（1%→5%→20%）→ 全量；每档都有明确的回滚触发条件与负责人

**红线**｜❌ 拿官方模型卡的参数当已验证能力；❌ 一次全量切换；❌ 灰度只盯 5xx，不看质量与延迟分布。

**下一问**｜"量化上线前必做什么？"（→ 本卡 #2）

## 2. 量化：W8A8 / AWQ / GPTQ 怎么选？上线前必做什么？

**一句话**｜选型看"要省算力还是省显存"；**上线必做业务 golden set 回归 + 困难样本人审**，不能只看 perplexity。

**30 秒答**｜
**W8A8**（int8 权重+激活）：通用首选，吞吐收益明确，精度风险相对可控；
**W4A16（AWQ/GPTQ）**：显存减半，是"单卡放不下"的解法，但精度损失必须实测评估；
精度极敏感的场景：FP8 或混合精度（敏感层保高精度）。
**上线必做**：业务 golden set 跑对比 + **困难样本人审**（边界 case、多跳推理、长上下文召回、代码/结构化输出）。
**判断线**：perplexity 降 0.1 不代表业务能用。
量化的失败通常是**特定任务塌方**（工具调用参数格式、长链推理、小语种），平均指标看不出来。

**弹药**
- 决策依据 = "收益 vs 风险"：W8A8 换来 x% 吞吐（可测），风险是某些任务退化（也可测，用分任务指标）
- 灰度节奏：影子流量对比 → 小比例放量 → 全量，每阶段留**同一份评测集的分数曲线**
- 回滚要点：量化模型独立版本、独立实例，回滚 = 切流量，不是热改配置
- 显存账：72B FP16 ~140GB → W4A16 ~36GB，单卡 80G 从"放不下"变"放得下且有余量给 KV"

**红线**｜❌ 说"几乎无损失"却没有评测证据；❌ 不做灰度，降完直接上生产；❌ 只看全局指标不看分任务。

**下一问**｜"上线后客户说'回答变笨了'，但没有任何报错，你怎么定界？"（→ 本卡 #3）

## 3. 上线后"回答变笨"但无报错，怎么定界？

**一句话**｜静默降质要**按变更链二分**：模板/采样参数 → 引擎版本 → 量化档位 → 数据分布，一次只回退一项。

**30 秒答**｜
先固定一个**可复现的失败样本集**（不能靠"我感觉变差了"）；
然后沿变更链二分：①**对话模板/角色拼接**是否变了（最高频根因）；②**采样参数**（temperature/top_p/停止符）；
③**引擎版本与配置**（chunked prefill、并发上限、`--max-model-len` 截断）；④**量化档位**；⑤**业务侧输入分布**变化。
**判断线**：如果同一样本在**旧版本上稳定好、新版本上稳定差**，就是可归因的工程变更，
不是"模型玄学"。定界的目标是找到**那一个 diff**，而不是快速给个说法。

**弹药**
- 模板问题特征：格式错乱、重复、提前停止、把工具调用吐成正文 → 比对 tokenizer 的 chat template 与 `add_generation_prompt`
- 截断被忽略：`max-model-len` 配小导致长输入被静默截断，答案"缺上下文"看似变笨（要查是否有关断告警）
- KV 抢占静默重算：显存吃紧时请求被抢占/换出，**质量不变但延迟塌方**，先分清是变笨还是变慢
- 对照实验：同一批 prompt、同一采样参数、两个版本各跑一遍，出**分任务差异表**

**红线**｜❌ "大模型就这样，不稳定"（这是放弃归因）；❌ 一次回退多项变更，问题复现不了就说不清。

**下一问**｜"引擎版本升级怎么做，才不会把这种事再来一遍？"（→ 本卡 #4）

## 4. 推理引擎/驱动升级，你怎么做才安全？

**一句话**｜升级当成**发布**做：差分指标 + 版本矩阵登记 + 可回滚，绝不允许"顺手升到最新"。

**30 秒答**｜
①**动机先行**：这次升级是为了新模型支持、性能收益还是安全修复？说不出收益就不升（收益决定验证重点）；
②**差分验证**：同一评测集 + 同一负载模型，跑"旧 vs 新"的**吞吐/延迟/质量**三条曲线；
③**版本矩阵登记**：模型/引擎/torch/CUDA/驱动**五元组**（+ 硬件架构）写进配置，禁止节点间漂移；
④**灰度与回滚**：新引擎独立实例池，回滚 = 切流量。
**判断线**：升级最常见的事故不是崩，而是**性能静默回退**（吞吐掉 15% 没人发现）
和**特性静默不生效**（投机解码配置项改名了，你以为开着）。

**弹药**
- 版本漂移的代价：集群里 3 个引擎版本 → 同一个模型给出不同行为，排障时无法归因
- 配置项要**运行时校验**：从服务日志/`/v1/models`/metrics 反查特性是否真的生效，不看启动命令
- 驱动与 CUDA 升级会连带影响 NCCL/通信库 → GPU 拓扑与通信相关用例必须回归
- 新硬件/新特性验证：`模型 + 引擎版本 + GPU 架构`三元组核（如 DSA/MTP 类特性可能 Hopper-only）

**红线**｜❌ 生产集群直接升最新版；❌ 升级后只验证"服务起来了"；❌ 没有版本矩阵，节点配置各版本混跑。

**下一问**｜"上线前的 checklist 到底有哪几项？"（→ 本卡 #5）

## 5. 推理服务上线前，你的 checklist 是哪几项？

**一句话**｜四组：**契约、容量、降级、可观测**——缺任何一组，都不叫"准备好上线"。

**30 秒答**｜
**①契约**：chat template 定版、`tool_calls`/流式/`reasoning_content`/超长输入 四类用例过；客户端与引擎字段约定一致。
**②容量**：压测给出**并发-吞吐-延迟曲线**（不是单点），明确 SLA 拐点在哪、峰值配额多少。
**③降级**：长度超限怎么办、引擎 OOM 怎么办、超时是重试还是截断——每种都有预案，且降级路径被测过。
**④可观测**：显存/算力利用率/延迟分位/错误码 按卡打标签上报，KV 命中率与抢占次数在监控里。
**判断线**：checklist 的价值在"容量"那组——**必须有曲线而不是一个数**。
一个"QPS 支持 200"的结论没有意义，"并发 60 以内 P99 TPOT 达标、超过后塌方"才是可运维的边界。

**弹药**
- 契约四类：工具调用 / 流式（首字节与增量边界）/ 超长输入 / 并发压测下的正确性
- 发布机制：滚动时新旧实例并存的**显存与 gang 约束**（多卡实例不能一半新一半旧）
- 上线动作要有变更单：模型 ID、权重 hash、引擎五元组、配置全文、回滚方式、负责人
- 预热完成才接流量：健康检查不能只看端口，要等首批预热请求成功

**红线**｜❌ 用"跑通了"当上线标准；❌ 没有降级预案（超时/超长/OOM 三问必答）；❌ 只有均值没有分位数。

**下一问**｜"怎么证明容量够？"（→ 本卡 #6）

## 6. 怎么给客户证明"这套容量够"？压测怎么做才算数？

**一句话**｜压**真实流量形态**（长度分布 + 到达分布），产出**曲线和拐点**，不是压一个漂亮数字。

**30 秒答**｜
①**回放真实分布**：上下文长度按实际分布采样（不是全用固定 prompt）、请求间套用峰值到达率；
②**逐级加压**：并发阶梯上升，记录每级的 TTFT/TPOT P50/P99、吞吐、显存水位、抢占次数；
③**找拐点**：P99 突破 SLA 或吞吐不再随并发上升的那一级就是容量上限；
④**留余量**：上线容量 = 拐点 ÷ 冗余系数（1.3–1.5）。
**判断线**：用固定短 prompt 压出来的 QPS 数字**毫无意义**——
它绕过了 KV 压力和调度成本，是"纸面吞吐"。这类数字在客户现场第一次真实压测就会翻车。

**弹药**
- 必测场景：长上下文混入（一条 100K 请求能把同实例的短请求尾延迟抬高数倍）、突发峰值、冷启动
- 抢占与排队要在压测里显式观察：`--max-num-seqs`、KV 使用率、被抢占请求数
- 结论表述："并发 X 以内满足 TTFT < a / TPOT < b，超过后 P99 塌方，因此按 Y = X/1.4 上量"
- 压测环境对齐：卡型、引擎五元组、量化档位与生产一致，否则数字不可迁移

**红线**｜❌ 报一个漂亮 QPS 不给分布和条件；❌ 只测稳态不测突发；❌ 压测配置与生产不同就外推。

**下一问**｜"如果这些细节你还没到生产深度，怎么答？"（→ 本卡 #7）

## 7. 被追问到你答不出的深水区（GPU 推理调优），怎么处理？

**一句话**｜**不编**。明确标注边界 + 给出系统性补法，这在评分里是**加分**，不是扣分。

**30 秒答**｜
标准说法：
> "这块我没到生产深度。我的补法是三步：跑通 vLLM benchmark 拿到自己机器上的真实吞吐曲线 →
> 读 PagedAttention 论文把显存管理模型吃透 → 复现一次量化回归（golden set 前后对比）。"

同时把主场拿回来：我有 K8s/GPU 调度、集群稳定性、可观测体系的实战（ACK 3 年），
**推理集群作为"异构易损系统"的运维心智**我是有的，缺的是引擎内部调优的纵深。
**判断线**：面试官问深水区，一半是在测**你知不知道自己不知道**。
在成本题上编一个数字，会连带把你所有其他数字的可信度拉掉。

**弹药**
- 迁移性证据（诚实处理 gap 用这套）：大模型知识体系（两本书）+ 嵌入式驱动背景（硬件亲和）+ 网络排障功底（RDMA 可迁移）+ AI Stack 工单一手场景
- 学习速度硬证据：**AI Stack 冷启动两周 → 一周 50 单、闭环率 95%**——直接回答"你怎么补训练领域 gap"
- 可现场演示资产：故障树引擎（16 顶层事件/约 300 底事件）、73 个分析器、网络逐跳追踪
- 反制编造：说出口之前问自己"分子分母是什么"，答不上就换成年货口径（讲方法、讲边界、讲补法）

**红线**｜❌ 编吞吐/编参数名/编"我们生产上是这样做的"；❌ 只承认不会，不给补法（= 没有成长证据）。
