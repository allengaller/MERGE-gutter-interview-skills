# 卡 · 算力规划与 TCO

> 估算题与成本题的速答口径。**这组题的分水岭是"会堆卡"还是"会算账"**——
> 面试官（AI Infra SA）的口头禅是"这个数字怎么算出来的？""每千 token 成本多少？""这笔投入客户多久回本？"
> 每题都是 `一句话 → 30 秒答 → 弹药 → 红线 → 下一问` 五段，直接照念。**结论可以给区间，过程不许跳步。**

---

## 1. 客户要私有化部署大模型，算力规划从哪一步开始？

**一句话**｜从**业务画像**倒推，不是从模型倒推——模型是第③步，不是第①步。

**30 秒答**｜五步路径：①并发画像（峰值/日均在线、QPS、上下文长度、延迟 SLA）
②换算单请求 token 吞吐需求（输入+输出 × 并发）
③选模型并**实测**单卡吞吐（不抄宣传数）
④卡数 = 峰值吞吐 ÷ 单卡吞吐 × 冗余系数（1.3–1.5）
⑤网络/存储/容灾配套。
**判断线**：①和④之间必须有"实测"这一步。任何跳过实测直接给卡数的方案，
在客户现场第一次压测就会翻车——因为吞吐对 batch、上下文长度、量化档位极其敏感。

**弹药**
- 冗余系数 1.3–1.5 的拆解：**流量抖动**（峰值不是均值）+ **故障域**（坏卡/坏节点要能容）+ **增长**（半年业务量）
- 显存下限另算：`权重 ÷ 单卡显存`，与吞吐算出的卡数**取大**
- 反例口径：客户说"要跑 72B"→ 72B 是权重约束；"2000 人用"是吞吐约束，两者算出来的卡数能差 3 倍

**红线**｜❌ 从"模型多大"直接拍卡数；❌ 全程没问延迟 SLA（TTFT/TPOT 不给，容量就没法定）。

**下一问**｜"客户只说'公司 2000 人都要用'，怎么办？"（→ 本卡 #2）

## 2. 客户只说"2000 人都要用"，你怎么往下算？

**一句话**｜这个数字**不能直接用**——先质疑前提，把"人头"翻译成"并发"，再翻译成"token/s"。

**30 秒答**｜人头 ≠ 并发。内部助手类应用的真实活跃率远低于人头数，
标准做法是**分层**：2000 人 → 日活（一般 20–40%）→ 人均日请求（5–10 轮）→ 集中度（80% 请求集中在 2 小时窗口）→ 峰值并发。
必问四项输入：**峰值并发、平均上下文长度、延迟 SLA、日均请求量**。
**判断线**：敢在计算之前先说"这个前提我要拆一下"是加分项。
照着 2000 当并发算，方案会大出一个数量级，客户第一笔预算就废了。

**弹药**
- 量级感觉：2000 人内部助手，峰值并发通常在 **20–50** 而不是 2000（这是经典估算题的标准假设）
- 集中度算法：日均请求总量 × 80% ÷ 峰值 2 小时 = 峰值请求速率
- 追问自己：是不是所有请求都走大模型？路由到小模型/缓存的比例直接改卡数

**红线**｜❌ 拿 2000 当并发数；❌ 不追问就给方案（"再买二十张卡吧"是减分信号）。

**下一问**｜"500 人日常使用 72B 模型，估一下 GPU 数量。"（→ `卡/性能与吞吐.md` #3 有完整推导）

## 3. 公有云 API vs 全私有化 vs 混合，TCO 对比模型怎么搭？

**一句话**｜四本账——**资源、人力、隐性、风险**，只比卡价的方案是在骗客户。

**30 秒答**｜
①**资源**：API 按 token 计费 vs 自建卡折旧 + 电费 + 机房 + 带宽；
②**人力**：自建要配推理引擎/运维/SRE 团队，这部分常年被漏算，通常**不低于卡成本**；
③**隐性**：自建踩坑周期（半年起）、模型升级要重做适配、版本锁定；
④**风险**：数据合规价值（不出的域本身就是收益）、供应与价格锁定。
**判断线**：给出**盈亏平衡点**——"月调用量超过 X 亿 token，且数据必须留在域内，私有化才回本"。
这条线是 SA 的专业价值所在，比任何技术选型都值钱。

**弹药**
- 分界判断：低频/试错期用 API；**规模化 + 数据敏感**才私有化
- 混合方案常常最优：**敏感推理私有化 + 弹性溢出公有云**（峰值买 token，平峰跑自建）
- 每千 token 成本口径：自建 = `(卡折旧 + 电 + 人力) ÷ 月总产出 token`，必须算到**实际利用率**，不是理论吞吐
- CFO 一句话模板："这个方案三年总成本 X，比全用 API 省 Y，代价是自己养 Z 个人、上线周期多半年"

**红线**｜❌ 只比卡价不比人力；❌ 说不出自家 API 与私有化的**切换路径**（客户会问"以后想搬走怎么办"）。

**下一问**｜"什么场景你会主动建议客户别自建？"（→ 本卡 #4）

## 4. 什么时候你主动说"这场景买 token 比自建便宜"？

**一句话**｜吞吐用不满卡的时候——**自建的成本是常驻的，API 的成本是线性的**，交叉点之前永远买 API。

**30 秒答**｜三判据：
①**量小或波动大**：日均活跃低、峰值尖、潮汐明显 → 自建要为峰值买卡，全天利用率不到 20%；
②**模型还在换**：业务没定型的试错期，每换一次模型自建侧要重做部署与评测；
③**没有运维承接**：客户没有能守夜的人，自建=把事故风险写进合同。
**判断线**：这句话是 SA 的**可信度杠杆**——敢在别的题上拼命推私有化的人，在这题上说"别自建"，客户才信你。

**弹药**
- 利用率反算：报"自建回本需要的最低日均调用量"，客户一听自己量级就懂了
- 折中方案：先用 API 起量，把**真实 token 曲线**跑三个月，再按实测外推私有化规模
- 私有化的非成本理由：数据不出域、离线/专网、自主可控、时延（边缘）——这几条不受账本约束，要单独讲

**红线**｜❌ 因为 KPI 在私有化上就硬凹自建方案；❌ 不算利用率就说"自建便宜"。

## 5. 推理成本超预算 3 倍，你的诊断路径和优化建议？

**一句话**｜先诊断再优化——**三张表**定位是哪一层漏水，再按阶梯收敛，不许上来加机器。

**30 秒答**｜诊断三张表：
①**利用率表**：GPU 利用率 vs MFU。利用率低 = 调度/批处理问题；利用率高但 MFU 低 = kernel/并行问题；
②**请求分布表**：长上下文占比、重复前缀占比、失败/重试占比；
③**批处理效率表**：实际并发 batch 大小、是否被 `max-num-seqs`/显存水位卡住。
优化阶梯（按性价比排序）：**前缀缓存 → 量化 → 连续批处理参数调优 → PD 分离 → 模型路由**。
**判断线**：优化上限是**硬件理论吞吐**，讲得出 MFU 对标才显得专业——
不是"还能再省 50%"这种话，而是"当前 MFU 12%，同类模型 H20 上做到 25% 是合理目标"。

**弹药**
- 最常见的隐形浪费：所有请求都带同一个长系统提示词却**没开前缀缓存**；重试风暴（超时阈值配太紧）
- 模型路由的收益来源：**简单任务走小模型**（改写/抽取/分类根本不需要旗舰模型）
- 成本单位统一：全部换算成 **元/千 token** 或 **元/单次业务**，跨方案才能比

**红线**｜❌ 上来就"加点卡"；❌ 一个利用率数字都报不出来就给优化建议。

## 6. 客户要建推理集群：网络、存储、拓扑怎么选？

**一句话**｜推理的网络压力比训练小一个量级，但**模型分发（存储）**和 **KV 传输（PD 分离）**是两个隐藏要求。

**30 秒答**｜
**网络**：同机 TP 走 NVLink，跨机才要 IB/RoCE；常规组网对纯推理够用，但一旦上 **PD 分离**，KV 跨卡传输就是高带宽硬要求（IB/RDMA 级）。
**存储**：看**模型分发**——几百 GB 权重要做到秒级加载，靠并行文件系统 + 本地缓存预热；以及业务数据（日志/向量库）。
**拓扑**：拓扑感知调度——NVLink 域内优先、跨机带宽分层、网卡与 NUMA 配对。
**判断线**：先问"要不要跨机"。能单卡/单机放下的模型，不要买 IB——**为不存在的约束付钱**是这类方案最常见的浪费。

**弹药**
- 大权重加载：冷启动分钟级 → 本地 NVMe 缓存 + 预热，否则滚动发布根本做不动
- 网络分层量级感觉：NVLink 数百 GB/s ≫ PCIe 双向 ~50GB/s ≫ 25GbE；IB/RoCE 100–400Gb 级
- 存储带宽算式：`权重 GB ÷ 可接受加载秒数 × 并发节点数` = 需要的聚合读带宽

**红线**｜❌ 推理集群照搬训练组网不考虑成本；❌ 不考虑模型分发带宽就定发布方案。

**下一问**｜"训练和推理混部呢？"（→ 本卡 #7）

## 7. 训推混部，怎么设计？

**一句话**｜潮汐错峰 + 优先级抢占 + 显存隔离，**利用率能上去，但运维复杂度显著增加**——trade-off 要讲全。

**30 秒答**｜
白天推理高峰让训练退避，夜里推理低谷把卡给训练（潮汐错峰）；
训练任务用低 PriorityClass，可被推理抢占；隔离用 MIG/独立实例或整卡切换（**大模型训练基本无法与推理共享一张卡的显存**）。
**判断线**：给客户的收益必须是**卡数**——例如"白天 128 卡全推理、夜里 96 卡转训练，等效于多买 X 张卡"。
但训练 checkpoint 与抢占的交互是硬约束：训练被杀必须能**断点续训**，否则混部省的钱不够赔一次白跑。

**弹药**
- 必须的前置能力：训练侧 checkpoint 频率 + 自动恢复；调度侧 gang 语义（不能半批被抢）
- 常见坑：抢占发生在 epoch 中间 → 已烧的算力作废；checkpoint 太密又拖慢训练
- 隔离三档：物理分池（最稳，利用率最低）→ 时间复用（潮汐）→ MIG 显存级（粒度最细，训练侧基本不适用）

**红线**｜❌ 只讲收益不讲隔离风险；❌ 没确认训练能断点续训就答应混部。

**下一问**｜"K8s 上跑 GPU 推理，调度和配额怎么治理？"（→ 本卡 #8）

## 8. K8s 上跑 GPU 推理：调度、配额、碎片怎么治理？

**一句话**｜GPU 不能当普通资源调度——**拓扑、gang、双维度资源模型**三件事是 CPU 池没有的心智。

**30 秒答**｜
**调度**：拓扑感知（NVLink 域内优先、网卡与 GPU 亲和）+ **gang scheduling**（多卡请求必须原子调度，否则一半卡被占、另一半等不到 → 死锁空烧）；
**配额**：按团队 ResourceQuota + PriorityClass（生产 > 实验）+ **quota 回收机制**（申请了不用的要收）；
**碎片**：小规格请求（1 卡、2 卡）打散大卡池，导致 8 卡请求永远排不满 → 定时治理 + 潮汐回收。
**判断线**：**卡数 + 显存双维度**建模。只按卡数配额，一个占满显存的请求和一个空跑的请求在你账上是等价的——这是"明明有卡却起不来"的根因。

**弹药**
- gang 死锁的经典形状：两个 TP=8 任务各拿到 4 张卡互相等；`min-available`/`pod-group` 语义缺失
- 碎片治理：给 8 卡整机请求**预留独占池**，小请求走可拼池，别混在一张调度表里
- 差异化护城河：3 年 ACK 经验可以直接讲——GPU 资源池运维与 CPU 池的核心差异就在拓扑与 gang
- 现场可查：`kubectl describe node` 看 allocatable nvidia.com/gpu；`nvidia-smi topo -m` 看亲和矩阵

**红线**｜❌ 把 GPU 当普通标量资源；❌ 说不出碎片是怎么产生的（只会说"排队等一下"）。

## 9. 多租户推理平台：配额、优先级、隔离怎么设计？

**一句话**｜混合制——核心租户独立实例保 SLA，普通租户共享池 + 严格配额 + 单租户并发上限。

**30 秒答**｜隔离层级从轻到重：**实例级**（物理隔离，成本最高）→ **配额级**（token/并发限流 + 优先级队列）→ **时间片**（抢占）。
线上最佳实践是混合：核心业务独占实例，长尾共享池，共享池里**必须有单租户并发上限**——否则一个租户的批量任务就能把全场拖死。
**判断线**：饿死问题本质是**限流设计问题**，不是调度问题。调度只能排队，队列没有配额加权就必然饿死。

**弹药**
- 公平性算法：按 quota **加权的公平队列**（WFQ）/ max-min 公平（DRF 思想），说得出名字并解释"按配额加权而非按到达顺序"
- 三层配额：并发数（防瞬时打满）+ token/min（控吞吐份额）+ 日/月总量（计费与预算）
- 数据隔离：上下文不跨租户、审计日志留痕；**计量透明**（token 级账单）是多租户平台的信任基础

**红线**｜❌ 所有租户一个池没配额；❌ 隔离方案完全没算成本（"全独占最安全"客户预算不答应）。

## 10. 算力受限环境（昇腾 + 数据不出域），部署方案怎么设计？

**一句话**｜分层评估 + **POC 实测**——模型层、引擎层、应用层各自核适配度，绝不拍胸脯说"无缝迁移"。

**30 秒答**｜
①**模型层**：Qwen 系列对昇腾适配最好，其他模型要看有没有官方适配版；
②**推理引擎层**：vLLM-Ascend / MindIE 的适配现状，**算子覆盖度逐个核**（尤其新架构、MoE、投机解码这类激进特性往往落后）；
③**应用层**：CUDA-only 组件（某些向量库、自定义 kernel、加速库）找替代或 CPU 化，给出**明确迁移清单**。
**判断线**：先小规模实测目标模型的**吞吐 + 精度**，再定规模。生态差距要诚实告知——
不说差距，等客户在生产上踩到，责任全在方案方。

**弹药**
- POC 验证清单：目标模型能否加载 → 精度对比（golden set 回归，不是看 loss）→ 实测吞吐/延迟 → 稳定性（长稳 + 故障恢复）
- 降级预案：核心链路全国产，非核心组件用替代方案/CPU 兜底；**别把整体可用性挂在一个未验证的适配上**
- CUDA-only 组件处置三选一：找国产等价物 / 改造成 CPU 路径 / 移出主链路（异步旁路）

**红线**｜❌ 说"完全兼容无缝迁移"；❌ 没有 POC 环节就直接给规模方案。
