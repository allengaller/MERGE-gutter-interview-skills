# 卡 · 引擎部署与五阶段排障

> 拿到一个**没见过的模型**怎么在几天内私有化上线。**面试官只关心一件事：你有没有阶段化方法论，还是只会把报错粘给搜索引擎。**
> 每题都是 `一句话 → 30 秒答 → 弹药 → 红线 → 下一问` 五段，直接照念。

---

## 1. 客户一周内要私有化上线一个刚发布的新模型，你怎么做？

**一句话**｜按五阶段推：**下载 → 引擎 → 显存并行 → 加载运行 → 服务化**，每阶段先写检查项再动手。

**30 秒答**｜第一步不是拉模型，是**读 release notes 找引擎版本门槛和硬件支持矩阵**——新架构必须有新引擎，
版本不够连加载都进不去。然后按阶段推进，每阶段一个"确认没问题的动作"：
下载完校验分片数量/hash；引擎装完先 dry-run 加载配置；显存算清 TP 和 KV 预算；
加载阶段做预热请求区分"编译中"和"真 hang"；服务化最后压 chat template 和 tool_calls。
**判断线**：能报出"我预判每阶段会出什么问题"就是高级，只会"报错了我再查"就是中级。

**弹药**
- 五阶段口诀：**下 / 引 / 存 / 载 / 服**
- 开工前四查：模型 repo ID、引擎最低版本、GPU 架构支持矩阵、磁盘余量
- 交付形态：`--tensor-parallel-size` + `--max-model-len` 起步值 + 压测放开节奏
- 上线判据：先小上下文灰度，长上下文单独压

**红线**｜❌ 上来就 `pip install vllm` 最新稳定版赌运气；❌ 只说"照着文档跑"，说不出阶段化预案。

**下一问**｜"权重下到一半断了，续传后加载报 safetensors header corrupt，怎么回事？"

## 2. 加载时报 `safetensors header corrupt`，但下载显示已完成

**一句话**｜**断点续传留下了损坏分片**——下载工具的"完成"不等于字节完整，必须先校验再进引擎。

**30 秒答**｜大模型是几十个到上百个分片，任何一个坏掉都会在加载时报 header 错，
而报错**不会告诉你是哪个文件**。所以处置是：拿 download 输出的分片清单核对**数量、每个文件大小、hash**，
把不一致的分片单独重下。第二步查磁盘——**空间不足经常伪装成别的错**（写到一半没地了）。
**判断线**：hash 全对但还报 corrupt → 怀疑存储层（网络文件系统缓存/坏道），不是下载层。

**弹药**
- 320B 级 MoE BF16 权重约 **640GB**、**约 141 个分片**——预留时按权重 + 临时/解压空间算
- 校验来源：ModelScope 下载清单，或 `config.json` 里的分片索引（`model.safetensors.index.json`）
- `df -h` + `du -sh` 双查；容器里挂载点满会报成加载错
- 大文件下载用支持校验/续传的工具，**不要用 curl 手搓**

**红线**｜❌ "重下一遍试试"——141 个分片重下几百 GB，是把 5 分钟问题变成半天事故。

## 3. 下载前三查是什么？拉错型号的后果？

**一句话**｜**组织名 + 大小写 + 型号**三查——拉错型号是多下几百 GB，把磁盘和排障时间一起干爆。

**30 秒答**｜ModelScope/HF 的 ID 是 `组织/模型名`，组织名写错直接 404；
型号写错更贵——同一系列里往往有参数量差一倍的兄弟型号（比如 "Flash" 版和全量版），
拉下来才发现装不进、还得回滚重下。所以我会把**模型 ID 和期望大小写进部署单**，
下载完第一件事是比对实际占用与预期（比如 BF16 权重 ~640GB），偏差超阈值立刻停。
**判断线**：说出"我按预期字节数卡一道闸"就是生产经验，说"我看着名字挺像"就是踩坑预定。

**弹药**
- `zai-org/GLM-5.3-Flash` —— 组织名 `zai-org`，大小写敏感，型号带 `-Flash`
- 兄弟型号误拉：743B 级别，比目标多几百 GB
- 预期大小速算：**参数量(B) × dtype 字节数** ≈ 权重 GB（BF16 = 2 字节 → 320B ≈ 640GB）
- 部署单里记：模型 ID、revision/tag、权重总大小、分片数、引擎版本

**红线**｜❌ 把 "Flash" 理解成"小模型"，按单卡/双卡规划——**Flash 指激活参数少、单 token 快，权重照样几百 GB**。

## 4. 报 `Model architectures [...] are not supported`

**一句话**｜**新架构要新引擎**——这是版本门槛问题，不是配置问题，改参数没用。

**30 秒答**｜报错含义很明确：当前引擎的架构注册表里没有这个 `architectures`。
第一步去模型卡/release notes 找**官方声明的引擎最低版本**（比如 vLLM ≥ 0.28.0 / SGLang 最新版），
第二步连带确认 `transformers` 版本能解析新 config 字段（稀疏注意力、多 token 预测这类新结构常有新字段）。
升级引擎后**必须重跑一次最小加载**，因为新引擎的 kernel、量化算子、并行实现都变了。
**判断线**：如果 release notes 里没写版本要求 → 按"未验证"处理，先在测试机验证，不要在客户生产环境赌。

**弹药**
- 版本门槛来自**模型发布方的 release notes**，不是来自你的 pip 源
- 同批要核：`vllm` / `sglang` / `transformers` / `torch` / `flashinfer` / `triton`
- 查架构名：`config.json` 里的 `architectures`，与引擎 support 列表比对
- 升级后回归项：加载成功、首 token 延迟、tool_calls 解析、精度抽查

**红线**｜❌ 搜报错文本找 workaround、或去改 `--trust-remote-code` 试图绕过——架构不支持就是不支持。

## 5. vLLM 和 SGLang 装进同一个虚拟环境，一个跑得好一个崩

**一句话**｜**依赖互相覆盖**——两个引擎都钉 `torch` / `triton` / `flashinfer`，后装的把先装的顶掉。

**30 秒答**｜这类引擎不是纯 Python 库，带编译期绑定的 CUDA kernel。
装 B 的时候 pip 会解一套不同的依赖闭包，`torch` 小版本、`triton`、`flashinfer` 被换掉，
A 的二进制就与新版本不匹配——表现是**A 崩在加载或首个前向**，报错还指向 CUDA/kernel，看不出是环境问题。
正确做法：**一个推理引擎一个环境（或一个镜像）**，用容器隔离，对比测试时两个镜像同一模型同一参数跑。
**判断线**：`pip check` 有冲突、或两个引擎的 `torch` 版本不一致 → 就是这个问题。

**弹药**
- 高危冲突项：`torch`、`triton`、`flashinfer`、`xformers`、`transformers`
- 隔离粒度：每引擎一个 venv，生产上**每引擎一个镜像**（依赖树 + CUDA 基座一起定版）
- 快速验证：`python -c "import torch; print(torch.__version__, torch.version.cuda)"` 在两个环境各跑一次
- 镜像里记 CUDA / driver 版本要求（driver 版本是宿主机的，别写进容器当事实）

**红线**｜❌ 在同一个环境里"降级一下再试试"来回倒腾——依赖矩阵一旦乱掉，之后所有故障都定不了界。

**下一问**｜"客户工程师想在 Mac 上跑，报 No supported GPU found，你怎么解释？"

## 6. 客户要在 Mac / 非 NVIDIA 卡上跑，报 `No supported GPU found`

**一句话**｜**推理引擎生态决定了硬件边界**——vLLM/SGLang 只走 NVIDIA CUDA，不是"模型不大就能跑"。

**30 秒答**｜这两个引擎的核心价值（PagedAttention、连续批处理）都是 CUDA kernel，
Apple Silicon 上没有对应实现，只能走 llama.cpp / MLX 这类 CPU/Metal 路线。
但要提醒客户那是**另一条路的账**：即便是官方量化版（如 1.x-bit 的 UD 系列），320B 级也要 **100GB+ 内存**，
Mac Studio 勉强能起，性能与并发完全撑不起生产。所以我的答复是：
Mac 只能作为**功能验证/演示**环境，不能进 SLA 讨论；要生产要么 NVIDIA 集群，要么走云端 API。
**判断线**：先分清客户是要"看看效果"还是"要上量"——两者的硬件结论完全不同。

**弹药**
- 引擎硬件面：vLLM/SGLang → CUDA；昇腾 → vLLM-Ascend / MindIE；Apple → llama.cpp/MLX
- 内存量级速算：量化到 ~1bit/参数时 320B ≈ 数十 GB 权重 + KV + 运行时，**100GB+ 才敢谈**
- "官方量化版" ≠ "能跑生产"：精度、并发、上下文三项都要单独验
- 汇报话术：把"能不能跑"和"能不能撑住 SLA"拆成两个问题回答

**红线**｜❌ 说"内存够就行"或"这个模型不大"——丢了并发、KV 显存和延迟三个约束。

## 7. 服务正常启动，第一个请求 5 分钟没返回

**一句话**｜大概率是**新 shape 触发 JIT 编译**，首 token 极慢是已知现象——但要证明它"在动"而不是"卡死了"。

**30 秒答**｜新架构/新 shape 会在首次遇到某个 batch/序列长度组合时编译 kernel，
期间 CPU 和 GPU 都有活动、日志在推进，只是不出结果。
我的判断动作是两件事：**看日志有没有在编译推进 + 看 GPU 利用率/显存是否在变**。
两者都活 → 等着或换预热请求把常见 shape 先跑一遍；日志停摆且 GPU 0% → 按真 hang 处理（走 NCCL 排查）。
处置上生产必做：**上线前用一组预热请求打满常见长度**，别把首次编译留给真实用户。
**判断线**："慢"和"死"的处置完全相反——一个是等，一个是回滚，**必须先分诊再动手**。

**弹药**
- 预热：按典型输入长度（如 1K/4K/16K）各发几条，把 JIT 编译成本前置
- 抓证据：`nvidia-smi dmon -s um`（利用率/显存是否在动）+ 引擎日志时间戳
- hang 排查：`NCCL_DEBUG=INFO`、看是否卡在集合通信、超时参数
- 探针纪律：**不要用 liveness 探真实推理接口**，冷启动期没响应就把容器重启循环打出来

**红线**｜❌ 第一反应"重启服务"——重启后又要编译一遍，把 5 分钟变成每 5 分钟一次的循环。

## 8. 分布式推理服务的通用启动坑，有哪些固定检查项？

**一句话**｜四件套：**NCCL/shm、端口占用、ulimit 文件句柄、共享内存大小**——这些和模型无关，属于 SRE 该秒答的部分。

**30 秒答**｜多卡/多机推理起不来，先排最廉价的通用原因：
①`/dev/shm` 太小（容器默认 64MB 级别会让 NCCL/torch 通信失败，要 `--shm-size` 或 emptyDir `memory`）；
②端口被占或分布式初始化端口配置冲突；③文件描述符上限太低（多卡 + 大量分片句柄，默认 1024 不够）；
④NCCL 拓扑/网卡选择（多网卡机器上没指定通信网卡会走错口，性能塌一半或直接超时）。
这四条查完再去看模型和显存。**判断线**：报错里出现 `unhandled system error`、`No space left on device`（shm）、
`address already in use`、`too many open files` → 全是通用坑，不要往引擎版本上引。

**弹药**
- `ulimit -n`（生产常调到 65535+）、`df -h /dev/shm`
- K8s 落点：`emptyDir: {medium: Memory, sizeLimit: ...}` 挂 `/dev/shm`
- `NCCL_SOCKET_IFNAME` / `NCCL_IB_HCA` / `NCCL_DEBUG=INFO` / `NCCL_DEBUG_SUBSYS`
- `--ipc=host`（容器内多进程通信），端口用 `--master-port` / 分布式初始化端口显式给

**红线**｜❌ 把"容器 shm 太小"当成引擎 bug 去升级版本——环境层的问题要用环境层的手法治。

## 9. 投机解码 / MTP 这类多 token 预测怎么开？

**一句话**｜**必须显式开**，且配置格式随版本变——配错轻则不生效（白配），重则启动崩。

**30 秒答**｜带 MTP 头的模型不会因为"支持这个特性"就自动启用，要在启动参数里显式给投机解码配置
（如 `--speculative-config`）。这类参数有两个坑：一是 **schema 跨版本会改**，
老配置的 JSON 在新引擎里可能直接解析失败；二是**不生效是静默的**，
所以开完必须验证——看单请求的 decoded tokens/step 或吞吐是否真的变化，别只看"启动成功"。
收益也要讲清：投机解码提的是 decode 阶段吞吐/延迟，**对 prefill 重的长输入场景收益有限**。
**判断线**：能说"我验证它真的生效了"就是做过，只说"我加了这个参数"就是抄文档。

**弹药**
- 生效验证：吞吐/延迟对比（同参数同流量两版），或引擎日志里 draft/accept 相关计数
- 代价：draft 头占额外显存、接受率低时反而变慢——**接受率是关键指标**
- 版本纪律：投机解码配置**跟着引擎版本一起定版**，升级时列入回归清单
- 同类特性：前缀缓存/ RadixAttention、量化、chunked prefill——都遵循"开启 + 验证生效"两步

**红线**｜❌ 把所有加速开关一次全开再看"好像变快了"——无法归因，也无法回滚。

## 10. 服务化：`/v1/chat/completions` 通了但客户端解析失败

**一句话**｜**chat template 与输出格式不匹配**——工具调用、reasoning 字段、角色交替这三处是新模型最常见的服务化坑。

**30 秒答**｜引擎"能返回文本"不等于"接口契约对"。三查：
①**chat template 版本**——新模型的工具调用/特殊 token 格式常和通用模板不兼容，
模板要从模型仓库取（往往需要 `trust_remote_code`）；②**非标字段**——推理类模型把思考内容放在
`reasoning_content`，客户端只读 `content` 就会拿到空串，字段契约要跟客户端一次性对齐；
③**角色交替约束**——部分模型要求 user/assistant 严格交替、system 位置固定，客户端拼历史时合并角色就报错。
流式还要单独压：断连、增量拼接、`[DONE]` 语义。**判断线**：换一个官方客户端能通、自研不通 → 是客户端适配，不是服务端。

**弹药**
- 模板来源：模型仓库的 `tokenizer_config.json` / `chat_template`，与服务端引擎版本一起定版
- 字段差异清单：`content` / `reasoning_content` / `tool_calls` / `usage`
- 多模态：官方若把模型归在 VLM 类，用到视觉时有 processor 与 `--allowed-modalities` 一类配置错
- 契约测试：把 tool_calls、流式、超长输入、并发四类各写一条固定用例，每次上线跑

**红线**｜❌ 让客户端"先把 reasoning_content 忽略掉凑合用"——业务看到的是模型不干活，排查成本全甩给推理侧。
