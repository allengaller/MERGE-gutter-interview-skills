# 卡 · 故障与稳定性

> 面试官的三个问号之二：**线上炸过你怎么排？** 这类的判据是"有没有把 GPU 集群当**异构易损系统**运维"。
> SRE 背景在这类题是**主场必须拿分**——只会重启大法直接降级。

---

## 1. 线上推理延迟突然涨 3 倍，你的排查顺序？

**一句话**｜**先看是全部请求慢还是长请求慢**——这一步分开"容量/流量问题"和"系统故障问题"，后面所有动作由它决定。

**30 秒答**｜①按长度分桶看 TTFT/TPOT 分布：只有长上下文那桶涨 → 流量结构变了（有人贴超长输入），
处置是长度分池 + 请求长度限制；全桶一起涨 → 往下走。
②看排队与并发：`running/waiting` 请求数、抢占次数 → 排队涨说明**容量不够或 batch 塌了**，不是"卡坏了"。
③看显存水位与 KV 使用率 → 是否触顶引发重算。④看节点维度：**是不是只有某几张卡/某个节点慢**（慢节点是最典型的 3 倍延迟来源）。
⑤查最近变更：引擎版本、驱动、模型、流量配置。
**判断线**：能按"全局 vs 局部"和"容量 vs 故障"两个二维切分着说，就是排过；只会罗列命令就是没排过。

**弹药**
- 第一刀永远是**分组对比**：按节点 / 按模型版本 / 按输入长度桶 / 按租户
- 关键指标：TTFT、TPOT、running/waiting、抢占次数、KV 使用率、`nvidia-smi` 利用率与显存
- 慢节点证据：同拓扑域内该节点延迟分位显著高于其他 → 摘流量再验证
- 变更关联：延迟拐点时间戳 ± 变更窗口，一眼定嫌疑人

**红线**｜❌ 上来"重启服务/加卡"；❌ 只看平均延迟（平均值会被长度分布变化骗）。

**下一问**｜"重启没解决，显存水位一直在顶，报 CUDA OOM——怎么查？"

## 2. CUDA OOM：服务跑着跑着显存爆了

**一句话**｜OOM 的三类原因：**长上下文尖峰、批过大、显存碎片**——先看水位曲线形状再定性。

**30 秒答**｜看曲线是**阶跃**还是**爬升**：
阶跃（某个时刻突然打满）→ 有超长请求或大 batch 进来，处置是**限制单请求最大长度 + 限制并发 + 降级拒绝**；
缓慢爬升后爆 → 泄漏/缓存无上限（前缀缓存不淘汰、KV offload 队列堆积、宿主侧进程），
处置是重启止血 + 定位增长点。还要区分"**真不够**"和"**被挤了**"：
`gpu-memory-utilization` 预算给小了会报分配失败但实际有余量，反之给满了会把通信 buffer 挤没。
止血顺序：降 `--max-model-len` → 降并发 → 调 utilization → 加副本，**每步都可回滚**。
**判断线**：报"预留水位 + 请求长度限制 + 优雅降级"这三件预防动作，就是管过线上。

**弹药**
- 定位碎片：`torch.cuda.memory_summary()` / 引擎暴露的 KV 分配指标；显存"有空隙但装不下"是碎片特征
- 分配失败 ≠ 用满：日志里看**申请了多少、还剩多少连续空间**
- 预防三件套：**预留水位（如峰值不超过 90%）+ 单请求长度硬限 + 超长降级路径**
- 别忘宿主侧：同节点其他进程（exporter、sidecar、监控 agent）也在吃显存/内存

**红线**｜❌ "把 utilization 调高一点就好了"——分不清是容量问题还是尖峰问题，下次以另一种方式再炸。

**下一问**｜"整池都健康，但个别请求特别慢——怎么系统性发现慢节点？"

## 3. 慢节点（straggler / slow node）怎么发现、怎么止损？

**一句话**｜**按节点维度的延迟分位监控 + 自动摘除**——同步并行下一个慢节点会拖垮整批任务。

**30 秒答**｜同步数据并行/集合通信的语义是"等最慢的那个"，所以慢节点不是"它自己慢"，而是"**全场慢**"。
发现靠三层：①**每节点延迟分位**（同负载下 P99 显著高的离群节点）；②**硬件信号**（ECC 错误计数、降频、XID）；
③**通信质量**（RDMA/IB 抖动、重传、CRC 错误——网络劣化造成的慢节点最容易被误判成 GPU 问题）。
止损是**自动摘除**：打标签隔离 → 摘流量 → 观察同域其他节点是否恢复（这一步同时验证了归因）。
**判断线**：能说出"先隔离再验证，隔离后全场恢复就证明是它"这个闭环，就是做过集群运维的人。

**弹药**
- 硬件侧：`nvidia-smi -q -d ECC,PERFORMANCE`（ECC/降频/温度）、`nvidia-smi dmon`（持续采样）
- 通信侧：`NCCL_DEBUG=INFO`、IB/RoCE 计数器（`perfquery`、网卡 error/discard 计数）
- 降频常见原因：**温度墙 / 功率墙**（温度、功耗上限），以及 ECC 触发后的保守降速
- K8s 落点：节点 label + taint 隔离，配合 gang scheduling 避免半调度死锁

**红线**｜❌ 只看集群平均指标（离群点被平均掉）；❌ 把"网络劣化导致的慢"当"卡坏了"去换卡。

**下一问**｜"任务直接不动了，日志停摆——NCCL hang 怎么排？"

## 4. NCCL hang：多卡/多机任务卡死不动

**一句话**｜**hang 不是慢，是集合通信凑不齐**——先分段验证链路，别改超时参数掩盖问题。

**30 秒答**｜hang 的两种形状：**某 rank 卡在自己的计算/IO 上**（其他 rank 在等它）
和**通信本身不通**（网络/驱动/拓扑）。
排查顺序：①`NCCL_DEBUG=INFO` + `NCCL_DEBUG_SUBSYS=INIT,NET,COLL` 看卡在哪个通信器和哪一步；
②确认是不是**所有 rank 都到了同一个 collective**（一个 rank 提前退出 → 全场 hang，这是最常见的伪通信故障）；
③分段验链路：节点内 P2P/NVLink、机间 IB/RoCE（逐层 ping/ib_write_bw）；
④查驱动/CUDA/NCCL 版本组合与超时参数。
止血：**任务级重试 + 故障节点隔离**（不要整体大回滚，也别只是重启同一台坏机器）。
**判断线**：先问"是所有 rank 都 hang 还是只有一个没到"，这个分诊顺序就是功力。

**弹药**
- 常规定位三查：**IB 链路 / 驱动与 NCCL 版本 / 超时参数**
- 一个 rank 崩了不退出 → 其余 rank 永久等待：**要有 rank 级健康探测与任务超时熔断**
- `/dev/shm` 过小会让 NCCL 起不来（表现为 hang/系统错误），别当成通信故障
- 弹性设计：训练侧用**断点续训 + 节点隔离 + 任务级重试**；推理侧用副本级摘除

**红线**｜❌ 调大 `NCCL_TIMEOUT` 当解决方案——把 hang 变成更久的 hang，故障还在。

## 5. XID 错误 / ECC / 掉卡，怎么变成自动处置？

**一句话**｜**XID 是 GPU 的内核级错误码**——按码分级：可忽略的计数、需观察的降频、必须隔离的掉卡。

**30 秒答**｜GPU 侧故障不像 CPU 那样只有"活/死"两态，它有一堆**亚健康态**：
ECC 可纠正错误累积、不可纠正错误、显存页退役、降频、掉卡（卡从 PCIe 消失）。
`dmesg` / `nvidia-smi -q` 里的 **XID** 编号是分类依据，工程做法是建一张映射表：
哪些 XID → 继续观察；哪些 → 隔离节点并通知更换；哪些 → 立即驱逐任务。
配合 **ECC 错误率阈值**和**页退役计数**做趋势告警，不要等掉卡才动。
**判断线**：能讲出"GPU 是易损件，要按错误码分级自愈，不是等人看"就是管过卡。

**弹药**
- 观测面：`dmesg | grep -i xid`、`nvidia-smi -q -d ECC,ROW_REMAPPER`、`nvidia-smi --query-gpu=...`
- 三类典型：**掉卡**（枚举不到，重启或换件）、**ECC 不可纠正**（隔离）、**降频**（查温度/功率墙）
- MIG 的价值与坑：切分提升小任务利用率，但**故障域也一起切**，且不是所有场景都能接受
- 自愈闭环：错误码 → 打 taint → 任务重调度 → 工单 → 硬件更换，**全程无人值守**

**红线**｜❌ 没听过 XID（这是 GPU 集群运维的入场券）；❌ "重启一下就好了"当作处置策略。

## 6. GPU 集群监控四件套是什么？

**一句话**｜**显存 / 算力利用率（MFU）/ 延迟分位数 / XID 错误**——四项缺一都算没建完。

**30 秒答**｜这四件套对应四类故障，各自不可替代：
**显存水位**抓 OOM 与 KV 挤占（含碎片）；**算力利用率 + MFU**抓"看着忙其实浪费"；
**延迟分位（TTFT/TPOT，按节点/按版本/按长度桶）**抓慢节点、长尾和发布回退；
**XID/ECC**抓硬件亚健康。
再加两项我会坚持：**抢占/排队次数**（容量健康度）和**前缀缓存命中率**（成本效率）。
关键是**全部按节点和按卡打标签**——没有维度就没有离群分析，平均值会骗人。
**判断线**：说出"必须按节点维度切，否则慢节点发现不了"，就把监控设计和排障能力连起来了。

**弹药**
- exporter：DCGM exporter（NVIDIA 指标进 Prometheus）+ 引擎自带指标（吞吐/延迟/队列/KV）
- 告警分级：**Critical** = 掉卡/服务不可用/SLO 燃烧；**Warning** = ECC 累积、延迟离群、水位 85%；**Info** = 命中率下降、碎片趋势
- 每卡维度是刚需：`container_accelerator_*` / `DCGM_FI_*` 系列带 GPU id
- 与业务指标闭环：token 成本 / 每请求成本，是 CFO 视角的那一层

**红线**｜❌ 只监控"服务在不在"和"卡有没有"——GPU 集群 80% 的故障是**亚健康和长尾**，不是宕机。

## 7. 100 卡以上集群，怎么系统性防而不是靠人盯？

**一句话**｜把 GPU 当**异构易损系统**做运维：**准入体检 + 运行期自愈 + 变更可控 + 故障预算**。

**30 秒答**｜四件事按层次做：
①**准入**——新节点/维修后节点先跑体检（通信带宽、算力、ECC、长时烤机），不过关不进池，避免"上线即慢节点"；
②**运行期自愈**——错误码→隔离→任务重调度全自动，配合任务级重试和断点续训，把人从"救火"里拿掉；
③**变更可控**——驱动/CUDA/引擎按节点分批灰度，**同一池内版本漂移要有上限**，
且每批都看延迟分位再晋级；④**故障预算**——按"每天坏多少张卡"做容量冗余，把故障当常态算进账。
**判断线**：能报出"准入体检 + 灰度上限 + 故障预算"这三条，就是管过大规模集群的口径。

**弹药**
- 体检项：`nccl-tests`（all_reduce 带宽对标）、单卡算力基线、ECC 清零、72h 烤机
- 自愈分级：任务级重试 → rank 级重启 → 节点隔离 → 硬件更换（对应不同止损粒度）
- 版本矩阵：driver / CUDA / NCCL / 引擎 / 模型，**五元组**受控，禁止无记录漂移
- 故障预算换算：若 100 卡日均坏 1–2 张，冗余 1.3–1.5 要能覆盖隔离后的容量缺口

**红线**｜❌ 靠值班同学盯监控大屏；❌ 驱动升级一把梭全集群（版本漂移导致的 hang 最难查）。

## 8. 多租户推理平台：一个租户把集群打满怎么办？

**一句话**｜**这是限流设计问题，不是容量问题**——单租户并发上限 + 优先级队列 + 弹性配额。

**30 秒答**｜隔离从轻到重三档：**实例级**（物理隔离，最贵，给核心租户保 SLA）、
**配额级**（token/并发限流 + 优先级队列）、**时间片**（抢占）。
线上最佳实践是**混合制**：核心租户独立实例，普通租户共享池但**严格配额 + 单租户并发上限**（防打满），
闲时把闲置配额借出（弹性配额），计量按 token 出账透明化。
饿死问题的正解是**按 quota 加权的公平队列**（WFQ/DRF 这类思路），不是"排队先到先得"。
数据面还要独立：上下文不跨租户、审计日志齐全。
**判断线**：主动报"隔离方案的成本"——只讲隔离不讲成本，SA 面试直接降级。

**弹药**
- 三层配额：**QPS/并发 → token 预算（每分钟/每天）→ 显存或卡数池配额**
- 优先级：生产 > 实验，抢占要能被抢占者感知（重试而非静默丢）
- K8s 落点：ResourceQuota + PriorityClass + 配额回收；Kueue/自愿批量调度做队列
- 观测：每租户的 P99、排队时长、被限流比例——**公平性要能被证明**

**红线**｜❌ 所有租户一个池没配额；❌ 隔离方案完全没算成本（"给每个团队独立集群"= 利用率塌方）。

## 9. 服务能起但大面积失败/返回空，先看哪三样？

**一句话**｜**先看是不是"格式错"而不是"服务错"**：chat template 版本、非标字段（如 `reasoning_content`）、后端是否真的在返回。

**30 秒答**｜客户端大面积异常但引擎健康度指标正常时，我按这个顺序切：
①**契约**——用最小客户端（curl）直接打 `/v1/chat/completions`，能通就是客户端解析问题（工具调用格式、字段位置、角色交替约束）；
②**版本**——引擎或模板刚升级过？模板与客户端适配层要一起定版；
③**真实返回**——流式场景要单独看，增量拼接、断连、`[DONE]` 语义任一处不一致都会表现成"返回空"。
**判断线**：能说出"我先用 curl 绕过客户端证明服务端健康"这一刀，就是排障老手。

**弹药**
- 502/504 vs 200-空内容：**网关层**问题和**契约层**问题的分界线
- 探针纪律：**liveness 不要探真实推理接口**（冷启动 JIT 期会被误杀成 CrashLoop）
- 灰度必带：新旧版本共存期，客户端要能按 header/版本区分行为
- 契约回归：tool_calls / 流式 / 超长输入 / 并发四类用例进 CI

**红线**｜❌ 一报错就回滚模型版本——分不清契约问题还是容量问题，回滚也不解决。

**下一问**｜"回滚能解决的话，你的引擎升级怎么灰度？"（→ `卡/上线与评测.md`）
