# 卡 · 显存与并行

> 这一类的**唯一评分标准**：显存账算不算得清。面试官会追问"这个数字怎么算出来的？"
> 心法一句话：**权重是地板，KV 是天花板**——地板决定最少几张卡，天花板决定能开多长、并发多大。

---

## 1. 8×H20（141GB/卡）部署 320B MoE，TP 给多少？

**一句话**｜**TP=8**。权重 ~640GB ÷ 141GB ≈ 4.5 卡只是**下限**，加上 KV 和激活余量就得打满 8 卡。

**30 秒答**｜先算地板：BF16 权重 = 参数量 × 2 字节 ≈ 640GB，8 卡总显存 1128GB，
除出来 4.5 卡是"只装权重"的理论下限。但推理进程还要 KV cache、激活值、CUDA context 与碎片余量，
按 4.5 卡排必炸在加载或首批请求。所以直接 TP=8 把权重摊薄，剩余空间全给 KV。
再往上还有 MoE 专属的优化空间：专家并行（EP）/ 数据并行混合，但要当前版本的 kernel 支持，
**属于"知道有这条路、上线先走稳的那条"**。**判断线**：能主动说出"4.5 是下限不是目标"就是懂显存账。

**弹药**
- 心法：**权重是地板（决定最少卡数）、KV 是天花板（决定长度 × 并发）**
- 速算：BF16 ≈ 参数量(B) × 2GB；FP8/INT8 ≈ ×1；W4 ≈ ×0.5
- H20 单卡 **141GB**，8 卡 1128GB；剩余显存基本全给 KV pool
- MoE 特性：**320B 总参 / 18B 激活**——激活量小所以单 token 快，但**权重仍需全量驻留显存**

**红线**｜❌ 把 "Flash / MoE 激活少" 当"模型小"，按单卡或双卡规划——这条直接判不通过。

## 2. MoE 激活参数只有 18B，为什么显存还按 320B 算？

**一句话**｜**激活只影响算多少，不影响存多少**——路由到哪几个专家是运行时决定，所有专家权重都必须常驻。

**30 秒答**｜Dense 模型每 token 用全部参数，MoE 每 token 只走少数专家（这里 18B），
所以**计算量和带宽压力小 → 单 token 快**。但你无法预知下一个 token 路由到哪个专家，
把专家换成 CPU/SSD 换入换出的代价远高于显存本身，所以推理引擎的默认做法是**全量专家权重驻留显存**。
结论：MoE 省的是**算力/延迟**，Dense 才更接近"参数量 ≈ 显存量"的直觉。
这也解释了 MoE 的另一条优化路：EP（专家并行）把不同专家放不同卡，用**通信换显存**。
**判断线**：说清"省算力不省显存"这一句，这题就过了。

**弹药**
- 计算侧收益：单 token FLOPs ≈ 激活参数量决定 → decode 阶段明显快于同总参 Dense
- 显存侧代价：专家权重大头常驻，KV 之外几乎没省
- EP/DP 混合的价值：把专家分布到多卡降低单卡权重压力，代价是 all-to-all 通信
- 通信敏感点：EP 的收益要看**卡间带宽（NVLink 域内 vs 跨机）**

**红线**｜❌ 说"MoE 所以显存只需要按 18B 算"——这是全场最致命的一句话。

## 3. 报 `max seq len is larger than the maximum number of tokens that can be stored in KV cache`

**一句话**｜**按标称 1M 上下文预留 KV，显存直接爆**——先用 `--max-model-len 32768` 起步，压测后再放。

**30 秒答**｜引擎启动时要为最大长度预留 KV 预算：`max_model_len × 每 token KV 字节数`，
再乘上想支持的并发。模型标称 1M 不代表你有 1M 的显存——
这个量级下 KV 需要比权重大得多，所以启动就拒绝。
处置分两步：**先降 `--max-model-len` 让服务起来**（32K 是常见起步），
再按真实流量分布决定放开放多大——业务里 95 分位输入长度是多少，就把上限放在那个量级上方，
超长场景单独走一个实例池。**判断线**：能说出"降 max-model-len 是止血，按长度分池才是方案"就是高级。

**弹药**
- 起步命令：`--tensor-parallel-size 8 --max-model-len 32768`
- 放开顺序：32K 起 → 压测 → 128K → 1M 单独验证（**1M 官方自己都说未充分验证**）
- 长度分池：长上下文独立实例保护短上下文吞吐，避免一条超长请求拖垮整池
- 相关项：`--max-num-batched-tokens`（chunked prefill）、KV 量化、KV offload

**红线**｜❌ 直接 `--max-model-len 1048576` 然后调低 `--gpu-memory-utilization` 硬凑——KV 被挤到 0，服务能起但并发为 1。

## 4. KV cache 显存怎么估？现场给个算法

**一句话**｜`2 × layers × kv_heads × head_dim × dtype_bytes × seq_len × batch`——**K 和 V 各一份所以乘 2**。

**30 秒答**｜每个 token 在每一层要存 K 和 V 两段向量，所以单 token 单层的字节数是
`kv_heads × head_dim × dtype_bytes`，再乘层数、乘 2（K/V），乘上下文长度就是**一条请求的 KV**，
乘并发就是**这一池需要的 KV 总量**。参数具体值查 `config.json`，不用背——
但**公式和量级感必须对**：长上下文是线性暴涨，32K → 1M 是 32 倍，
一条 1M 请求的 KV 可能吃掉整卡剩余显存。**判断线**：算完主动说一句
"所以显存不是看模型多大，是看我要同时接多少条多长的请求"。

**弹药**
- 公式：`2 × L × kv_heads × head_dim × bytes × seq_len × batch`
- 降 KV 的四条路：**GQA/MQA（更少 kv_heads）→ KV 量化（fp8/int8）→ 滑动窗口/截断 → KV offload**
- 反推并发：`(可用显存 − 权重 − 激活余存) ÷ 单请求 KV = 最大并发`，这就是"天花板"
- 治理指标：**KV cache 使用率 / 命中率（前缀缓存）/ 抢占（preemption）次数**

**红线**｜❌ 公式里漏掉 ×2、或把 `head_dim × num_heads` 当成 `hidden_size` 却说不清 GQA 时两者不等——被追一层就崩。

## 5. `--gpu-memory-utilization`（显存占用比）怎么定？

**一句话**｜**两端都是坑**：太低 → KV 预算为 0 服务起不来或并发为 1；太高 → 挤掉系统和通信显存，运行中被 OOM。

**30 秒答**｜这个参数的语义是"引擎允许自己用到单卡显存的多少比例"，
扣下来的部分才是 KV pool，所以它直接决定并发上限。
设太低（比如 0.6）会出现"明明还有空闲显存但 KV 分配不出来"的怪现象；
设太高（比如 0.98）会把 CUDA context、NCCL/通信 buffer、激活峰值、以及其他进程（监控 exporter）的空间挤没，
表现是**跑着跑着 OOM，而不是起不来**——排查成本高得多。
我的做法：从 **0.9 附近**起步，留固定余量，然后**看运行期显存峰值水位再调**，
多机场景要额外为通信 buffer 留更多余量。**判断线**：说"这个值不是越大越好，要看还剩什么要用"就是调过。

**弹药**
- 语义澄清：它是**上限预算**，不是"占用率目标"——低不代表省显存，代表 KV 少
- 必须留余量的东西：CUDA context、NCCL/通信 buffer、激活峰值、exporter/监控进程
- 多机 TP/PP 时余量要比单机更大（通信 buffer 与 pin memory）
- 观测：`nvidia-smi` + 引擎暴露的 KV cache 使用率指标，两者对不上就是碎片或旁路进程在吃

**红线**｜❌ "显存不够就调高 utilization" 当通用建议——OOM 现场说不清是哪一类占用，等于没调。

## 6. 72B FP16 为什么单卡 80G 放不下？有哪些出路？

**一句话**｜**权重就要 ~140GB**（72 × 2），单卡 80G 连地板都不够——出路是**多卡 TP** 或**量化后单卡**。

**30 秒答**｜72B BF16/FP16 权重约 140GB，还要加 KV 与激活，80G 单卡物理上装不下。
三条路按代价排：
①**2 卡 TP**（保持 FP16/BF16，精度零损失，代价是卡间通信与占用双倍）；
②**量化**（W8A8 约减半到 ~72GB 仍要 80G 档以上，W4A16 约 ~36GB 可单卡，代价是精度需评测回归）；
③**换更小模型**（业务能不能接受，是 SA 该问的问题，不是工程师的默认结论）。
**判断线**：报方案时必须同时报"精度是否变、要什么评测"，只报"能塞进去"就是不合格。

**弹药**
- 速算：FP16/BF16 = 参数 × 2B；FP8/INT8 权重 ≈ 参数 × 1B；W4 ≈ 参数 × 0.5B
- 量化档位：**W8A8**（int8 权重+激活，通用首选，吞吐收益明确）/ **W4A16**（AWQ、GPTQ，显存减半，精度要评）
- 单卡放不下时先看**能不能接受精度损失**，再看**能不能加卡**——顺序反了就是成本失控
- KV 也要算：量化权重省的是地板，**长上下文的天花板一点没省**（除非 KV 也量化）

**红线**｜❌ "量化几乎无损，直接上"——没有评测集回归和灰度就承诺精度，是生产事故预定。

## 7. 同一套命令换到 A100 / V100 上跑不起来

**一句话**｜**新模型的算子会收窄硬件支持面**——稀疏注意力、多 token 预测这类特性常依赖特定架构的 kernel。

**30 秒答**｜发布节奏决定了新算子先在新架构上做（Hopper 专属 kernel / 特定 flashinfer 版本），
老卡上要么没有实现，要么只有未优化的回退路径，报错常是 kernel/JIT 类而不是配置类。
所以选卡前第一步是**读官方硬件支持矩阵**，把"这个模型 + 这个引擎版本 + 这个 GPU 架构"当成一个三元组来验，
不能只看"显存够不够"。更老的 V100 连 BF16 都不支持，dtype 还得降到 float16，
这又牵出数值溢出和精度差异。**判断线**：能说出"三元组验证"就是做过异构集群的人。

**弹药**
- 支持矩阵三要素：模型 / 引擎版本 / GPU 架构（+ CUDA 与 driver）
- dtype 降级链：BF16 → FP16（V100 一类不支持 BF16）→ 精度需回归
- 异构池设计：按架构分池部署，**不要把不支持新算子的卡混进同一服务池**
- K8s 落点：node label + affinity 把架构当调度维度（GPU 型号是拓扑的一部分）

**红线**｜❌ 用"显存差不多"当兼容依据——显存只是必要条件，算子支持才是能不能跑的前提。

## 8. TP / PP / EP / DP 分别解决什么，怎么选？

**一句话**｜**TP 切单层（省显存但吃带宽）、PP 切层（跨机友好但有气泡）、EP 切专家（MoE 专属，吃 all-to-all）、DP 复制（提吞吐，显存不省）**。

**30 秒答**｜四个维度解决的是不同瓶颈，不是四个并列选项：
TP 把每层的矩阵切到多卡，**通信在每层内部**，所以只适合 NVLink 域内，跨机 TP 会被带宽打死；
PP 按层切，**只在层边界通信**，跨机友好，代价是流水线气泡和首 token 延迟；
EP 把不同专家放不同卡，专治 MoE 的权重驻留问题，代价是 all-to-all；
DP 是多副本扩并发，**每副本都要完整权重**，所以它解吞吐不解显存。
我的选择顺序：**单节点内先 TP 打满；跨机再考虑 PP/EP 组合；吞吐不够加 DP 副本**。
**判断线**：能按"通信发生在哪里"来解释四者差异，就是真懂并行。

**弹药**
- TP 判据：卡间带宽（NVLink 域内优先，跨机慎用）
- PP 判据：能容忍额外延迟（气泡）换跨机可行性
- EP 判据：MoE 且 all-to-all 通信能被拓扑吸收
- 组合形态：如 `TP=8` 单节点 × PP×2 × DP×N，或 MoE 上 EP+DP（专家数据并行）

**红线**｜❌ 把 DP 当"省显存手段"，或把 TP 跨机拉满——方向性错误，一追问就露。

## 9. GPU 集群的拓扑感知，具体感知什么？

**一句话**｜感知**NVLink 域、PCIe/NUMA 亲和、IB/RoCE 网卡归属**三件事——目标是让通信对端待在同一层带宽域里。

**30 秒答**｜同一个机内两卡走 NVLink 和走 PCIe 的带宽差一个量级，跨机走 IB 和走以太网又差一个量级。
所以调度要做三件事：①TP 组内的卡**必须落在同一 NVLink 域**；
②同 Pod/同任务的多卡请求**gang scheduling 原子调度**，否则一半拿到卡一半等，直接死锁或长尾；
③跨机任务的网卡与 GPU 要按 **PCIe switch / NUMA 亲和**配对，选错网卡延迟翻倍。
小规格请求（单卡任务）会打散大卡池，所以要**按拓扑分池 + 定时整理碎片**，而不是全池随机放。
**判断线**：说出"gang scheduling 防死锁"这一条，就说明管过多卡任务。

**弹药**
- 资源模型：**卡数 + 显存双维度**（共享卡/MIG 场景必须显存维度）
- gang scheduling / 网络拓扑感知调度（K8s 上是 Volcano / Gang / ACK 拓扑感知；MIG 切分做隔离）
- NVLink 域查询：`nvidia-smi topo -m`；网卡-GPU 亲和：`nvidia-smi topo -m` + `ibdev2netdev`
- 慢节点定位常来自拓扑问题：同拓扑域内某条链路劣化 → 该域整体延迟抬高

**红线**｜❌ 把 GPU 当同质资源随机调度（"有卡就行"），碎片和跨域通信会让集群吞吐凭空掉三到五成。
