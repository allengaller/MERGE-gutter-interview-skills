# 卡 · 性能、吞吐与估算

> 这类题的评分点是**推导链**，不是结论。面试官三句追问："这个数字怎么算出来的？""分子分母是什么？""冗余系数哪来的？"
> 铁律：**结论可以给区间，假设清单必须给全**。

---

## 1. vLLM 为什么快？

**一句话**｜两件事：**PagedAttention** 管显存（消碎片，同显存装更多并发）+ **continuous batching** 管调度（请求级进出批，不等整批）。

**30 秒答**｜朴素实现按最大长度给每条请求预留连续显存，实际长度参差不齐 → 大量碎片 + 并发上不去；
PagedAttention 把 KV cache 切成页按需分配，**显存利用率上去，同一张卡能同时服务的请求数就上去**。
另一半是批处理：静态批要等最长的那条生成完才换下一批，短请求白白占着算力；
continuous batching 让请求**逐 token 级动态进出批**，GPU 一直吃饱。
**判断线**：答到"**显存是推理瓶颈的主战场**"这句就到位了——只说"开源、有 CUDA 优化"是及格线以下。

**弹药**
- PagedAttention 管的是 **KV cache 的物理布局**，不是算子加速
- continuous batching 提**吞吐**；对单请求延迟的帮助有限（长请求会挤占 slot）
- 相关机制：chunked prefill（把长 prefill 切片，避免阻塞 decode）、CUDA graph、flash attention kernel
- SGLang 差异点：**RadixAttention 前缀树缓存**（多轮/共享前缀命中率高）+ 结构化输出加速

**红线**｜❌ 只会说"因为是开源的所以快"，或把 PagedAttention 说成"更快的注意力算子"——它解决的是显存碎片，不是 FLOPs。

**下一问**｜"和 SGLang 怎么选？"

## 2. vLLM 还是 SGLang？怎么选型？

**一句话**｜**看流量形态**：多轮对话/共享长系统提示词 → SGLang 的前缀树命中收益明显；通用高并发与生态稳妥 → vLLM。

**30 秒答**｜两者核心能力已经互相趋同（都有 PagedAttention 类显存管理 + 连续批处理 + 量化 + 投机解码），
所以选型不该停在"谁快"，要落到**你的负载特征**上：
SGLang 的 RadixAttention 把共享前缀组织成前缀树，Agent/多轮对话这类"同一套长系统提示反复命中"的场景省 prefill 显著；
vLLM 的接口生态、模型覆盖和版本节奏更稳，且**新架构的支持门槛常以 vLLM 为基准**。
最终答案是方法论：**同一模型、同一硬件、同一压测流量各跑一遍，看吞吐/P99/前缀命中率再定**，不做宗教争论。
**判断线**：主动说"我实测两个再选"比背差异清单更值钱。

**弹药**
- 压测三指标：吞吐（tokens/s）、TTFT、P99 端到端延迟；外加**前缀缓存命中率**
- 引擎版本门槛：**新架构看 release notes 声明**，谁先支持用谁（例：vLLM ≥ 0.28.0 / SGLang 最新版）
- 分环境部署：两个引擎**绝不装同一 venv**（依赖互相覆盖）
- 长期成本：引擎绑定要换模型时重验一次，选型是**每代模型都要重做的决策**，不是一次定终身

**红线**｜❌ "SGLang 更快"当无条件结论——没有负载画像的比较没有意义。

## 3. 经典估算：500 人日常使用 72B 模型，要多少卡？

**一句话**｜**先给假设，再给公式，结论给区间**：按日均 10 轮、峰值并发 20–50、每轮入 2K 出 1K，落在 **8–16 卡 80G 档**。

**30 秒答**｜四步走完：
①峰值并发 → 同时活跃的请求数（20–50）；②单请求吞吐 → 每轮输入 2K（prefill）+ 输出 1K（decode），
峰值总 token 吞吐需求 = 并发 × 每轮 token ÷ 可接受完成时间；
③**实测单卡吞吐**（不抄宣传数），72B FP16 权重 ~140GB，单卡 80G 放不下 → 每副本至少 2 卡 TP；
④卡数 = 峰值吞吐 ÷ 单卡吞吐 × 冗余 **1.3–1.5**，再与"显存下限（权重 + KV）"取大。
KV 用 `batch × 长度 × 层 × 头维度` 校一遍，32K 上下文起步时 KV 会显著压低并发，卡数要上调。
**判断线**：说"结论 8–16 卡，但假设清单比结论重要"就是合格；直接报"20 张 A100"是红线。

**弹药**
- 公式：**卡数 = 峰值吞吐需求 ÷ 实测单卡吞吐 × 冗余(1.3–1.5)**
- 显存下限另算：`权重 ÷ 单卡显存` 与吞吐解出来取大
- 上下文 32K 起 → KV 显存翻数量级 → 批上限下降 → 卡数上调 + 上 KV 治理
- 汇报口径：给"卡数区间 + 三条关键假设 + 哪个假设最敏感"

**红线**｜❌ 只给卡数不给过程；❌ 忽略 KV 显存（把估算做成"权重除法"）；❌ 用厂商 benchmark 峰值当单卡吞吐。

## 4. 客户只说"2000 人都要用"，估算怎么起手？

**一句话**｜**从业务画像倒推，不是从模型倒推**——先质疑"2000 人 ≠ 2000 并发"，把活跃度分布和日均请求数问出来。

**30 秒答**｜人头数没有用，内部助手类应用真实并发和人头差一到两个数量级。
我要的四项输入：**峰值/日均在线人数、人均日请求数、平均上下文长度、延迟 SLA**。
典型形状是"2000 人里日均活跃几百、峰值同时在线几十"，所以第一步就把 2000 拆成活跃率分布，
第二步再问清场景（写作助手 vs 客服机器人 vs 代码补全，token 画像完全不同）。
**敢质疑前提本身是加分项**——SA 的价值是把"我们要多少卡"翻译成"你们真实峰值是多少并发"。
**判断线**：拿到"2000 人"就报卡数 = 直接降级；能反问出 SLA 和上下文长度 = 通过。

**弹药**
- 必问清单：**并发画像（峰值/日均）、token 画像（输入长度/输出长度）、延迟 SLA、增长预期**
- 常见量级：内部助手类人均日均 5–20 轮；峰值/日活比例常是 10–20%
- 延迟 SLA 决定 decode 侧预留：TTFT 与总完成时间要分开定
- 追问反向："如果只能要一个数，我要峰值并发 QPS"——它直接进公式

**红线**｜❌ 从"模型多大"直接拍卡数；❌ 全程没问过延迟 SLA（吞吐和延迟是两条账）。

## 5. 冗余系数 1.3–1.5 的依据是什么？

**一句话**｜**峰值抖动 + 故障域 + 增长**三块：算出来的卡是"平均能撑住"，不是"抖一下还撑住"。

**30 秒答**｜拆开说：①**流量抖动**——早高峰、突发公告、批量任务会让瞬时并发远超均值，
按均值买卡必挂；②**故障域**——单副本所在节点/机柜故障时，剩下的卡必须能吞下全部流量，
否则降级；100 卡集群同时坏 2–3 张卡是常态；③**增长预留**——扩容采购有周期，
买的时候就要覆盖下个季度。取值高低取决于业务形态：
面向内部办公助手机器人可以低（1.2–1.3，流量可预测、允许排队），
对外 SLA 服务要高（1.4–1.5 甚至更高，且要按多可用区分布）。
**判断线**：能报出"这个数字我是这么拆的"就够了——面试官要的是可复现推导，不是标准答案。

**弹药**
- 抖动口径：**按峰值而非均值算**（峰值/均值比要从业务侧要，别自己拍）
- 故障域要落成**部署形态**：多副本、跨节点反亲和、可用区分布（K8s 侧是拓扑约束）
- 更省的替代方案：**弹性溢出**（基线自建 + 峰值走公有云 API），比堆冗余便宜
- 反向问题："如果客户预算只够 1.0 倍呢" → 答降级策略（排队、限流、小模型兜底），不是答"那就慢一点"

**红线**｜❌ "行业惯例都这么乘"——被追一层就崩；必须能拆成三块来源。

## 6. 优化阶梯：从最便宜的动作开始排

**一句话**｜**前缀缓存 → 量化 → 连续批处理参数 → PD 分离 → 模型路由**，顺序按"改动成本"从低到高排。

**30 秒答**｜先诊断再优化（利用率、请求分布、批处理效率三张表），然后按阶梯上：
①**前缀缓存**——系统提示词/few-shot 稳定前缀只算一次，重复模板场景立竿见影，几乎零风险；
②**量化**——W8A8/W4A16 换吞吐与显存，代价是精度，**必须评测回归 + 灰度**；
③**连续批处理与调度参数**——batch 上限、`max-num-batched-tokens`、chunked prefill，收益中等但要压测调参；
④**PD 分离**——规模门槛高，KV 跨卡传输代价大；
⑤**模型路由**——简单任务走小模型，是**业务侧改造**但常是收益最大的一层。
**判断线**：每层都主动报"收益 + 代价 + 什么规模值得上"，就是专业；只会报其中一层，就是初级。

**弹药**
- 阶梯第一动作不是"调引擎"，是**看请求分布**（长上下文占比、重复前缀占比）——决定哪层收益最大
- 上限：硬件理论吞吐；对标用 **MFU**（模型算力利用率），不是 GPU 利用率
- 加速开关要**一次开一项**，否则无法归因也无法回滚
- 模型路由的前提：有意图/难度分类器，且小模型在该任务上评测过

**红线**｜❌ 上来就"加机器"或"上 PD 分离"——前者是成本失控，后者在小规模上反而更慢更贵。

## 7. 前缀缓存（prefix caching）在什么场景赚、什么场景亏？

**一句话**｜**共享前缀比例高就赚**——同一套长系统提示 / few-shot / 多轮历史；**前缀每次都变就白搭内存**。

**30 秒答**｜机制是把相同前缀的 KV 复用，命中部分不用重算 prefill，
所以省的是**算力与 TTFT**，长前缀 + 高重复命中时收益最大（比如带万字工具定义的 Agent、统一模板的批量任务）。
亏的场景：每条请求前缀都不一样（动态内容放在最前面、把时间戳/用户 ID 拼在开头），命中率直接归零——
所以**提示词工程要配合**：稳定内容放前面、动态内容放后面，才能形成公共前缀。
多轮对话要把历史拼成前一请求的后缀延续，才能续用缓存。
监控必做：**前缀缓存命中率 + 命中带来的 TTFT 改善**，不观测就等于不知道有没有收益。
**判断线**：能说出"把动态字段挪到提示词末尾来提高命中率"就是真做过优化。

**弹药**
- 命中率公式：**命中 token 数 ÷ 总输入 token 数**；SGLang 的 RadixAttention 就是前缀树版实现
- 配合手段：多轮上下文截断策略、few-shot 固定在模板头部、工具定义稳定化
- 副作用：缓存占显存 → 挤压 KV pool 与并发；**命中率与并发要一起调**
- 与 Agent 成本联动：系统提示 + 工具定义是最大的一块可缓存前缀，直接反映在每会话 token 成本上

**红线**｜❌ 只说"开了缓存就省钱"，说不出命中率和提示词结构的关系。

## 8. KV cache 线上治理：长上下文压力怎么管？

**一句话**｜四招：**前缀缓存、滑动窗口/截断、KV offload、按上下文长度分池**——监控看命中率与显存水位。

**30 秒答**｜KV 显存 = `batch × 长度 × 层 × 头维度`，长上下文**线性暴涨**，一条 200K 请求能占掉一整池的额度。
治理按"先复用、再限制、再下沉、最后隔离"排：
①前缀缓存让共享部分不重复占；②会话级滑动窗口 + 摘要压缩控制长度增长（Agent 场景必做）；
③KV offload 把冷 KV 下沉到内存/SSD，**用吞吐换容量**；
④**按长度分池**——长上下文走独立实例池，避免它拖垮短请求的 P99。
业务侧还要有硬约束：单请求最大长度、超长输入的降级（截断/拒绝/走离线）。
**判断线**：能说出"分池是为了保护短上下文吞吐"就是管过线上。

**弹药**
- 监控四项：**KV 使用率 / 前缀命中率 / 抢占（preemption）次数 / 排队时长**
- 抢占是显存不够的信号：被抢占请求要重算 → 吞吐塌方，比 OOM 更隐蔽
- offload 代价：HBM → 内存/SSD 的往返延迟，只适合冷数据，别当默认开关
- 长度分布先行：**P50/P95/P99 输入长度**决定分池阈值和 `--max-model-len`

**红线**｜❌ 只调 `max_tokens` 不管 KV；❌ 没听过"前缀缓存命中率"和"抢占次数"。

## 9. PD 分离（Prefill / Decode 分离）什么时候上？代价是什么？

**一句话**｜**大规模 + 长上下文 + 峰值明显**才值得；这题答"什么情况下不该上"比答"怎么上"更见功力。

**30 秒答**｜原理：prefill 是 compute-bound（吃算力），decode 是 memory-bound（吃带宽），
混在同一批卡上互相干扰——长 prefill 会把 decode 的 P99 拖高。
分离后两组各自独立扩缩、各自按瓶颈选型。但代价三条很硬：
**①KV 要跨卡传输**（要 IB/RDMA，带宽不够直接白干）；②系统复杂度翻倍（两组池 + 调度 + 扩缩联动）；
③故障域变大。所以小规模上它**反而更慢更贵**。
**判断线**：明确说出"我现在的并发和长度分布还没到那个门槛，先做前缀缓存和分池"——这是最漂亮的答案。

**弹药**
- 上的门槛信号：**prefill 长尾明显**（P99 输入远超 P50）+ 规模够大 + TTFT 与 TPOT 需要分别 SLA
- 传输代价：KV 传输量 ∝ 长度 × 层 × 头维度——**长上下文场景这笔账很大**
- 轻量替代：**chunked prefill**（把长 prefill 切片与 decode 混排）能在不上 PD 的情况下缓解干扰
- 汇报话术："PD 分离是规模问题不是技巧问题"

**红线**｜❌ 当万能银弹推荐；❌ 不知道 KV 跨卡传输的带宽要求。

## 10. GPU 利用率高但吞吐不行，问题在哪？

**一句话**｜**GPU 利用率是个骗人指标**——它只说"有 kernel 在跑"，不说"算得值不值"，要看 **MFU**。

**30 秒答**｜`utilization` 是"采样期内至少有一个 kernel 在执行"的比例，
碎片化小 kernel、通信等待、低效实现都能把它推到 90% 而实际算力用不到两三成。
正确的分层是：**MFU/TFLOPs 对标 → 看有效计算**；
**batch 并发度 / KV 使用率 → 看是否吃饱**；**延迟分位（TTFT / TPOT）→ 看业务体感**。
低吞吐常见根因按概率排：并发不足（batch 太小、KV 挤占）> 频繁抢占重算 > 通信占比高（跨机 TP）>
精度/kernel 未优化（没走 Flash Attention、非 Hopper 回退路径）。
**判断线**：主动纠正"利用率 ≠ 有效利用率"这一句，是这题的分水岭。

**弹药**
- **MFU**（Model FLOPs Utilization）= 实际达到 FLOPs ÷ 硬件理论 FLOPs；比 GPU 利用率诚实
- 关键分位：**TTFT**（首 token，看 prefill 与排队）、**TPOT**（每 token，看 decode 与 batch 健康度）
- 通信占比：跨机并行时看 `NCCL` 相关耗时；`nvidia-smi nvlink` 看域内带宽
- 观测组合拳：吞吐 + TTFT + TPOT + 显存水位 + 抢占次数，**五件套一起看才能定因**

**红线**｜❌ 拿"我们 GPU 利用率 95%"当成果汇报——内行第一个问题就是"MFU 多少"。

## 11. 推理服务的 SLA 怎么定？只说"快"行不行？

**一句话**｜**吞吐和延迟两条都要有 SLA**，且延迟必须拆成 **TTFT + TPOT** 两段——只讲一个必被降级。

**30 秒答**｜单说"平均响应 2 秒"没意义，用户体感是两段：**首 token 多久出来（TTFT）**决定"是不是卡住了"，
**每 token 间隔（TPOT）**决定"读起来跟不跟得上"。
所以我要定三条：**TTFT P90/P99、TPOT P90/P99、峰值吞吐（tokens/s 或 QPS）**，
再配可用性（错误率/排队丢弃率）。容量规划按吞吐算，用户体验按延迟算，
两者在 batch 上冲突（batch 越大吞吐越高、TPOT 越差），**这个 trade-off 必须让业务签字**。
**判断线**：能说出"加大 batch 提吞吐会伤延迟，所以 SLA 要拆开定"，就是懂推理系统的人。

**弹药**
- 三段式：**TTFT（prefill + 排队）｜TPOT（decode 步进）｜端到端总时长**
- 流式场景 TTFT 权重最高；长文生成场景 TPOT 权重最高
- 容量红线：**P99 延迟随负载非线性恶化**——不要按"平均值还有空间"扩容
- 降级要有定义：排队超时返回、限流返回 429、超长请求走离线批处理，**写进 SLA 而不是临场决定**

**红线**｜❌ "只讲吞吐不讲延迟，或反之"——这是 AI Infra SA 面试的明示红线。
