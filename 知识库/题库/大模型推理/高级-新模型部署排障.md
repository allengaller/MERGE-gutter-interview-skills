# 题库 · 大模型推理 · 高级场景题

> **难度**：高级（推理 / Infra 方向，5y+ 或资深 SA/P7 档）
> **时长**：30-40 分钟（按 L1-L5 分层追问递进，可拆成多道短题）
> **素材来源**：GLM-5.3-Flash（320B 总参 / 18B 激活 MoE、DSA 稀疏注意力 + MTP 多 token 预测、标称 1M 上下文）首日私有化部署排错清单（2026-09，来源见文末）
> **配套知识**：[AI-SA/AI基建.md](../AI-SA/AI基建.md) Q7-Q11（推理引擎 / 显存 / 稳定性基础题）——本题是那 13 题的**综合实战版**

## 面试官画像

出题人心里只有一个问号：**你部署过的是"见过的模型"，还是"没见过的模型"？** 官方文档永远写不全，拿到一个发布 48 小时的新模型，你有没有一套阶段化、可复现的排障方法论——还是只会把报错粘给搜索引擎？

## 题干（情境）

> 智谱刚发布 GLM-5.3-Flash：320B 总参数 / 18B 激活的 MoE，DSA 稀疏注意力 + MTP 多 token 预测，官方标称 1M 上下文。**注意它不是小模型**——"Flash" 指激活参数少、单 token 推理快；BF16 权重本身就要 **~640GB** 显存。
>
> 客户要求数据不出域，**一周内私有化上线**。你手上是一台 **8×H20（141GB/卡）**，模型从 ModelScope 拉（`zai-org/GLM-5.3-Flash`）。
>
> **请给出你的完整部署方案：按"下载 → 引擎 → 显存并行 → 加载运行 → 服务化"五个阶段，每个阶段你预判会出什么问题、用什么命令/检查项确认、出了怎么定位？**

## 分层追问（面试官逐层放题）

### L1 · 下载与完整性（阶段 0）

**追问**："模型拉到一半断了，续传完 vLLM 加载时报 safetensors header corrupt。怎么回事、怎么防？"

**参考要点**：权重 ~141 个分片，断点续传可能留下损坏分片；下载完成先**校验分片数量/大小/hash**（modelscope download 输出或对 config.json 里的分片清单核对）再进引擎；磁盘要按 640GB 权重 + 解压/临时空间预留——磁盘不足在报错里往往伪装成别的错。

**再追问**："repo ID 写成 `zai-org/glm-5.3-flash` 会怎样？误拉成 GLM-5.3（743B 兄弟型号）会怎样？"——前者 404；后者多下几百 GB 把磁盘和排障时间一起干爆。**组织名 + 大小写 + 型号**，下载前三查。

### L2 · 引擎与依赖（阶段 1）

**追问**："启动直接报 `Model architectures ['...'] are not supported`，第一反应？"

**参考要点**：新架构要新引擎——**vLLM ≥ 0.28.0 / SGLang 最新版**；同时确认 transformers 版本能解析 DSA/MTP 的新 config 字段。部署新模型第一步是**读 release notes 里声明的引擎版本门槛**，而不是先 pip install 最新稳定版赌运气。

**再追问**："vLLM 和 SGLang 装进同一个 venv，一个能跑一个崩，为什么？"——triton / flashinfer / torch 版本互相覆盖，**推理引擎必须分环境**。

**再追问**："客户工程师想在 Mac 上跑，报 `ValueError: No supported GPU found`，你解释一下？"——vLLM/SGLang 只支持 NVIDIA CUDA；Apple Silicon 只能走 llama.cpp 类 CPU/Metal 路线，且官方量化版 UD-IQ1_S 也要 100GB+ 内存。**推理引擎生态决定了硬件边界**，不是"模型不大就能跑"。

### L3 · 显存与并行（阶段 2）

**追问**："8×H20 怎么切？TP 给多少？为什么不能单卡放？"

**参考要点**：640GB ÷ 141GB ≈ 4.5 卡是**下限**，还要留 KV cache、激活值、碎片余量 → **TP=8**；MoE 架构可以进一步谈 EP（专家并行）/DP 混合的取舍与当前版本 kernel 兼容性。减半路径：FP8 / 官方量化版。算显存账要有"权重是地板、KV 是天花板"的意识。

**再追问**："启动报 `max seq len is larger than the maximum number of tokens that can be stored in KV cache`，为什么？怎么办？"

**参考要点**：默认按 1M 上下文做 KV 预算直接爆。先 `--max-model-len 32768` 起步，压测后再逐步放开。能写出 KV cache 估算公式（`2 × layers × kv_heads × head_dim × dtype_bytes × seq_len × batch`）更好——**公式和方法要对，具体层数/头数查 config 即可，不要求背**。`--gpu-memory-utilization` 过低 KV 为 0、过高挤爆系统显存，两端都是坑。

**再追问**："客户还有一批 A100/V100，同一套命令为什么跑不起来？"——DSA/MTP 依赖 **Hopper 架构专属 kernel / 特定 flashinfer 版本**，非 Hopper 卡报 kernel/JIT 错——新模型的新算子会收窄硬件支持面，选卡前先看官方支持矩阵。V100 级连 bf16 都不支持，dtype 还要降到 float16。

### L4 · 加载与运行（阶段 3）

**追问**："服务起来了，第一个请求 5 分钟没返回，像卡死。是 bug 吗？"

**参考要点**：新 shape 触发 **JIT 编译**，首 token 延迟极大是已知正常现象——做预热请求 + 看日志确认编译在推进。关键区分：**"编译中"（GPU/日志在动）vs "真 hang"（NCCL 卡住、日志停摆）**，处置完全不同。

**再追问**："MTP 投机解码怎么开？""还有哪些基础运维坑？"——`--speculative-config` 格式随版本变，GLM-5 的 MTP 头需显式开启，配错轻则不生效重则崩；NCCL/shm 报错、端口占用、ulimit 文件句柄不足是通用分布式服务坑，SRE 背景应秒答。

### L5 · 服务化与上线判断（阶段 4）

**追问**："OpenAI 兼容接口上线，客户端解析 tool_calls 失败、角色交替报错。"

**参考要点**：GLM-5 的 **chat template / 工具调用格式特殊**——核对 trust_remote_code 与模板版本；`reasoning_content` 是非标字段，客户端要适配；流式断连单独压。另外官方把它归在 **VLM 类**——若用到视觉，还有多模态 processor / allowed-modalities 一类配置报错。

**再追问**："业务要求用满 1M 上下文，你放不放？"

**参考要点**：官方自己都说 1M 长上下文**未充分验证**——上线决策分档：32K/128K 先灰度，1M 场景单独压测；超长输入可能**静默降质**而非崩溃，比崩溃更危险。这是"Flash ≠ 能白嫖 1M"的对外话术，也是高级候选人和中级候选人的分水岭。

## 面试官底牌：最小可跑参考（以官方文档为准）

```bash
# vLLM
VLLM_USE_MODELSCOPE=1 vllm serve zai-org/GLM-5.3-Flash \
  --tensor-parallel-size 8 --max-model-len 32768
# SGLang 对应：SGLANG_USE_MODELSCOPE=1 + --tp 8
```

## 红线（出现即扣大分）

- 把 "Flash" 理解成小模型，按单卡/双卡规划显存
- 遇到报错只会搜索报错文本，讲不出阶段化排障方法论
- 不知道 `--max-model-len` 与 KV cache 显存的关系
- 部署前不读 release notes、不核对引擎版本与硬件支持矩阵
- 长上下文"标称多少就放多少"，没有灰度/压测意识

## 评分标准

| 档位 | 表现 |
|------|------|
| **高级通过** | 五阶段都有事前预判 + 检查项；显存账算得清（权重地板 / KV 天花板 / 余量）；对未验证能力（1M 上下文）有分档上线判断；能区分"慢"和"hang" |
| **中等** | L1-L3 常规报错能处理，但靠报错信息驱动、缺事前预案；KV 估算公式对、参数记不全可接受 |
| **不通过** | 只会跑 demo 命令；把 Flash 当小模型；说不出为什么必须多卡并行 |

## 给候选人的一句复盘

这题考的不是 GLM-5.3-Flash 本身，而是**"部署一个你没见过的模型"的元能力**：读 release notes → 核对版本门槛 → 算清显存账 → 分阶段验证 → 灰度上线。报错清单会过时，方法论不会。
