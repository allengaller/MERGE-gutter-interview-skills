# AI Infra SA · 专业轮题库（算力 / 推理基础设施方向）

> **目的**：验证"把模型跑得**快、稳、省**"的能力——线上最佳实践口径：算力经济学（吞吐/延迟/成本三角）、集群稳定性、利用率治理。
> **面试官**：AI 基础架构 / PAI 资深专家。他自己管过千卡集群，估算题、排障题都往死里追。
> **专业轮 60 分钟**；HR / 高管 / 压力轮复用 [全栈SA](../全栈SA/导航.md)。你的 SRE/ACK 背景在这个方向是**主场**，K8s 功底题必拿分。
> 深挖背景知识：[可观测性.md](../../主题/可观测性.md) / [K8s内核.md](../../主题/K8s内核.md)。GPU 推理栈是已声明的相对弱项——原理要讲清，缺实战要坦诚 + 给补法（口径与 全栈SA 第3轮 Q4/Q10 一致）。

## 方案面（算力规划 + TCO + 国产化）

### Q1 客户要私有化部署大模型，算力规划从哪一步开始？完整路径是什么？
**追问**："客户只说'公司 2000 人都要用'，怎么办？"
**参考要点**：从业务画像倒推，不是从模型倒推——①并发画像（峰值/日均在线、QPS、上下文长度、延迟 SLA）②单请求 token 吞吐需求 ③选模型定单卡吞吐（实测，不抄宣传数）④卡数 = 峰值吞吐 ÷ 单卡吞吐 × 冗余系数（1.3-1.5）⑤网络/存储/容灾配套。"2000 人"没法直接算——先分层（活跃度分布、日均请求数），内部助手类应用实际日均活利率远低于人头数，敢质疑前提是加分项。
**红线**：从"模型多大"直接拍卡数；没问延迟 SLA。

### Q2 经典估算题：500 人日常使用 72B 模型，估算 GPU 数量并给推理过程。
**追问**："上下文 32K 起步，答案变吗？"
**参考要点**：给可复现过程：假设日均 10 轮/人、峰值并发 20-50、每轮输入 2K + 输出 1K token → 峰值总吞吐需求；72B FP16 权重约 140GB，单卡 80G 放不下需 2 卡张量并行或量化后单卡；配合 KV cache（batch×上下文长度×层数×维度）算显存压力；结论给区间（如 8-16 卡 80G 档）并强调**假设清单**比结论重要。32K 长上下文 → KV cache 显存翻数量级，批处理上限下降，卡数上调且建议上 KV 管理优化。
**红线**：直接给"20 张 A100"没有过程；忽略 KV cache 显存。

### Q3 公有云 API vs 全私有化 vs 混合，TCO 对比模型怎么搭？
**追问**："客户 CFO 只看三年总成本，你的账怎么算？"
**参考要点**：四本账——资源（API 按 token 计费 vs 自建卡折旧 + 电费机房）、人力（自建运维团队 vs 云托管）、隐性（自建踩坑周期、模型升级成本）、风险（数据合规价值、供应锁定）。给出**分界线判断**：低频/试错期用 API，规模化 + 数据敏感才私有化；混合方案（敏感推理私有化 + 弹性溢出公有云） often 最优。给客户看"什么规模私有化才回本"的盈亏平衡点，这是 SA 的专业价值。
**红线**：只比卡价不比人力；说不出自家 API 与私有化的切换路径。

### Q4 离线/国产算力受限环境（昇腾 + 数据不出域），部署方案怎么设计？
**追问**："客户的应用里有 CUDA only 的组件呢？"
**参考要点**：分层评估——模型层（Qwen 系列对昇腾适配最好）、推理引擎层（vLLM-Ascend / MindIE 等适配现状，算子覆盖度逐个核）、应用层（CUDA only 组件找替代或 CPU 化，明确迁移清单）。给降级预案：核心链路全国产，非核心组件替代方案。诚实告知生态差距（部分算子/版本坑），给 POC 验证清单——先小规模实测目标模型的吞吐与精度，再定规模。
**红线**：拍胸脯说"完全兼容无缝迁移"；没有 POC 验证环节。

### Q5 推理成本超预算 3 倍，你的诊断路径和优化建议？
**追问**："优化空间还有多少？上限在哪？"
**参考要点**：先诊断再优化——看利用率（GPU 利用率 vs MFU，低利用率是调度/批处理问题）、看请求分布（长上下文占比、重复前缀占比）、看批处理效率（并发度、batch 大小）。优化阶梯：前缀缓存（重复系统提示词场景立竿见影）→ 量化（W8A8/W4A16，吞吐提升但需评测回归）→ 连续批处理参数调优 → PD 分离 → 模型路由（简单任务小模型）。上限就是硬件理论吞吐，讲得出 MFU 对标才显得专业。
**红线**：上来就"加机器"；说不出任何一层利用率数字。

### Q6 客户要建推理集群：网络、存储、拓扑怎么选？
**追问**："训练和推理混部呢？"
**参考要点**：推理集群网络压力小于训练（参数量级传输），常规组网够用但 KV 跨卡传输（PD 分离时）要高带宽；存储看模型分发（大权重秒级加载 → 并行文件系统/本地缓存预热）与业务数据。拓扑感知调度：GPU 亲和性（NVLink 域内优先、跨机带宽分层）。训推混部：潮汐错峰（白天推理、夜间训练）+ 优先级抢占 + 显存隔离（MIG/独立实例），利用率能上去但运维复杂度显著增加，给客户讲清 trade-off。
**红线**：推理集群照搬训练组网不考虑成本；混部只讲收益不讲隔离风险。

## 技术面（推理引擎 + 调度 + 稳定性）

### Q7 vLLM 为什么快？PagedAttention 解决什么问题？
**追问**："和 SGLang 的差异了解吗？"
**参考要点**：vLLM 两大件——**PagedAttention**（KV cache 按页管理，消显存碎片，同显存容纳更多并发）+ **continuous batching**（请求级动态进出批，不等整批完成）。SGLang 差异点：RadixAttention 前缀树缓存（多轮对话/共享前缀场景命中率高）、结构化输出加速。答到"显存是推理瓶颈的主战场"就到位了。
**红线**：只会说"开源的快"；说不出 PagedAttention 管的是什么。

### Q8 PD 分离（Prefill/Decode 分离）什么规模才值得上？代价是什么？
**追问**："跨卡 KV 传输的延迟怎么办？"
**参考要点**：原理——prefill 是 compute-bound（吃算力），decode 是 memory-bound（吃带宽），混部互相干扰；分离后各自独立扩缩。**值得上的条件：大规模 + 长上下文 + 峰值明显**，小规模上了反而增加 KV 跨卡传输成本与运维复杂度。代价：KV 传输带宽要求（IB/RDMA）、系统复杂度翻倍、故障域变大。这题答"什么情况下不该上"比答"怎么上"更见功力。
**红线**：把它当万能银弹；不知道 KV 传输成本。

### Q9 量化：W8A8 / AWQ / GPTQ 怎么选？上线前必做什么？
**追问**："客户场景对精度极敏感呢？"
**参考要点**：选型——W8A8（int8 权重+激活，通用首选，吞吐收益明确）、AWQ/GPTQ（W4A16，显存减半，精度损失需评估）、敏感场景 FP8/混合精度。**上线必做：评测集回归**（业务 golden set 跑精度对比 + 困难样本人审），不能只看 perplexity。给出"量化收益 vs 精度风险"的决策依据和灰度节奏（影子流量 → 小比例 → 全量）。
**红线**：量化只说"几乎无损失"没有评测证据；不知道要灰度。

### Q10 KV cache 线上治理：长上下文内存压力、前缀复用怎么做？
**参考要点**：KV 显存 = batch × 上下文长度 × 层数 × 头维度，长上下文线性暴涨挤占并发额度。治理四招：**前缀缓存**（系统提示词/few-shot 共享前缀只算一次）、滑动窗口/截断策略、KV offload（显存不足下沉 HBM→内存/SSD，换吞吐）、按上下文长度分池部署（长上下文独立实例池，保护短上下文吞吐）。监控看 KV cache 命中率与显存水位。
**红线**：只调 max_tokens 不管 KV；没听过前缀缓存命中率。

### Q11 推理服务线上炸了：GPU OOM / 慢节点 / NCCL hang，分别怎么排查？
**追问**："给你 100 卡的集群，怎么系统性地防？"
**参考要点**：GPU OOM——显存碎片/长上下文尖峰/批过大，看显存水位曲线定位（预留水位 + 请求长度限制 + 优雅降级）；慢节点——ECC 错误/降频/网络劣化，做**慢节点检测与自动踢除**（延迟分位数监控 + 摘流量隔离）；NCCL hang——IB 链路/驱动版本/超时参数，先分段验证链路。系统性防：GPU 集群要当**异构易损系统**做运维（监控四件套：显存/算力利用率/延迟分位数/XID 错误），这是 SRE 背景的主场题，讲出与普通服务运维的差异。
**红线**：SRE 出身却只会重启大法；没听过 XID 错误。

### Q12 K8s 上跑 GPU 推理：调度、配额、碎片怎么治理？
**追问**："多个团队抢卡怎么分？"
**参考要点**：调度——GPU 拓扑感知（NVLink/IB 亲和）、gang scheduling（多卡请求原子调度防死锁）、显存/卡数双维度资源模型；配额——按团队 ResourceQuota + 优先级抢占（生产 > 实验），quota 回收机制；碎片——小规格请求打散大卡池，定时治理 + 潮汐回收。结合 ACK 实战经历讲（3 年 ACK 专家是差异化护城河），讲出"GPU 资源池和 CPU 资源池运维心智的差异"。
**红线**：把 GPU 当普通资源调度；说不出碎片是怎么产生的。

### Q13 多租户推理平台：算力配额、优先级、隔离怎么设计？
**追问**："某个租户打满集群，其他租户饿死怎么办？"
**参考要点**：隔离层级从轻到重——实例级（物理隔离，成本高）→ 配额级（token/并发限流 + 优先级队列）→ 时间片（抢占）。线上最佳实践：混合制——核心租户独立实例保 SLA，普通租户共享池 + 严格配额 + 单租户并发上限（防打满）；弹性配额（闲时借出）；计量计费透明（token 级账单），多租户数据隔离（上下文不跨租户、审计日志）。饿死问题本质是限流设计，讲得出公平性算法（如按 quota 加权队列）更佳。
**红线**：所有租户一个池没配额；隔离方案完全没算成本。

## 本轮通过标准

- 估算题过程可复现、假设清单清晰，敢质疑不合理前提
- 推理优化有机制级理解（PagedAttention / PD 分离 / 量化 / KV 治理），知道"什么规模才值得上"
- 集群稳定性讲得出 GPU 特有故障模式与检测手段（SRE 主场必须拿分）
- 成本账四本齐全，全程"利用率/TCO"视角——这是 AI Infra SA 与普通运维的分界线
