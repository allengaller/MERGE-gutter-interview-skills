# Topic · 上游社区贡献（SIG）

> 给 interview-coach skill 加载。**按需引用**——面试官问"你给上游提过 PR 吗"时回这里查。
> 这篇不讲 Kubernetes 怎么用，讲"怎么在别人的代码库里留下一处被接受的改动"，以及这件事在面试里怎么变现。

---

## 先说清楚：面试官问这个在测什么

不是测名气，是三件事，答的时候要主动往这三件事上收：

| 他真正在测 | 及格回答的形状 | 挂掉的回答 |
|-----------|---------------|-----------|
| **陌生代码库生存能力** | "我是从这段失败的测试用例反推入口函数的" | "我看了一遍源码" |
| **工程规范服从** | 说得出 CLA、sign-off、verify、reviewer 从哪来 | "我提了 PR 但没人理" |
| **与陌生人对齐的能力** | 被拒之后怎么把 review 意见变成第二版 | 抱怨 maintainer 不搭理中国候选人 |

**关键判断线**：能不能说出**具体 PR 号 + 目标仓库 + 谁 approve + 进了哪个 release**。
说不出这四项，这段经历在面试里等于 0 分——因为无法核查。

## 贡献路径（按投入排序，从 20 分钟到 2 周）

1. **Triage（最被低估的一步）**：给未复现的 issue 补最小复现、贴 `/retest`、判断是否重复、
   把 label 从 needs-triage 推到 kind/bug 或 kind/failing-test。
   这一步**不需要权限**，且 maintainer 感激度最高——它替他们省了最贵的时间。
2. **修 flaky / 失败测试**：从 test-infra 的报告里挑一个稳定复现的失败，
   根因常常是"测试假设了时序"而不是产品 bug。这类 PR 小、可读、易过。
3. **文档**：website 仓库的门槛最低，但**别做纯排版**——
   做"把某个易错参数的正确口径写清楚"这种，面试时才讲得出内容。
4. **补一个单测分支 / e2e 用例**：为已有函数补边界（尤其是你自己生产上踩到的那个边界）。
5. **bug fix**：必须先在 issue 里确认"这个方向要吗"，再动手。
6. **KEP（设计提案）**：需要 SIG 背书、走评审、上线还要 Production Readiness Review。
   候选人能讲到 KEP 的结构（为什么/非目标/分阶段启用/可回滚），就已经在考架构了。

**最便宜的可核查贡献**：自己在生产上踩过的 bug → 搜 issue 是否已知 →
写一个**能稳定复现的测试** → 提 fix。三步都在做自己已经在做的事。

## 硬门槛清单（每一项都能让 PR 白干）

- **CLA**：CNCF 项目走电子 CLA。个人签还是企业签要分清——
  在职员工改的与工作相关的代码，通常要**公司签**，个人签了也会被卡在 checklist 上。
  这一条最浪费时间，动手前先签。
- **commit sign-off**：每条 commit 要带 `-s`（DCO）。漏了会被机器人点名，
  补救是 `git rebase -s`（或 `git commit --amend -s`）后强推自己的 feature 分支。
- **issue 先行**：没有 good first issue / help wanted 标记就不要直接提 PR。
  正确顺序是：提 issue → 在 issue 里说"我来做" → 得到 maintainer 认可 → 再提 PR 并在正文写 Fixes #编号。
- **本地跑 verify**：CI 里的 lint / gofmt / 生成代码校验（make verify 一类）
  能在本地先跑完，别拿 CI 当格式化工具——刷三轮红灯会被认为不熟悉流程。
- **找对人 review**：看该目录的 OWNERS 文件，reviewers 和 approvers 是两批人；
  在 PR 里用 /cc /re-request 之类命令主动请人，而不是等。
- **改动要小**：一次 PR 控制在几百行以内，功能与重构**分两个 PR** 提。
- **测试与代码同 PR**：修 bug 必带能复现该 bug 的测试，否则 review 第一句就是"有测试吗"。

## 组织结构与节奏（讲得出这些显得真在里面待过）

- **SIG**（Special Interest Group）按能力域切：网络、存储、节点、架构、可扩展性……
  你的改动属于哪个 SIG，就去那个 SIG 的例会和频道露脸，别只在 GitHub 上喊。
- **wg**（working group）是跨 SIG 的临时议题组，**subproject** 是 SIG 下的代码归属单元
  （很多仓库不在主仓库里，主仓库只是编排）。
- **权限阶梯**：community member → 某仓库 reviewer → 某目录 approver。
  逐级靠"被合并且被验证有效"攒出来，没有考核表格可刷。
- **发布节奏**：一个 release cycle 约 4 个月，中间有 feature freeze / code freeze /
  release note 截止三个门。**错过 freeze 的改动会被 /hold 到下个版本**——
  这就是"为什么我的功能在下游发行版晚一个版本才有"的标准答案。

## 被拒了怎么办（面试官真正想听的一段）

被拒的三类原因，以及各自的下一步动作：

1. **范围不属于这个 SIG** → 问清楚该找谁，把提案转过去；不要在被拒的仓库里反复重提。
2. **缺设计先行** → 补一页"为什么/非目标/替代方案"，回到 issue 或 SIG 例会讲，再回来写代码。
3. **与既有抽象冲突** → 这通常是**最有价值的一拒**：说明你已经理解了这个组件的边界。
   面试里的讲法是"我当时以为缺个功能，后来发现它是故意不做，因为 X"。

**绝对不要做的**：在 issue 里 @ maintainer 催、开第二个 PR 绕过 review、把被拒的改动包装成"我贡献过"。

## 关键 trade-off（面试必聊）

| 选择 | 换来什么 | 代价是什么 |
|------|---------|-----------|
| 自己维护 fork vs 推到上游 | fork 立刻可用、不受评审节奏约束 | 每次升级重解冲突、招聘方无法核查、团队其他人拿不到修复 |
| 广度（刷 30 个小 PR）vs 深度（1 个真实 bug 跟到底） | 广度好看 | 深度才可核查，且深度才能讲出组件边界 |
| 运维型贡献（triage / 文档 / 测试）值不值得写进简历 | 值得，但前提是说得出"它防住了哪一次回归" | 只写"参与社区"会被判为空话 |
| 用开源 vs 改开源 | 会用是及格线 | 本仓库 SRE 角色卡的红线就是"只会用开源，不懂原理"——贡献是证伪这条最硬的证据 |

## 常见误区（90% 候选人栽）

- ❌ 把"我读过 kubernetes 的调度器源码"当贡献——被追问"入口函数是什么、第几个 filter"就穿帮。
- ❌ 简历堆一串 PR 链接，说不清改了什么、谁 review、进了哪个 tag。
- ❌ 未签 CLA 先开工，写完 500 行卡在一纸流程上。
- ❌ 直接提 PR 不先开 issue（十有八九被关）。
- ❌ 一个 PR 既改行为又重命名一整个包。
- ❌ 把 typo/纯格式 PR 当成"社区贡献"计数——面试官一屏就能看出来。
- ❌ 说"我们给社区提了个 issue 就完了"：issue 是**最低**成本的贡献，讲的时候要按它本来的分量讲，
  别拔高——拔高后被追问会整体失信（同"报数字不给分母"一个性质）。

## 面试钩子

**及格线**：能讲清以下任一题 → 可信
- "你怎么在一个自己没用过的仓库里定位问题？"（答法：从失败测试 / 日志字符串 / OWNERS 反查入口）
- "说一个你被 maintainer 拒绝的改动，为什么被拒？"
- "上游一个 bug 你为什么不自己修完拉倒，非要推上游？"
- "你怎么判断该给哪个 SIG 提？"

**加分项**：
- 报得出 PR 编号 / 目标仓库 / approver 的 handle / 落在哪个 release tag
- 知道 verify、freeze、/hold、OWNERS 这些流程词并用得准
- 讲得出 KEP 的结构（为什么 / 非目标 / 分阶段启用 / 回滚方案 / PRR）
- 把贡献和自己生产事故连起来："这个 bug 就是当时那次告警的根因，修完回归测试我补了 e2e"

**追问方向**：
- "那次改动上线后，下游什么时候拿到的？为什么？"
- "你 review 过别人的 PR 吗？你拒过什么？"
- "社区沟通和公司内沟通有什么不一样？"

---

**维护者注**：本文档每半年 review 一次。CLA 主体、release freeze 时间、SIG 划分都会变；
不变的是"可核查"这条判断线——能被验证的才叫贡献，不能被验证的只是话术。
